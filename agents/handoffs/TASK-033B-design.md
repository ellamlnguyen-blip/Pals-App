## Bounded stages after decision

**Stage C — poll persistence and authorization.** After ADR acceptance, add private poll/option/vote/retry tables and caller-bound RPCs in an additive migration; use the exact DM generation or Hangout conversation as source. Implement current access checks, source-then-poll lock order, one current vote, creator close, immutable options, idempotent create/vote, bounded reads and rate limit. Database tests cover forged source IDs, nonparticipants, pending/terminal DM, leave/removal/cancel/block/gate/readiness/opt-out, exact and changed-payload retries, concurrent votes/close, counts and voter privacy. No UI in this stage. Review migration for authorization and retained evidence before dependent UI dispatch.

**Stage D — poll UI.** Use only Stage C authorized APIs in both accepted DM and Hangout threads. Show question/options, aggregate counts, own vote and closing state, pending/error/retry and small-group inference note. Verify actual desktop/narrow rendered create/vote/close, denied state and no voter list. Do not display a poll in DM requests.

**Stage D2 — friendship-formed DM.** Only after explicit ADR-0016 amendment acceptance: the first actual send between current accepted eligible friends atomically creates an accepted friend-origin pair or transitions an existing pending pair to friend-origin accepted and appends the message to that same generation. Record consent provenance without claiming independent recipient request acceptance; backfill existing accepted pairs as request-origin, preserving pending/terminal rows and history. Keep nonfriend request/recipient accept/ignore path. Friendship acceptance alone never creates a thread or transitions pending state. Old terminal generations/messages never revive. Retained directional suppression still applies to nonfriend requests; a new accepted friendship may authorize a new friend-origin generation, with bilateral blocks always denying. Recheck friend-derived consent for reads/sends/retries; unfriend pauses friend-origin access until friendship returns or the recipient explicitly accepts DM access through adapted request UI, recorded as independent consent. Request-origin accepted pairs keep that independent consent. Test first send vs unfriend/block/opt-out, pending transition, suppression, stale/terminal generations, retries and opposite-direction concurrency. Verify persistent backend and authorized UI path.

**Stage E — co-host invitations.** Only after explicit acceptance of the ADR-0012 change: add private pending invitation/retry ledger and source-authorized invite/accept/decline/withdraw/status RPCs. Revoke or narrow direct promotion in the *same* migration. Reuse existing assignment model, Hangout revision, shared lock and live eligibility. Add one target invitation notification code, revocation-aware inbox projection and UI; host reads authoritative response status without acceptance/decline notification fan-out. Test invite vs leave/removal/block/cancel/demotion and duplicate/replayed responses; confirm no powers before acceptance and no auto membership.

**Stage F — reminder.** Ella chose one hour before start. Commit bounded backend schedule/config and server-owned occurrence identity. Verify reschedule, cancellation, joining/leaving near due time, blocks/readiness, gate/mute races, repeated job delivery, catch-up policy and bounded load. A browser tab cannot be required to generate it. Obtain environment-specific schedule and persistence evidence at final sign-off.

**Stage G — three optional activity categories.** Add default-off independent owner preferences and durable source evidence for newly published Hangout, friend creation and friend join. Build bounded backend fan-out with current discoverability/friend/block/preference checks and deterministic single-row precedence for overlapping categories. Test opt-in/out races, campus scope, restricted visibility denial, rejoin/retry, friendship teardown, full-campus load bound and revoked item projection. Stage G may need further schema design review before implementation if safe durable fan-out is unavailable; never create unbounded in-transaction campus notifications.

**Stage H — integration/release.** Fresh reviewer checks cross-source lock order, grants/RLS, data preservation, migration tests and rendered E2E. Synchronize MVP/notification/messaging/auth docs and handoffs; coordinator publishes records. Parent remains incomplete until accepted code integrates to canonical main, task and main remote SHAs are verified, Ella signs off the concrete hosted backend/application candidate, and the named environment proves persistence and authorized reads. No stage silently enables hosted gates.

## Decisions for coordinator to obtain

Ella resolved two choices: DMs may start through current accepted friendship or an accepted message request; start-soon means one hour before. Coordinator still needs explicit acceptance or amendment of proposed ADR-0042, especially the ADR-0016 friend-origin first-send/pending/suppression/consent policy, ADR-0012 co-host invitation replacing immediate promotion, and poll privacy/rate bounds. Existing four notification categories remain default on; only the three new optional activity categories default off.

The coordinator should keep dependent permission/schema implementation on hold until ADR acceptance, while independent Stage A UI review and existing-flow verification can proceed.
