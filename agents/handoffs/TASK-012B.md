## Outcome

Added a request control to authorized People detail, plus a private `/people/friends` page linked from People and the owner profile. The page reads caller-owned relationship ID/generation/direction/state through reviewed RPCs, pages by peer ID at 24, and fetches optional name only through a fresh `get_people_detail` call per row. Active owners who lose readiness still get ID-only management. Ready owners can submit an exact known relationship ID for a People block even if text or friendship status has become unavailable. No peer photo, raw profile, private table, Hangout permission, notification, migration, or hosted behavior was added.

Create uses one client-generated UUID per live request intent and retains it for a same-intent retry after an uncertain response and successful status recheck. Transitions use the currently displayed immutable generation and a server-side fresh preflight read. Decline/cancel/unfriend/block confirmations describe their local effects. Writes are followed by authoritative status reads; an empty pair is described only as current absence, and stale/unknown transitions disable further mutation until recheck or reload. Outbound block success is proved by finding the exact ID in bounded paginated `list_people_blocked_ids`; `get_people_detail` absence is never treated as block proof. The existing detail block confirmation now says any current friendship ends even with the friendship gate off.

## Independent review corrections

The first exact-tip review found that a People detail preflight could succeed, then a peer opt-out or block could make `create_friend_request` fail while `get_friendship` returned an empty pair. The old result left the detail text and retry action visible. Create now distinguishes a confirmed RPC denial from transport uncertainty and rechecks `get_people_detail` after the authoritative relationship read. A detected loss returns unavailable and clears the detail; a visible explicit denial returns stale with mutation disabled. Only an uncertain transport response with a still-visible peer and an empty current pair permits retry using the same in-memory key. A confirmed write followed by an empty pair is stale, without a success claim. The pure outcome regression tests revoked detail, explicit denial, confirmed disappearance and uncertain same-key retry. The actual Auth/action suite also verifies an opted-out peer produces an unavailable create result.

The review also found that the known-ID block control could immediately repeat after an unknown paginated proof or lost response. It now locks after every attempted block, shows a full reload and outbound blocked-ID link, and maps only the exact outbound-ID match to confirmed. A state regression checks unknown/other/confirmed mappings, and the real action suite verifies a People-gate-off block returns unknown with no-store response. The focused rendered retest of this corrected control could not run because the Mac locked and the browser automation inventory reported no browser surfaces. The earlier desktop/phone/keyboard rendering evidence applies to the unchanged row/dialog layout; the corrected unknown-lock state was verified by code/unit/real action rather than a new screenshot.
