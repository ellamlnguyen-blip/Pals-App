## API and state design

New private relations: `pilot_account_admission(account_id,state,revision,created_at,updated_at)`, `pilot_admission_managers(account_id,state,revision,created_at,updated_at)`, `pilot_availability(singleton,enabled,revision,created_at,updated_at)`, `pilot_capabilities(key,enabled,revision,created_at,updated_at)`, `pilot_management_audit`, `pilot_management_requests`, and separate `pilot_manager_audit`. Live roster and manager account foreign keys use ON DELETE CASCADE, matching the existing Auth/account lifecycle. Immutable audit and idempotency receipts store historical actor/target UUID values without an account foreign key, following existing moderation audit practice. This adds no account-deletion restriction or new hosted retention/deletion policy; historical UUIDs never confer live authority. No backfill, manager inference or admission seed. Policy and thirteen capabilities seed false/revision 1. All relations RLS enabled, explicit PUBLIC/anon/authenticated revokes, no policies/grants permitting client table access. Missing policy denies and mutation does not recreate it. Roster and manager absence is state absence/revision 0, not active.

Public authenticated-only signatures:

- `set_pilot_account_admission(p_account_id uuid,p_state text,p_expected_revision bigint,p_reason text,p_request_id uuid)` returns `(state text,revision bigint)`.
- `set_pilot_policy(p_key text,p_enabled boolean,p_expected_revision bigint,p_reason text,p_request_id uuid)` returns `(enabled boolean,revision bigint)`. `p_key='availability'` selects the singleton; otherwise exact capability allowlist applies.

No actor input, manager assignment, arbitrary subject reader, roster list, email resolver, SQL input or source-data read. Caller derives only from `auth.uid()`. All mutable functions VOLATILE SECURITY DEFINER, empty search_path and fully qualified identifiers. Manager authorization requires current active account and current active manager row, without student membership/readiness/admission or availability requirement.

Normalize reason through unchanged `private.profile_trim`, Unicode character length 1–2000. Nonnegative expected revision and nonnull request UUID required. Fingerprint is canonical JSONB array of operation, target/key, desired state/value, expected revision, normalized reason (stored exact JSONB, avoiding reliance on hash collision resistance). Ledger primary key `(actor_id,request_id)` spans both operations. Exact retry checks current manager/account authority before ledger return, returns saved minimal receipt only and appends no audit. A changed payload, operation or actor cannot retrieve another actor's receipt. New authorized same-state request creates one successful no-op audit/receipt, retains revision and causes no secondary effects. CAS checked before mutation/no-op; mismatch atomically denies. Every first roster insert revision 1; each actual transition increments once. Activation checks current UNC account/Auth/membership/campus evidence without profiles/photos. Revocation requires target account existence but may proceed after email/membership/campus loss. Audit records actor, operation, target/key, old/new state/value, old/new revision, reason, request and server time. Audit/ledger UPDATE/DELETE triggers reject even privileged ordinary cleanup; full disposable reset owns immutable fixture cleanup.

## Exact graph and modes

Every management new operation AND exact retry, plus the fixture-only trusted manager writer, uses this order and holds transaction locks through commit:

1. Reject isolation other than READ COMMITTED. Acquire unchanged `private.social_hangout_mutation_lock()` = exclusive transaction advisory `(16016,1)`.
2. Acquire **exclusive** transaction advisory pilot evidence key `(16027,1)`. This single key deliberately serializes ALL roster/manager/policy/capability existence and state changes, including absent rows. It occupies the existing two-integer advisory namespace and is distinct from social `(16016,1)`, moderation `(17017,1)` and one-integer request hash keys. The trusted writer uses exactly these same keys, not just a row lock.
3. Lock singleton policy row SHARE (UPDATE for availability mutation); lock capability rows in key order, SHARE generally and UPDATE only the changed key. Check seeded row presence. Manager operations do not require enabled policy, but missing singleton denies policy mutation and student helpers later deny closed. Admission mutation may proceed with availability off.
4. Lock involved **account UUIDs sorted ascending**, removing duplicates: actor then target are not positional ordering. Accounts SHARE; no status write from A1a. These locks block external moderation account UPDATE, deletion and privileged status updates.
5. Lock manager rows for the same sorted UUID evidence set SHARE (UPDATE for trusted manager target), then roster rows sorted UUID SHARE (UPDATE for admission target). Missing rows are protected by step 2, not imaginary row locks. Trusted writer uses same order for bootstrap, update and no-op.
6. For activation only, target Auth row SHARE, membership row SHARE, then its campus row SHARE, with campus UUID derived exclusively from the current tuple returned by the locked membership SELECT (never a pre-lock or JWT value). All actual row locks are retained. Re-read exact current confirmed email and membership equality, allowed exact-domain UNC slug and active campus/account after all waits. Missing membership denies activation; absence never grants access. This path never locks profile or Storage rows.
7. Check live actor/account/manager again in a separate READ COMMITTED statement after every potential wait and immediately before retry return/write. Recheck target/config and CAS using fresh statements after locks. Then ledger/audit append and target change atomically. Global boundaries serialize duplicate requests; no additional request advisory order is needed.

Steps 4 and 6 may wait on external source writers, because neither Auth nor moderation writers currently take the new evidence key. PostgreSQL row locks, not the new advisory key, protect against those writers. Sorted UUIDs remove intra-A1a inversion. Existing external Auth deletion can acquire Auth then accounts, and membership/campus maintenance can conflict with activation's account/Auth/membership/campus ordering. PostgreSQL deadlock detection may abort one transaction; do not catch and convert deadlock/serialization/lock timeout into a success or receipt. A transaction that survives must complete fresh authorization; abort is an accepted safe outcome. No promise of universal deadlock freedom against privileged or provider transactions is made. Tests must identify abort evidence separately from observed waits and successful commit-order proofs.

Account deletion is an external Auth/accounts writer, not a manager-state mutation: account SHARE held by the operation blocks deletion until commit. If deletion commits first, fresh account/manager checks deny new calls and retries; if an authorized operation commits first, subsequent deletion cascades only its live roster/manager rows while historical audit/receipt UUIDs remain private. Account deletion does not transfer admission to any replacement UUID. Observe both commit orders and verify no additional deletion restriction is introduced by these new relations. Manager revocation/assignment, absent-manager and absent-roster races serialize via steps 1–2. Writer commits first: operation waits then denies revoked manager/target or stale CAS, or sees the new authorized manager. Operation commits first: writer waits and can later revoke; the earlier authorized receipt remains historical. Exact retry after manager loss denies before consulting/returning ledger. Policy changes/shutdown serialize through the same keys and locks; manager authority is independent of availability, so a management operation after shutdown may succeed while ordinary student access in A1b must deny. Expected-revision competing operations cannot silently upsert over one another.

## A1b contract for direct writers and source mutations

A1a introduces a private non-client `pilot_evidence_lock()` primitive for transaction **shared** advisory `(16027,1)` and a write primitive for exclusive mode. Existing social RPCs in A1b acquire social first, then shared evidence before policy/admission evidence rows and other source locks. A1b must reconcile each existing RPC source order explicitly rather than introduce a row-to-social inversion.

Direct profile UPDATE already locks profile before its BEFORE triggers. Storage INSERT/DELETE already acquires its row before triggers; delete may later acquire profile UPDATE, and profile photo assignment locks Storage KEY SHARE. These direct paths cannot be claimed serialized by social lock and must **not** take social after their row locks. Their A1b live trigger obtains shared pilot evidence after the direct row lock, then current policy/capability/roster SHARE and sorted account/Auth/membership/campus evidence locks; it rechecks caller-bound onboarding eligibility after waits. The A1a management exclusive boundary never locks profiles/Storage, so it cannot form a profile/Storage ↔ evidence cycle by itself. Future RPCs holding shared evidence and then profile/Storage can still encounter preexisting row-first profile/Storage inversion: safe PostgreSQL abort is permitted, stale authorization never is. A1b must document/test that graph and keep direct trigger checks VOLATILE; RLS statement-snapshot checks alone are insufficient.

Existing direct writer account SHARE is compatible with A1a account SHARE. External account UPDATE causes waits; no A1a UPDATE-account upgrade is introduced. Ordinary admission changes lock no profile/photos, so direct writer shared evidence held to commit gives two outcomes: direct write first may stand; admission/policy writer first forces direct trigger wait and current denial. A1b must prove both with observed waits, including absent roster and missing policy. Stronger isolation fails closed via the lock helper before writes; existing photo row consistency abort semantics remain preserved. Snapshot reads or already delivered bytes may finish under existing ADR0021/0027 limits; this design does not recall them.

## Trusted local manager fixture provenance

No hosted bootstrap procedure or public manager RPC is introduced. Fixture-only private trusted function uses `session_user` captured inside SQL as actual database executor, not a caller actor string; it accepts target UUID/state/CAS/reason/request, uses graph above, and appends immutable separate manager audit with executor, original SQL role from `current_setting('role',true)`, server backend PID and server timestamp. Function execution is revoked from PUBLIC/anon/authenticated/service_role; only migration-owner postgres local fixture channel can execute. Before touching authority require `session_user='postgres'` AND `current_setting('role',true)` in `('none','postgres')`; capture that original role setting in audit. SECURITY DEFINER changes `current_user`/`current_role`, so neither is proof of the caller's original role. Actual-role tests explicitly SET ROLE authenticated/anon/service_role under a postgres session and must still deny this path; no arbitrary executor/actor field is accepted. Postgres is the independently identified actual local test executor, not an asserted real-world named person; hosted provenance remains excluded. Fixtures cannot claim client/RLS evidence through that privileged path. HTTP client manager sessions use Auth-issued UUIDs and actual authenticated requests.
