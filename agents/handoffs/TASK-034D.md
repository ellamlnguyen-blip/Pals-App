## Owned changes

- `supabase/migrations/20261015000900_pals_similarity.sql` adds an authenticated-only `browse_similar_pals(p_major,p_graduation_year,p_cursor,p_limit)` JSON page with the existing five safe browse fields. It returns `items`, `has_more`, and an opaque cursor. It does not accept a name query or return scores, hometown, interests, private revisions, hidden counts, or evidence of a match.
- The migration adds a client-revoked, RLS-enabled private snapshot table with one row per owner, random handle, campus/filter/owner-revision/ranking-version binding, up to 10,000 candidate IDs plus profile/rich-consent revisions, five-minute expiry, bounded expired-row cleanup, and a limit of 30 distinct snapshot creations per minute. An identical first-page result reuses the live handle, avoiding refresh/back-navigation failures. A changed candidate list replaces it. Candidate scores are never stored. Cursors are random issued tokens mapped privately to offsets; copying a token to another owner/filter or changing its bytes is denied.
- `supabase/tests/database/pals_similarity.test.sql` is a transactional pgTAP fixture for normalization, distinct interests, >24 pagination after filters, cursor binding/forgery (including a known private snapshot handle with a fabricated offset), no score/private projection, raw profile denial, stale profile revision, rich-gated hometown ordering and rich withdrawal. It has **not** run.

Ranking uses normalized exact interests (+2 each, max four), major (+3), graduation year (+2), and hometown (+1 only with current rich gate, viewer People choice, and subject rich choice). It filters all eligible candidates before scoring/limit, sorts score descending then normalized name under bytewise `C` comparison and UUID, and retrieves display fields with fresh `private.people_visible` and filters on every page. The browse holds the shared social mutation lock, owner profile and rich-gate row locks, then locks ranked subject profile/rich-preference rows and revalidates their revisions/consent before projection; the locks last through response construction. This closes the first-page ranking-to-display and later-page revision-to-display gaps for those inputs. Candidate profile/rich revision or rich-choice changes make an old cursor stale. People/account/email/campus/block changes remove a candidate on a later page; a changed global rich gate or owner choice makes the snapshot stale. Owner profile revision changes make it stale. `has_more` is computed after scanning live candidates. The old `browse_people` API remains for compatibility.

## Proposed documentation wording for coordinator

Product: “Pals browse filters by major and graduation year, then orders eligible same-campus profiles by saved interests, major, graduation year, and hometown where rich sharing currently permits that hometown. The list does not reveal a score, private match detail, popularity signal, or a name-search control. A refreshed list may reorder after profile edits.”
