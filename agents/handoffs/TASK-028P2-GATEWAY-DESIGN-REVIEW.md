# TASK-028P2 lane B — peer photo gateway security design review

Date: 2026-10-06. Review baseline: `9913df3a663d96b097847ea830db063de77cfa46`. Scope: read-only review of the accepted ADR-0036/0037 and rich-profile contract against existing auth, profile-photo, Storage and People code. No gateway, resolver, schema, hosted state or fixtures were changed by this review.

## Decision

**Conditional design clearance for implementation with a two-check gateway.** The proposed service-only resolver is defensible under the accepted contract if the route binds `actor_id` solely to `auth.getUser()` on the request-cookie user client, the resolver independently checks the entire rich predicate in one statement snapshot, and a separately constructed server-only service client performs only the resolver and exact private-object download. Current owner-only Storage RLS offers no user-bound peer download without widening raw access or introducing a bearer URL, both excluded by the accepted policy. A service credential is a broad backend credential, so module and environment isolation, role grants, and negative HTTP tests are required; the RPC itself cannot narrow a leaked key's general privileges.

### B1 — deleted Storage names can be reused; revalidate after download

`profile-photos` rejects overwrite of an **existing** object name (`20260927000200_pilot_owner_admission.sql`, `private.reject_client_profile_photo_update` and the insert existence check). It does not reserve a name after deletion. The owner upload form uses `crypto.randomUUID()` (`apps/web/app/profile/actions.ts`), but an authenticated owner can use the Storage API directly with a previously deleted name under the current owner/path policy. A resolver may authorize object A at a selected path/revision. The owner can then detach A (advancing revision), delete A, and upload different object B at the same path before the gateway's path-based Storage download. The download could return B, which was never the object authorized in that snapshot. Checking object metadata ID in the resolver alone does not bind a later path-only download to that ID.

The narrow mitigation is **two fresh resolver checks**, one before and one after the exact-path download, with no bytes returned until the second succeeds. Each resolver call must return the current `storage.objects.id`, exact path and profile revision to the server. The second call must re-evaluate the full rich predicate under a fresh READ COMMITTED statement snapshot for the same actor, subject, slot and expected revision; require identical object ID, path and revision. Any null, error or mismatch yields a neutral miss and discards buffered bytes. Detach/delete/reupload of a name advances the profile revision, and a re-created object gets a different ID; both are caught. Supported owner overwrite of a present object is rejected by the current Storage UPDATE trigger. A revocation after the second authorization check may still complete under the documented request-snapshot rule. Do not substitute a metadata-only second check or compare path alone.

Before use, demonstrate with real Storage that a direct owner `upsert` cannot mutate bytes while retaining the same object ID and profile revision; verify the current SQL trigger covers Storage finalization as observed, not just synthetic SQL. Test detach/delete/reupload at the same path between first resolution and download and during download, with a neutral 404 and no bytes. If Storage has a supported same-ID overwrite path that bypasses the trigger, add an immutable object-version guarantee or defer peer photos. A durable no-reuse ledger is a fallback, not a prerequisite if these invariants hold.

## Binding and resolver requirements for implementation review

- The route must use the existing cookie-backed `supabase()` user client (`apps/web/lib/supabase.ts`) and call `auth.getUser()` for every request. Pass only that returned `user.id` as `actor_id`; do not accept an actor from URL, body, headers, cookies or a decoded JWT claim. A missing/errored Auth result denies without invoking the service client. Keep the service client in an `import "server-only"` module, with a separate secret variable, no cookies/session persistence, no client component import, no service secret in `NEXT_PUBLIC_*`, response, logs or analytics. The existing `authConfig()` correctly permits only publishable/anon credentials for the user client (`apps/web/lib/config.ts`); do not relax it to provision the gateway.
- Grant resolver EXECUTE only to `service_role`, revoke default PUBLIC/anon/authenticated, set empty search path, require `current_setting('role', true) = 'service_role'`, reject stronger isolation, and return no row for missing/denied/stale. A service caller-supplied actor remains trusted **only because** the route verified and supplied it; direct service calls can impersonate users. Test this server-trust assumption through route behavior and SQL grants.
- In one set-based statement snapshot, join the current actor/subject Auth, account, membership, campus, People and rich preferences, both feature gates, pilot availability/capability, subject text publishability, bilateral blocks, selected profile slot/revision and `storage.objects` owner/bucket/path-prefix/object ID. Do not call volatile helpers in separate statements or use the legacy `get_people_detail` result as authorization. Match `20261004000100_confirmed_unc_email_immediate_access.sql` for live confirmed exact-allowlist Auth evidence. Require distinct actor/subject and the requested positive revision equal to the current profile revision. Resolve only `primary` or `0`–`3`; absent slot/object is neutral miss. Return the exact current object path only to the route. Download that exact path once; never retry by slot or a client path.
- The route must treat the profile revision as a stale-URL guard, not proof that an object remained selected throughout the subsequent fetch. Revalidate the full predicate and object identity after download as B1 requires; the documented snapshot rule applies after that final check.

## Image and HTTP boundary for implementation review

Cap **downloaded bytes before buffering** at 5 MiB, with abort/timeout and bounded simultaneous decodes. A post-`storage.download()` `Blob.size` check alone does not cap memory/network work because the SDK may have already buffered the response. Check JPEG/PNG/WebP magic, then decode with a maintained library configured to reject corrupt and multi-frame inputs and to enforce at most 20 million input pixels; inspect frame/page count explicitly rather than assuming only one frame was decoded. Auto-orient, resize to at most 2048 by 2048, re-encode a single safe JPEG/WebP frame, strip EXIF/ICC/comments, and enforce a bounded output size. Do not pass through original bytes or MIME. The contract's generic “reject polyglot” requirement needs a concrete testable parser rule; magic checking alone cannot identify every valid image with appended payload. Re-encoding is the decisive output boundary, while known appended/embedded active formats should be denied.

Parse exactly one `slot` and `revision` query value and bounded UUID path segment; reject duplicates, malformed syntax and unexpected parameters with 400 if applicable. Never let a query field become a Storage path. Return 404 for unavailable/denied/stale/missing object, 503 for infrastructure/decode failure as specified, and no library or Storage error text. All responses, including `HEAD`, `OPTIONS` and exceptions, need `Cache-Control: private, no-store, max-age=0`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`, no validators, no redirect, and no cached transformation. Explicitly reject non-GET methods; do not rely on framework defaults to supply the privacy headers. `dynamic = 'force-dynamic'`, `revalidate = 0` and `fetchCache = 'force-no-store'` match existing dynamic peer pages but are not substitutes for response/CDN checks.

## Required evidence before gateway use

Show direct authenticated/anon resolver denial, a service-role-only SQL invocation, forged actor and copied-URL route denial, all predicate revocations, stale revision/slot replacement and missing object. Exercise both resolver-before-change and change-before-resolver orders, plus deletion/reuse during fetch under B1's two-check rule. Verify real local Storage fresh upload, rejected upsert/overwrite and same-name reupload behavior, then hostile images (oversize, decompression bomb, animation, corruption, EXIF/GPS, orientation, polyglot cases), actual output metadata and every success/error/method header. Provision only the exact disposable-local secret through root's local environment step; do not print or commit it.

No hosted key, hosted operation or application integration is cleared by this review. Concurrent DATA lane files were not inspected as final work and remain subject to their own handoff/review.
