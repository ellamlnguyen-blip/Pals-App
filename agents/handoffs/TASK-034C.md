## API and policy

`public.list_my_chat_attention(p_cursor text default null,p_limit integer default 24)` returns JSON with `items`, `has_more`, and `next_cursor`. Each item gives source kind/ID, allowed peer ID or Hangout title, direction/state where applicable, `sort_time`, and an owner-only `has_unread` boolean. The first page evaluates all currently eligible DM generations and joined Hangouts, then stores an ordered-ID snapshot for five minutes. Subsequent pages reauthorize each ID, skip revoked entries and derive `has_more` from remaining live entries. The cursor has a private-key digest and binds to the owner's active snapshot; a new first page replaces it. There are at most 10,000 IDs per snapshot. A duplicate first-page request within 100 ms reuses the active snapshot to absorb ordinary mount/focus refreshes; later first pages replace it. Expired snapshot cleanup is a private, client-revoked pg_cron job that removes at most 100 rows per run, following the existing notification-job pattern; student list calls perform no cross-owner cleanup.

Security review correction: the live owner account/confirmed-email/campus/feature gate now runs before any account row lock, cursor parsing, or candidate read, including later cursor pages. First-page creation takes the existing shared social/Hangout mutation lock before the account row lock and repeats the owner gate after each wait. This serializes source creation between the 10,001-ID precheck and full ranking query, while respecting source-writer lock order. The first page detects the 10,001st eligible source ID before message aggregation. `chat_attention_source` and `chat_attention_visible` are SQL `STABLE` helpers; their called authorization helpers in this projection are also `STABLE`, and DM eligibility/consent checks are inlined against current tables. Each page row binds source authorization, allowed metadata, watermark, and activity to the calling SQL statement snapshot. This avoids nested `VOLATILE` PL/pgSQL statements taking newer snapshots after a source guard. A revocation committed before the statement denies the row; an already running statement retains the existing read-in-flight limit.

`public.touch_my_chat(p_source_kind text,p_source_id uuid)` accepts an accepted/readable DM generation or currently joined Hangout, uses server time, and throttles writes for five seconds. It does not advance read state. `public.acknowledge_chat_page(p_source_kind text,p_source_id uuid,p_highest_visible_sequence bigint)` accepts only a sequence in the first 50 currently visible messages after the saved watermark, advances monotonically, and rechecks source access after existing shared social/pair or Hangout parent lock waits. A prior watermark replay is harmless while source access remains current.

DM management rows follow active pending/accepted generation membership; only pending recipients or accepted consented participants receive body-derived unread state. Friend-origin accepted DM pauses without current friendship unless recipient consented independently. A blocked/terminal generation is absent. Hangout access uses `private.chat_authorized`; blocked-author messages are excluded before latest activity, unread, and forward-page validation. A Hangout rejoin reuses its prior owner watermark. An old DM generation cannot confer access to a new one. Owner gate/account/email/campus checks remain live. Private tables are RLS enabled and have no client grants; private helpers are client revoked. No peer receipt, message body, count, hidden sequence, or raw private table is returned.
