### Blocking finding: exact object path can change during URL construction

`downloadPeerPhoto` builds a URL from `object_path.split('/').map(encodeURIComponent).join('/')`. `encodeURIComponent` leaves `.` and `..` segments unchanged; WHATWG URL parsing normalizes them. For example, a resolver-returned metadata name `subject-id/../victim/photo.png` becomes a request for `/profile-photos/victim/photo.png` while both resolver snapshots still bind to the original `subject-id/../victim/photo.png` metadata object. The SQL predicate checks subject prefix and owner but does not require a canonical photo filename. The current authenticated owner Storage INSERT policy admits only `subject-id/[a-f0-9-]+.(jpg|png|webp)`, so ordinary owner writes cannot create this metadata row; a broad service backend credential and exact-object contract must not assume that policy alone prevents the path mismatch. Require an exact canonical path grammar aligned to the owner Storage policy before any service fetch, reject dot/empty/encoded/backslash ambiguity, and add a regression proving URL construction cannot target another object. Re-review the fix before clearance.
