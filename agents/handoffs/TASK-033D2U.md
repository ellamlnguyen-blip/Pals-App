## Outcome

- `/api/dm` first send accepts an explicit `mode: "friend" | "request"` with the same validated peer, UUID key and 1–2000 character trimmed body. Omitted mode remains request for the existing client/test contract. Friend mode calls `public.send_friend_dm_message(p_peer_id, p_request_id, p_body)` and normalizes its returned `generation_id`. Request mode calls `public.create_dm_request(p_target_id, p_request_id, p_body)`. A fresh accepted friendship with no active DM pair returns `stale` for an old request-mode page instead of issuing a new request; an active pair still reaches the backend for exact retries. Both modes retain fresh cookie-bound `dmAccess`, People detail, no-store and backend source authority.
- A friendship status RPC error in request mode returns retryable `kind: error`/503 before any creation. The People composer retains its frozen mode, body and key for the same retry.
- `/api/dm/[id]` GET and POST use the new caller-bound `public.get_dm_consent_ui_state(p_peer_id)`. Existing body pagination and first-page pause probe remain. `friend_send` sends with `public.send_friend_dm_message(p_peer_id, p_request_id, p_body)` only on an active pending pair with current friend capability. `allow_dm` calls `public.accept_friend_dm_consent(p_peer_id, p_generation_id)` only when the current projection says the actor is the eligible original recipient of an unconsented friend-origin pair. Both actions repeat backend locks and authorization. Existing actions remain.
- People Say hello selects friend or request mode from current friendship, freezes mode/body/key for uncertain retries, and updates the link after confirmed send. An in-page friendship change updates the choice through a narrow optional `FriendControl.onRelationshipChange` callback. Direct thread shows the pending-pair friend conversion composer, and the original recipient's explicit Allow DM action in a readable or paused friend-origin pair. Request-origin pauses are not labeled as friend-consent pauses. The existing conceal-on-auth/visibility behavior remains.
- An uncertain `friend_send` that actually converted the pending pair can be retried with the same key/body/action after the authoritative reader reports `accepted`. The ready composer invokes the frozen action (also preserving an uncertain `reply`), while the API passes accepted-pair retries to `send_friend_dm_message` for the backend retry ledger and current authorization check. A denied mutation immediately masks old bodies, then re-reads the conversation; only an authorized reread may restore the frozen retry and current messages.
- Added additive `20261015000500_dm_consent_ui_state.sql`. The status projection returns `peer_id, generation_id, direction, state, consent_origin, recipient_consented, friend_send_available, can_allow_dm`, only for the caller's active pair under `private.dm_require`; capabilities also require current bilateral DM eligibility. It does not return a body or change existing permissions. Added transactional SQL test for no empty pair, origin, recipient-only action and post-unfriend consent/capability.
