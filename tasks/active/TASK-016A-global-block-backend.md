## Outcome

One caller-owned directional block becomes the database authority for People, friendship, DM, Hangout access, current attendance, group chat and notification projections. New block writes reconcile every retained shared joined Hangout in one transaction, while old stored blocks reconcile before the Hangout gate can reopen. This stage builds only the backend and a temporary accurate web safety boundary. TASK-016B adds reports; TASK-016C supplies the final block/report UI. No hosted operation, production migration, live-user transition, Realtime or co-host power is authorized.

## Lock and transaction contract

The implementation must use a **dedicated namespaced transaction advisory lock for local social/Hangout mutation**, acquired before any request-key lock, pair lock, Hangout row, eligibility/gate row, message row or notification recipient lock. It may serialize all such writes locally; correctness matters more than throughput for this bounded stage. Document the exact key and ensure it cannot collide with an existing single-key advisory hash. Never acquire it from a trigger after the caller already holds a lower-order lock. Rework the RPC entry points themselves, including `create_hangout`, friendship/DM create and send retry paths, and the old `set_people_block` signature. A wrapper is acceptable only if it is the sole client-executable write path and its callee cannot be executed around the lock. Database-side reconciliation also acquires this lock first.

Canonical order among covered writers: **shared mutation advisory lock → relevant request UUID lock → unordered account-pair lock(s) in stable UUID order → all affected Hangout parent rows in ascending Hangout UUID order → source/safety gate and live evidence row locks in documented stable order → pair/conversation/message/participant or provenance writes → notification source-gate/notification-gate locks → recipient advisory locks in ascending UUID order**. Avoid taking a second request or pair lock after a Hangout row. Notification triggers must remain downstream of parent/gate acquisition. The existing photo-delete path can still deadlock with a profile/photo evidence lock as documented in AUTHORIZATION; a database deadlock aborts safely and is retryable, never partially commits a block.

| Covered writer | Existing first/late locks; required revision |
| --- | --- |
| Friend create/transition and `set_people_block` | Pair lock, then eligibility gates/rows, then optional notification gate/recipient. Friendship create has request UUID lock **before** pair; move the shared lock before both. Block must never start at the old pair lock. |
| DM create/reply/send/transition | Request UUID where applicable, then pair, DM/People gates/evidence, pair/message writes, notification gate/recipient. Move shared lock ahead of retry lock. |
| Hangout create/edit/join/leave/remove/cancel/joining-state | Create has request UUID lock; other writers take `lock_hangout` parent row, and edit/cancel/join/leave may later take source/notification gate and recipient locks. Move shared lock ahead of both request and parent. Retain CAS revision semantics. |
| Chat send | Hangout parent, Hangout/chat gates and actor evidence, then conversation/message, then notification trigger gate/recipient. Move shared lock before parent. Reads take no mutation lock and reauthorize by statement snapshot. |
| Safety set/unset and migration reconciliation | Shared lock first; pair then sorted affected Hangout parents; snapshot and recheck after waits; record evidence and mutate all effects atomically, with no ordinary departure/teardown notification. |
| Preference/gate writes | Existing direct privileged local gate switches and owner preference writes do not acquire the new lock. They hold gate/recipient or owner rows only and never later acquire the shared lock; source writers recheck after waits. No client gate DML is added. |

After taking the shared lock, use a fresh READ COMMITTED statement for affected Hangout discovery; then lock the parent rows in ascending ID order and **requery/recheck** the full joined affected set before writes. All join/leave/remove/block operations use this same lock, so no new membership can appear between the final affected-set check and commit. A mutation committed first may stand; a later block wins and tears down overlap. A block committed first makes later join/send/formation deny. Both opposite block directions and multiple shared Hangouts must terminate without row-order-dependent outcomes. A SQL statement that evaluated gate/eligibility before a lock wait is insufficient: recheck in a later statement.

## Historical evidence, reconciliation and retries

Keep `private.people_blocks` as the only block relation. Add minimal private immutable Hangout relationship provenance, recording unordered peer/Hangout overlap and the caller's own participation relationship before transitions can overwrite intervals. On an authorized join (including rejoin), record overlap with each currently joined member under the shared lock; preserve host relationship via immutable Hangout host and caller membership. Record required provenance before ordinary leave/remove and before block/reconciliation departures. Do not retain peer names, photos, messages or location. No client or moderator SELECT. The projection of caller-owned Hangout IDs/state uses existing retained membership, not the peer provenance table.

Pre-migration overlap is accepted only when retained authoritative participant intervals prove simultaneous presence; two rows sharing only a Hangout ID are insufficient. Current joined intervals count; `joined_at` to `left_at`/`removed_at` may prove one last interval; overwritten earlier intervals cannot be reconstructed. Terminal DM generations and immutable host of a Hangout the caller joined are independent sufficient evidence. Existing owned block, retained friendship/DM participation or proven Hangout relationship also permits the new block as ADR-0018 states. Do not infer a peer from a retry key without a stored peer field. Unknown, hidden and invalid target cases receive neutral unavailable. New block requires the safety gate and an active caller, but historical evidence works after readiness/campus/People opt-in loss. Repeating the same desired state with no intervening change has no second side effect; a stale `block=true` request arriving after a deliberate unblock is a new serialized desired-state write and may block again, because this API has no operation key/version. The UI must not auto-retry across an intervening user decision. Unblock deletes only the caller's direction and restores no friendship, DM or membership. Suspended/banned accounts cannot manage blocks.

For a **new** block, compute all initially shared joined Hangouts under the shared lock. In each, a blocker-host removes the joined target; a nonhost blocker leaves, even when the target is host. A target host is never evicted or transferred. Apply the same rules to cancelled records for retained state/evidence while cancellation continues to deny private/chat access. Suppress ordinary leave/removal notifications and avoid automatic reports. For an existing block retry, verify/repair its deterministic separation if needed without widening authority or replaying events.

For **pre-existing** People blocks, the migration leaves every source gate off and reconciles before any Hangout gate can be enabled. Derive one initial conflict snapshot across all retained joined memberships. Within each Hangout, mark every nonhost target of a host-owned outbound block `removed`; independently mark every nonhost blocker in any initially conflicting pair `left`. Where the **same person** qualifies for both, `removed` wins. A host block must not skip unrelated nonhost-blocker departures in that Hangout. Process IDs in stable order while effects are determined from the original snapshot, not a shrinking roster. Preserve provenance before changes. One transaction either completes the full reconciliation or rolls back. Re-running on unchanged data is a no-op, and gate-off/on cycles never restore attendance or permit unresolved stored conflicts. The migration/test handoff must state the exact bootstrap ordering and prove the safety gate, People gate and Hangout/chat gates default false after reset and cleanup.
