# TASK-018A — Private attendance backend

Status: Reviewed contract; implementation blocked on explicit ADR-0022 acceptance
Date: 2026-09-24
Parent: `tasks/active/TASK-018-attendance-confirmation.md`
Baseline for contract: independently remote-verified canonical main `35092024a2b0be5132dd9ee8b84c746fb9c03d2c`

## Goal and ownership

Implement only the database authority for a person's private, self-reported attendance and a bounded ID-only owner projection. This stage does not build the student UI or create notification/analytics events. A fresh task-specific implementation agent works from canonical main after this contract is reviewed/published and ADR-0022 is explicitly accepted. The coordinator owns shared status records and integration.

## Migration boundary

- Add a committed migration with a private, singleton attendance gate initialized false, RLS on every new private relation, and explicit revokes from `public`, `anon` and `authenticated`. The answer relation has one row per `(hangout_id, account_id)`, caller-owned answer boolean, positive revision, server update time and the necessary existing foreign keys. Do not add a public participant attendance field, peer projection or direct table grant.
- Add caller-bound, security-definer exact own-read, bounded owner-list and answer-write RPCs. Derive the actor only from `auth.uid()`; reject unauthenticated, suspended or banned callers and platform-role bypass. The list uses a stable Hangout-ID keyset, at most 24 past retained rows, and projects only own Hangout ID, own answer/revision/answer time, `within_window` and `currently_actionable` booleans. `currently_actionable` additionally reflects the current Hangout source gate; it cannot invite a guaranteed-denied write while that gate is off. Exact read exposes only that caller's answer/revision/answer time for an eligible retained ID. Unknown, foreign and disabled IDs have a neutral unavailable result. Neither path leaks schedule, title, host, location, roster or private details. An unready active owner remains eligible under the accepted policy.
- For every answer write, require READ COMMITTED, take the established global social/Hangout mutation lock first, then lock the Hangout parent row without calling `private.lock_hangout`, which requires ready-campus access and would incorrectly deny the accepted unready or blocked-host owner path. After the parent, lock the Hangout source gate and attendance gate rows `FOR SHARE`, then current account evidence and the retained participant/answer rows in a documented consistent order. Recheck active status, both gates, retained participation, schedule window, pre-start cancellation and no private disable after waits. Use a uniform authorization error for denied writes. Different-value writes use expected revision; identical current-value writes in an open window return current state before revision comparison and never alter time/revision. After closing, all writes deny; exact own-read can recover a response whose acknowledgement was lost at closing.
- Enforce `starts_at`/`ends_at` immutability once the *old* schedule's attendance opening instant has arrived, regardless of attendance gate state. Preserve existing accepted Hangout edits to other fields. The check must be database enforced on the existing authoritative edit path and any direct table path, under the Hangout parent lock with the database clock sampled after lock acquisition. A permitted pre-opening schedule edit atomically moves the attendance window. Verify no old RPC signature or direct write route can move scheduled instants after opening.
- Owner reads require READ COMMITTED and use a single fresh statement snapshot with current gate/account/participant/disable checks for each row; stronger isolation fails closed so an old client snapshot cannot reveal an answer after a committed revocation. They do not require People, safety or Hangout source gates, and do not call `can_read_hangout`, because that would revoke the accepted ID-only path after readiness loss, removal or a host block. They also do not weaken ordinary Hangout detail, roster, chat, notification or safety authorization. The attendance gate off denies all attendance RPC reads/writes and never backfills responses.

## Required evidence

1. SQL tests with actual `anon` and `authenticated` roles: gate-off denial; direct table SELECT/INSERT/UPDATE/DELETE and embed denial; owner/foreign/forged actor/operator cases; host/joined/left/removed cases; unready active, cross-campus and suspended/banned cases; hidden blocked host without source detail; disabled Hangout denial; pre-start cancellation versus after-start cancellation; no source-text leakage in exact/list projections.
2. Clock-boundary and retry tests: explicit end and two-hour fallback; before/open/after 30-day close; first write expects revision zero and stores revision one, then correction, stale conflicting write, identical no-op with stale revision, change-away-and-back, and lost acknowledgement at closing. Freeze schedule in the authoritative edit RPC and direct table path after opening, while preserving title and other allowed edits; pre-opening reschedule moves the window.
3. Observed concurrency with two actual sessions for attendance write versus host time edit, cancellation, moderation disable, account sanction, source/attendance gate revocation, block and participant leave/remove. Verify both commit orders where relevant, no partial answer, no deadlock and no unauthorized result after a committed revocation. Read-side tests cover gate-off flags, after-commit denial, stronger-isolation denial and no source/peer disclosure.
4. Two clean disposable local resets, database suite and schema lint; relevant Hangout, safety, moderation and notification regressions; real Auth/PostgREST calls; workspace checks as available. Record exact commands/outcomes and limits in the handoff. Finish with zero fixtures, all gates false and owned local services stopped. A fresh exact-tip security review must clear P0/P1/P2 before coordinator integration.

## Exclusions and stop conditions

No UI, safety questionnaire, report creation, peer result reader, public aggregate, notification event, PostHog, scheduled work, Realtime, geolocation, host override, hosted migration, production data, gate enablement or deployment. If implementing the accepted ID-only exception requires broader source disclosure or an edit restriction different from ADR-0022, stop that part and propose a reviewed policy amendment. Do not treat this draft or Proposed ADR-0022 as implementation authority.

## Contract review outcome

A fresh scoped GPT-6 Sol medium reviewer identified one parent-lock ambiguity and three narrower projection/retry/isolation issues. The contract now explicitly avoids the ready-only `private.lock_hangout` helper, orders source and attendance gates after the parent, distinguishes window from current actionability, defines first-write revision semantics and requires READ COMMITTED reads. The reviewer rechecked the revision and found no remaining concrete P0/P1/P2 issue. The dispatch tool did not expose Standard-speed verification.
