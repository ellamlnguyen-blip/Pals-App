## Exact action boundary

- Add one narrowly typed caller-bound authenticated RPC, for example `apply_account_moderation_action(report_id, request_id, expected_case_revision, action, reason)`. Derive the actor only from `auth.uid()` and live account/role; require the existing moderation gate, READ COMMITTED, an exact stored `user` report target, and Stage A's self-filed/self-target/own-host conflict rules. Do not accept a separate subject ID or campus/role claim. The target must currently have no platform role, including for replay. A moderator or admin may suspend an active nonoperator account; only an admin may ban an active or suspended nonoperator account and reinstate a suspended or banned nonoperator account. On exact replay, recheck the actor's current action-specific role: a demoted admin cannot retrieve a prior ban/reinstatement result as a moderator. An invalid source state, unavailable target, unauthorized actor, stale revision, gate-off caller, wrong target type or conflicted report receives neutral denial and no mutation/audit. Do not invent a general account lookup or history reader.
- Require a case currently `in_review` and an exact expected case revision. Require a trimmed plain-text reason of 1–2000 Unicode code points. Each accepted new action advances case revision once, closes it with `action_taken` and links a durable private sanction record containing exact report/subject, operator, action, prior/new account status, current campus when available, reason, server time and request ID. Add the minimum private schema and restrictive references needed so a linked `action_taken` case cannot exist without its committed sanction; no report/account deletion may silently erase the audit trail. The sanction and closure must roll back together on any failure. Reopening follows the accepted Stage A case behavior, clearing only the case's current disposition/link while retaining the sanction/audit history; it never reverses a status change.
- Append one server-authored immutable private audit event for each accepted new enforcement action, linked to the sanction and report. It records exact subject UUID/type, current authoritative campus when available, operator, reason, request ID, prior/new account status, prior/new case state and revision. No allegation narrative, profile/photo, message, location or source copy enters the audit or retry ledger. Extend Stage A's private audit/ledger only as narrowly as needed; no raw client grants or general audit browser. Exact `(operator, request_id)` replays with the same normalized payload return the original minimal result without another status/case/audit change, after fresh gate/active actor/role/conflict/target-platform-role checks. Changed-payload reuse fails generically. Ensure a request UUID cannot be repurposed across Stage A case transitions and B1 enforcement under the same operator identity.
- Lock/recheck the gate, live actor role/status, stored report, target account, target platform-role absence and current campus through commit. Reuse the accepted Stage A authorization semantics and avoid new deadlock cycles with TASK-016 safety's shared advisory lock and Hangout-first writers. A status revocation begun first must deny a stale in-flight student mutation; a student mutation that already holds the necessary evidence locks may commit first, then the sanction takes effect. Test both observed commit orders. A second operator's stale case revision or an exact replay after operator revocation cannot apply or reveal a new action. Do not weaken existing RLS, source-gate or safety checks.

## Enforcement surface

- Inventory every current student-facing direct REST table/embedded reader, Storage policy, caller-bound RPC, web API/server action and retained recovery path whose authorization depends on an active account. Ensure a suspended/banned subject loses all authenticated student feature access, including profile/photo, People, friendship, DM, Hangout discovery/detail/roster/join/edit/private instructions/chat, Calendar and Notifications, except its existing own account-status boundary. Existing private safety evidence remains retained; there is no student report/case/audit reader. Enforce at the database or authoritative source boundary, not only by hiding routes. Preserve the intended denial semantics for unknown versus restricted subjects. A Storage signed URL issued before sanction is a bearer capability outside live account checks; stop new owner-issued URLs and app photo reads after sanction, test an already issued URL through expiry, and record this residual exposure without claiming immediate revocation.
- Reinstatement restores only the active account status and newly eligible access under current gates/evidence. It never recreates removed friendships, DM generations, Hangout participation, disabled Hangouts or missed notifications. Do not proactively delete relationships or attendance on sanction unless an accepted source rule expressly requires it; status-based denial is the enforcement mechanism here.
- Preserve operator access only while the operator's own account stays active and their live role exists. Do not let an existing session, JWT claim, old direct RPC signature, service-role web proxy or browser state bypass a newly committed status restriction. Keep owner-only status readable so the existing restricted screen can explain the state.
