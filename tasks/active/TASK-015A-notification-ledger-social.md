# TASK-015A — Private notification ledger and social-source events

Status: Contract under independent review; no implementation dispatched
Date: 2026-09-23
Parent: `TASK-015-notification-inbox-preferences.md`
Policy: Accepted ADR-0017 (user accepted reviewed, main-published proposal on 2026-09-23)

## Outcome
Create a default-disabled, disposable-local notification ledger and owner preferences with safe caller-bound readers, then generate only the friendship and DM events authorized by ADR-0017. The remaining Hangout/chat source hooks and student UI are later stages.

## Required context
Read `AGENTS.md`, parent TASK-015, ADR-0017, MVP/PRINCIPLES, NOTIFICATIONS, ARCHITECTURE/DATA_MODEL/AUTHORIZATION/SECURITY_AND_SAFETY/REALTIME_AND_MESSAGING/TESTING, Accepted ADR-0013/0014/0016 and TASK-012/014 handoffs. Inspect the actual friendship and DM migration functions, grants, retry ledgers, default-off gates, RLS tests and real Auth/PostgREST suites. Use only a fresh additive migration; do not edit prior migration files.

## Allowed work
- Add a private notification gate (disabled after migration), private recipient ledger and sparse or explicit owner preference storage, all with RLS and no `anon`/`authenticated` table grants. Use a unique per-recipient identity `(source kind, immutable generation or message ID, event/transition code, recipient ID)`: friendship/DM request and acceptance are distinct transitions on one generation, while later DM messages use their own server message IDs. Never key an event to a client retry UUID. Retain rows after source teardown; friendship hard deletion must not cascade into the notification ledger, and a later generation is distinct. Store no source body, peer name/photo/email, private location or copied description. Keep event source ID/type/code server-owned and constrained to the supported variants; no generic client insert or admin bypass.
- Add caller-bound, fixed-search-path RPCs to read/change the four optional preference categories; read a deterministic keyset page of at most 24 owner items with read timestamp and a neutral unavailable form; and idempotently mark an owned item read. Authenticated clients may execute these exact RPCs only. Require READ COMMITTED and the notification gate for all caller operations; suspended/banned callers cannot read or act, while an active owner may manage preferences after losing readiness. Denied/missing cross-owner items must not leak existence. No unread reversal or count endpoint.
- Reauthorize each social item's current source in the read projection, after checking recipient ownership. An incoming friendship request is actionable only while the friendship gate is on, that generation remains pending for the recipient and current People projection permits the peer; acceptance only while that gate is on, the same generation remains accepted and peer visibility permits. A DM request/acceptance/message target is actionable only for a current active pair generation with the bilateral current body-read eligibility required by ADR-0016; the reader must not expose text, a hidden peer ID or link after opt-out, block, cross-campus split, readiness loss or gate disable. When unavailable, return only opaque notification ID, generic unavailable label, time and read state; null out server event code, source type/ID, actor/target IDs and source-specific label. Let the later web route call the existing source API for final access.
- Hook only `create_friend_request`, its actual accept transition, `create_dm_request`, the actual DM accept transition (explicit or atomic reply), and subsequent `send_dm_message` into same-transaction event creation. The first four event types use `social_requests`; only a later accepted-thread message uses `messages`. The atomic first reply generates one acceptance item, not a second message item. Exact retry and no-op actions generate none. Notification gate off means no new row and no replay. Source feature gates remain required by their existing operations. Keep recipient selection authoritative and avoid changes to source eligibility, suppression, block effects or payloads.
- Use a per-recipient advisory transaction lock for both preference writes and event creation, available when no preference row exists. In source hooks, acquire the notification gate row `FOR SHARE` after existing source retry/pair/eligibility locks, then the recipient advisory lock, then recheck the gate and preference in a fresh READ COMMITTED statement before inserting. Preference writes also acquire the gate row `FOR SHARE` *before* the recipient advisory lock, then recheck the gate and active-owner state under that lock. Mark-read writes take the gate row lock before any recipient advisory lock if one is needed. A gate disable committed first yields no row or preference write; a source that secured the shared gate lock first may commit its row before disable. Sort recipient IDs when fan-out is added later. A committed mute first suppresses the later optional item; an event that locks first may commit before the mute. Make this ordering explicit and test both orders. Preserve source idempotency and committed-event uniqueness.
- Add focused pgTAP/SQL actual-role tests and real local Auth/PostgREST tests for gate default/disabled behavior, owner isolation, direct table and forged RPC denial, bounded cursor order, mark-read, preferences, all five social event cases, first-reply one-event behavior, source teardown/visibility revocation, unfriend/re-request generation isolation, exact retries and no-op, and mute/gate/event races with observed lock waits. Keep fixtures synthetic, reset gates false, remove fixtures and stop disposable services. Update relevant engineering docs and write a task handoff with results and limitations.

## Explicit exclusions
Hangout edits/cancellation/join/leave, Hangout-chat source hooks (TASK-015B); Notifications web UI (TASK-015C); push/email/Realtime, background reminders, safety/moderation/attendance/co-host events, hosted use; global block/reporting, source permission redesign, friend-aware ranking, analytics, badge counts, message excerpts, peer media, arbitrary links, production retention, unrelated CI fixes.

## Acceptance checks
- [ ] Additive migration applies on two clean local resets; database lint, workspace checks, actual-role SQL and real Auth/PostgREST checks pass within documented limits.
- [ ] No client can read/write raw records, forge a recipient/source, inspect another inbox or infer a hidden social source. Reader revocation after commit is verified, including an in-flight read boundary where feasible.
- [ ] Current eligible source mutations create exactly their specified optional items; retries, no-ops, mute, gate disable and concurrent preference changes follow ADR-0017. No extra source action fails solely because the optional notification gate is disabled.
- [ ] Default-off gates restored, fixtures/services cleared; no hosted target touched. Independent exact-tip security review, coordinator handoff review, canonical main integration and remote verification precede TASK-015B dispatch.
