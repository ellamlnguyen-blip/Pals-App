## Goal and ownership

Replace the `apps/admin` placeholder with a local operator workflow for the already accepted audited report, case, account-action and Hangout-disable RPCs. An authorized moderator or admin can sign in, page through reviewable reports, open exact report detail, start/annotate/close/reopen a case, and apply only the supported action for the stored target. This stage adds no database authority. The implementation agent owns `apps/admin`, its focused UI tests, any necessary package dependency entries, relevant admin/UX documentation and `agents/handoffs/TASK-017C.md`. The coordinator owns shared NOW/BACKLOG/CURRENT_STATE/CHANGELOG, final review and integration.

Read `AGENTS.md`, TASK-017 parent, completed A/B1/B2 contracts, handoffs and reviews, Accepted ADR-0006/0018/0019/0020/0021, MVP, authorization/security/safety, UX direction and shared design tokens. Use B2's exact integrated RPC signature and allowlist after its security review; a material backend/UI contract conflict returns to the coordinator before changing authority. No C implementation starts from unreviewed B2.

The current B2 task tip defines `apply_hangout_moderation_action(p_report_id uuid, p_request_id uuid, p_expected_case_revision bigint, p_reason text)` and returns only `(case_state, revision, target_disabled)`; `get_moderation_report` adds nullable `target_disabled` after `target_campus_id`. Verify these exact shapes again at the integrated B2 tip before C dispatch. The Hangout action has no client-supplied action enum because its sole action is disable.

## Design and interaction plan

Reading this as: a private, serious campus-safety workspace for a small trained operator team, using the existing Pals blue/white palette with restrained motion, clear hierarchy and compact evidence layouts. The live `usepals.com` reference inspected on 2026-09-24 has a bright white canvas, soft campus blue, rounded surfaces and friendly Nunito style. The operator screen should retain brand recognition while putting allegations, state, timestamps, decisions and access denial ahead of decorative treatment. Shared tokens remain in `packages/design-tokens`; admin-specific density and semantic danger/warning treatments live in the admin app unless broadly useful.

At desktop width, present a bounded queue and a focused detail/work area without a general user browser. On tablet and phone, show queue then focused detail in a single column with an explicit Back to reports control. Preserve focus across selection, page changes and action completion; do not trap keyboard users in a detail pane. The first view must handle missing local configuration, unauthenticated, loading, empty queue and unavailable service honestly without revealing report existence. A signed-in nonoperator, revoked operator and disabled private moderation gate all receive the same neutral “moderation unavailable” state from the RPC; the UI cannot identify which condition caused it. Use one main landmark, skip link, semantic headings/labels, visible focus, status announcements and confirmation dialogs accessible by keyboard and screen reader. Test light and dark token rules, desktop/tablet/phone and a 320px stress width.

## Authentication and data boundary

- Use the project's existing Supabase SSR/cookie approach with the publishable client key, adapted to the admin app's own fixed local origin on port 3001. Sign-in/sign-out, callback and cookie refresh belong to the admin origin; sessions and mutation requests stay server-bound. The UI may use the current session to render state, but live `public.accounts` and `public.platform_roles` plus the default-off moderation gate are enforced by the database RPCs for every report read/write. No service-role key, privileged web proxy, client table grant, raw SQL endpoint or trust in JWT role claims.
- Invoke only the caller-bound, audited `list_moderation_reports`, `get_moderation_report`, `transition_moderation_case`, `apply_account_moderation_action`, and final B2 Hangout-disable RPC. Match field allowlists and actions exactly. Do not fetch user profiles, photos, full Hangout rows, private places, chat/DM messages, attachments or source tables to enrich detail. Show allegation text explicitly as an unverified report and current target status separately from the allegation.
- Render sensitive responses with `Cache-Control: private, no-store` and `Referrer-Policy: no-referrer`; use neutral server-action/route errors and server-side authenticated RPC calls with the publishable key. Do not place allegation text, target UUIDs or report UUIDs in query strings, browser storage, analytics, console/error logs or shared caches. Treat request bodies, React/RSC payloads and redirects as sensitive transport surfaces; restrict them to exact fields required by the audited RPCs and never log them. Use in-memory selection and server-bound form/request data; do not preload or prefetch report details. Only a deliberate detail opening calls the audited detail RPC. No analytics on the operator surface.
- Treat an RPC denial as authoritative even if the shell earlier displayed a role. Clear stale detail/action state on denial, sign-out, account/role/gate revocation or changed report selection. Abort or discard late detail responses using a selection/session generation guard: an A response must never render beneath B's heading after rapid A→B selection. Bind each confirmation and pending mutation to its captured report ID, revision, action and payload so a later selection cannot retarget it. Neutral error copy must not distinguish unknown, conflicted, stale or inaccessible target IDs. Do not echo backend errors or identifiers. A queue item cannot be treated as permission to open or act later.

## Review and action flow

- Queue is the server's bounded newest-first page (maximum 24), with only report ID/time, target type/ID, reporter ID, category and case state. Support server cursor paging with a deliberate Next/Back control and no speculative read. Every successful page read is audited by the database. Do not offer arbitrary lookup, search or bulk action.
- Detail opens via exact selected report ID. Show only the server's detail fields: report metadata, plain-text allegation, provenance kind/reference, case state/revision/note/disposition, and current target lifecycle/status/campus plus nullable Hangout disabled state. Keep unavailable-target behavior explicit. Do not infer or fetch identity/location context that the RPC omitted. Treat provenance as evidence reference, not a link to a broader reader.
- Case transitions use a fresh cryptographic request UUID and the displayed server-owned case revision. Expose only Stage A actions valid for the current case state: start review, annotate, close no action, close duplicate with an explicit existing reviewable report ID, and reopen. The duplicate flow accepts a manually entered candidate ID read from an already viewed queue page; explain that the candidate must be a distinct earlier report for the exact same stored target, ordered by `(submitted_at,id)`. Show the currently selected report ID and timestamp beside that input and allow a reviewable older candidate shown in the currently loaded queue to be selected directly. Do not add search/lookup or prefetch hidden reports. A duplicate confirmation states that it closes this case as linked to another report; the database validates earlier ordering, target equality and current reviewability. A neutral denial returns to detail without exposing an inaccessible candidate. Never present `action_taken` as a manually selectable disposition.
- Account actions appear only for user-target reports in `in_review` based on the projected target status and operator's own current role: moderator/admin suspension, admin ban and admin reinstatement. The detail projection does not reveal whether a target holds a platform role, so a visible control may receive the database's neutral denial; it must not trigger a role lookup or expand the detail allowlist. Hangout disable appears only for a Hangout-target report in `in_review` with an available, not yet disabled target. UI hiding is advisory; the database still checks role, conflict, case revision and exact target. Do not offer a Hangout-to-host account sanction or a re-enable action. An already disabled target is not actioned again from a different report.
- All actions require a visible action-specific confirmation. Case-only start/annotate/close/reopen confirmations state that they record a review decision and apply no sanction. Suspend/ban/reinstate/disable confirmations describe the actual student-access effect. Collect and validate a trimmed required reason up to 2000 code points for enforcement, and bounded note for relevant case transitions. Confirm against the exact report and case revision displayed, pass the server-owned report ID, request UUID and revision, disable submission while pending, and show outcome only after server success. For timeout/unknown outcome, keep the exact action, payload, revision and request UUID in memory through modal close, selection changes and in-session refresh attempts for an explicit same-key Retry; generating a new UUID after uncertain submission is prohibited. A full reload or tab loss destroys that memory and cannot reveal whether an unresolved action existed. The next session makes no success/failure claim, requires a deliberate fresh audited detail before any action, and may show a generic reminder that unconfirmed earlier actions could have completed. Never blindly reissue a lost action. On success, deliberately reload audited queue/detail and display the authoritative state. On stale revision, refresh detail and ask the operator to reconsider rather than silently resubmit.
- The console does not send notices to reporters or targets, expose audit history as a new reader, or claim that local moderation is staffed or hosted.
