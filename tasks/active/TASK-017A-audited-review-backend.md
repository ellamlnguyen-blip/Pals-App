## Allowed implementation

- Commit a migration after the TASK-016 reporting migration. Add `private.moderation_feature_gate` (singleton, default false), one private case per report, a private operator-scoped mutation retry ledger, and an append-only private audit relation. Enable RLS and remove anon/authenticated table grants. Give no platform role a raw table, Storage or general source reader.
- Change the existing `private.safety_reports.reporter_id` foreign key from cascade to restrict, add a restrictive case-to-report reference, and ensure audit actor/subject UUIDs do not cascade away with account or report deletion. No routine deletion API. Test that deleting a reporter with a report cannot silently erase the allegation/audit.
- Expose only narrowly typed `public` RPCs to authenticated callers: `list_moderation_reports` (descending `(submitted_at, id)` keyset, maximum 24), `get_moderation_report` (one exact report ID), and `transition_moderation_case` (one exact report, operator-scoped request UUID, expected case revision, action/note and optional duplicate reference). The strict `(submitted_at, id)` order also defines an earlier duplicate candidate, including tied timestamps. No arbitrary target ID lookup, search, raw SQL proxy or student-facing case reader.
- The live actor is `auth.uid()` with active account and explicit `moderator`/`admin` platform role in the database. The separate moderation gate must be on. Never trust client role/campus/reporter claims. Queue excludes and exact-ID RPCs deny reports filed by that operator, targeting them, or targeting their hosted Hangout. A target holding any platform role is unavailable for case action in this console. Recheck host/role changes after contention. The role and gate checks are required even if the caller has a valid signed-in student session.
- Queue returns exactly ADR-0019's field allowlist: report ID/time, target type/ID, reporter ID, category and case state. Detail alone adds narrative, provenance kind/reference ID, note/disposition, and current target status/campus or Hangout lifecycle/campus; no name, email, bio, photo, public place/description, private instruction, message or location. Stage B may add the disabled state field later. An unconflicted operator can still open an existing report when its current target row is missing: return the allegation with `unavailable` target context and do not resolve another source. An unknown report ID receives neutral denial. Never return raw audit or retry rows.
- Every successful queue page and detail response writes a same-transaction immutable audit event. Queue audit records the returned IDs/count and a server-issued request UUID; detail audit records its report ID. No narrative is copied into audit. An empty queue page still gets an audit event. Audit records use server actor/time and cannot be edited or deleted through client roles or new RPCs.
- Case actions are `start_review`, `annotate`, `close_no_action`, `close_duplicate`, and `reopen`. A case without a row reads as `open`, revision zero. `start_review` permits only open → in_review; `annotate` permits only in_review → in_review; both close actions permit only in_review → closed; `reopen` permits only closed → in_review and clears the current disposition and duplicate link. Every accepted new action, including an identical-text annotation, increments revision once and appends one audit event. An invalid source state has no mutation/revision/audit. All transitions use an expected server revision and operator-scoped UUID replay key with normalized-payload fingerprint; exact replay returns the original minimal result without a second revision/audit, changed-payload reuse fails generically, and a stale new request cannot overwrite another operator's action. Require a bounded plain-text note (1–2000 trimmed Unicode code points) for annotate, close and reopen; `start_review` has no note. `close_duplicate` requires a distinct earlier report with the exact same target type/ID that this operator can currently review; unknown/inaccessible reference returns a neutral denial. Persist that referenced report ID in the private case and audit, but do not add it to the detail response beyond ADR-0019's field allowlist. `action_taken` is unavailable in Stage A. Stage B will add an atomic sanction-and-closure path linked to the exact report target; this stage must not fake a sanction.
- Case transition and its audit append commit atomically. Audit previous/new case state and revision, operator, report ID, reason note and request ID without copying the allegation narrative. The audit relation and retry ledger are private and RLS-protected. No notification, automatic action or target/reporter case-status exposure.
- An exact transition replay must first pass the current moderation gate, active operator account/role and current report conflict checks. Only then may it return the stored minimal result without reapplying the now-stale expected revision or appending another transition audit. A revoked operator, gate-off caller or newly conflicted actor receives neutral denial even when holding a valid earlier request UUID.

## Lock and denial boundary

Require READ COMMITTED for new RPCs; fail closed at stronger isolation. Document a deadlock-safe order for gate, operator account/role, report, target conflict evidence and case/retry locks. Lock mutable authorization evidence through each response or transition, then freshly recheck after any wait. A committed gate disable, role revocation, account restriction, host change or target-role change before final authorization denies the new operation; an operation that held the evidence locks first may commit before the revocation. Keep existing safety submission locks/API behavior unchanged. Unknown, conflicted, gate-off, unauthorized and stale-sensitive exact-ID requests return neutral errors without target-existence clues. Audit and response must describe the same authorized page/detail snapshot.

For a user-target case transition, a mere negative lookup in `public.platform_roles` is insufficient: hold a conflicting lock on the target `public.accounts` key row through the final role check and commit, such as `FOR UPDATE`, so a concurrent platform-role insertion's foreign-key key-share lock cannot pass unnoticed. Acquire account/key locks in a consistent UUID order with the operator account and document compatibility with the existing safety/report lock order. Test both observed commit orders for target-role insertion versus case action. Do not depend on an absent role row as a lock.
