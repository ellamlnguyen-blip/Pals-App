## Exact lock and revocation order

Current `public.join_hangout` takes the shared social advisory lock, then `private.lock_hangout`: parent Hangout `FOR UPDATE`, Hangout gate `FOR SHARE`, campus/identity/safety evidence and moderation disable checks, plus the parent's physical update. It then checks published/open, blocks against joined peers and participant state, inserts/updates the joined row, records overlap and emits optional notifications after source locks. Preserve this order and the source gate/evidence rechecks after any wait.

On **only** `did_join`, after the participant row and safety overlap record but **before** notification emission, take the safeguard gate singleton `FOR SHARE`, check its current enabled state in a fresh READ COMMITTED statement, count joined rows under the already-held parent lock, and insert the unique signal if at least 25. The gate row comes after source/participant locks and before notification gate/recipient locks. Disabling the safeguard gate takes its row lock; if disable commits before the source checks that row, no signal is written. A join whose signal gate lock wins may finish before disable. Gate-off never vetoes a valid join or notification; notification failure semantics remain as already accepted. Keep old RPC signature and exact join idempotence.

Avoid a trigger that fires outside this serialized, caller-bound new-join path. Do not add a separate source lock order, client DML permission or gate read through `authenticated`. If a new constraint conflicts with existing tests or migration upgrades, fix it in A's additive migration/tests, not by editing history or weakening RLS.
