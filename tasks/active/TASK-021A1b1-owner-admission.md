## Goal and exact database state ABI

Make live caller status and owner onboarding/primary Storage eligibility admission-aware without requiring complete readiness to create it. No arbitrary-subject public status API. `get_access_state()` retains text return/signature and authenticated-only EXECUTE; the exact ordered result contract is:

| Priority | Current authoritative condition | Result |
| --- | --- | --- |
| 1 | auth.uid null or provisioned account absent | `signed_out` |
| 2 | Account exists but suspended/banned/nonactive | `restricted` |
| 3 | Availability missing/off OR admission row absent/revoked | `pilot_unavailable` |
| 4 | Active admitted caller, availability on, existing live exact UNC verification invalid | `unverified` |
| 5 | Otherwise incomplete required profile or missing/nonowned primary object | `onboarding` |
| 6 | All existing required readiness checks pass | `ready` |

Absence/revocation/shutdown share `pilot_unavailable`; never return roster state/revision/reason or another UUID. Strings `unverified`/`onboarding` now mean admitted callers because priority3 ran first; preserve these stable existing strings rather than invent synonym states. Invalid Auth/campus/email evidence includes mismatch, inactive/wrong campus, unconfirmed/missing membership and exact-domain failure. Keep `private.has_verified_membership()` unchanged in UNC meaning; do not turn verification into admission. Capability flags are separate purpose authorizers: this status describes account/admission/readiness, and is not authority to use a capability merely because it returns ready/onboarding. A2 must explicitly consume this ABI later. Current `apps/web/lib/access.ts` throws outside its five old strings; access/Hangouts/Calendar/saved-Hangout consumers therefore cannot count as integrated pilot evidence after `pilot_unavailable` is introduced. Do not patch these apps in B1 or count a successful old build as pilot integration.

Create one caller-bound admitted-onboarding eligibility predicate with fixed empty search path. If RLS invokes it directly, give only the minimum authenticated EXECUTE/schema usage required for that caller-bound boolean; otherwise keep it internal-only. Revoke PUBLIC/anon/service_role execution and retain internal arbitrary-subject helper client revokes. Inventory the resulting grant explicitly; no admission row/state/revision or arbitrary UUID input is exposed. It requires current availability, active admission/account, unchanged verified UNC evidence and `pilot_capability_enabled('onboarding')`, but no completed profile/photo. Owner draft read/write and required primary Storage SELECT/INSERT/DELETE use it. No manager/operator bypass. Retain existing ownership, private `profile-photos` bucket, UUID path/MIME/size/no UPDATE/no overwrite, row revision, owned-object/primary/extra-reference validation and deletion protection. Primary initial upload/assignment, replacement fresh object then revision-protected assignment, and obsolete unreferenced object cleanup must work before ready. A1c separately narrows optional fields/additional reference writes; do not delete retained fields/objects or claim gallery-purpose SQL denial here.

Independently replace `private.ready_subject_campus(uuid,uuid)` to require current availability/subject admission plus the full existing active-account/Auth/UNC/campus/profile/owned-primary evidence; internal EXECUTE revokes remain. Do not derive arbitrary subject readiness from caller auth.uid or get_access_state. Existing `private.ready_campus()` uses caller state and retains its existing Hangout gate; B2 adds exact Hangout capability/source checks. Audit its consumers so indirect gating changes are recorded, not claimed as complete source enforcement.
