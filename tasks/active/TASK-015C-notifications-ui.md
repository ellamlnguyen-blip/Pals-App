# TASK-015C — Local Notifications inbox and preferences UI

Status: Contract under independent security/design review; no implementation dispatched
Date: 2026-09-23
Parent: `TASK-015-notification-inbox-preferences.md`
Policy: Accepted ADR-0017
Required baseline: latest verified `origin/main` after reviewed TASK-015A/B integrations and this contract publication

## Outcome
Give an active student a private Notifications tab with one bounded inbox page at a time, clear read state and owner category preferences. Use only the reviewed caller-bound A/B RPCs. Keep unavailable-source items neutral and never treat an inbox row as access to its destination.

## Required context and design read
Read `AGENTS.md`, parent TASK-015, ADR-0017, A/B contracts/handoffs/reviews, MVP/PRINCIPLES, NOTIFICATIONS, AUTHORIZATION/SECURITY_AND_SAFETY/REALTIME_AND_MESSAGING, UX information architecture/screen inventory/design direction, and the installed `design-taste-frontend` skill. Inspect current app navigation, tokens, Chats/People auth-transition patterns, and `https://usepals.com/` before implementation. The coordinating session inspected the live reference on 2026-09-23: bright white, campus blue, rounded and friendly, with a notification icon in the header. The accepted navigation and Hangout wording override that site's current labels. Use existing Nunito and shared tokens; plan a quiet student utility (design variance 4, motion 2, density 4), not a dashboard or social feed. The accompanying UX plan is `docs/ux/TASK-015C-NOTIFICATIONS-PLAN.md`.

## Allowed work
- Add a local-only `/notifications` page and no-store API/action surface for `list_notifications`, `get_notification_preferences`, `set_notification_preference` and `mark_notification_read`. Require `APP_ENV=local`, validated loopback Supabase, current signed-in active account and the database notification gate. Do not expose a hosted fallback or service-role key. An active account that has lost readiness may see generic unavailable items and manage preferences, as the backend permits; signed-out/restricted accounts receive neutral denial. Validate bounded cursor, UUID/category/boolean inputs and actor continuity server-side. All success/error/denied responses are `private, no-store`.
- Render a latest page of at most 24 in descending server order, with explicit older-page navigation and refresh of only the visible page. No unread count/badge, infinite history fetch, message preview or peer profile/photo lookup. Each item shows its returned generic label, server time and read/unread state. `Unavailable` items show no source-specific code, actor or link. The essential Hangout cancellation remains visible even if updates are muted; no essential toggle appears. Show category toggles for social requests, messages, Hangout updates and host activity with plain language that they affect **future inbox items**, not the underlying requests/messages/actions; existing items remain. Show a small noninteractive note that cancellations still arrive.
- Derive destination URLs from an explicit allowlist of returned event codes and validated IDs only: friendship events → `/people/friends` as an intentionally generic friendship-list landing (the relevant peer may be on a later 24-item page); DM events → `/chats/direct/{peer-id}` using the currently returned actor ID only; Hangout-chat → `/chats/hangouts/{hangout-id}`; edit/cancellation/host activity → `/hangouts/saved/{hangout-id}`. Label the friendship action “View friendships,” not “Open this request.” Never render or follow a stored arbitrary URL. Reauthorize through the existing destination page/RPC when opened; if that source denies after the inbox read, show its normal unavailable state. Mark-read is idempotent and owner-only; do not add unread reversal. An uncertain mark/preference write must ask the user to reload rather than claiming success.
- Add Notifications as the fifth primary navigation link by replacing current placeholders in the existing primary-navigation surfaces only: Hangouts shell, Calendar, People, Chats, direct thread and Hangout-chat thread. Do not add a new navigation shell to secondary pages that lack one. Show it as a link only in the validated local app where the route exists. Preserve current layout and shared design tokens; do not change product navigation labels, backend source behavior or cross-feature permission policy. Keep keyboard focus and link names clear, dark-mode contrast, phone widths, touch targets, and loading/empty/error/denied states.
- Treat inbox content as sensitive even without message bodies: clear it on signout, account switch, visibility loss and every auth-transition begin; resume only after a current-account authorization probe settles. Handle overlapping transition tokens and stale/in-flight responses without briefly unmasking another account's items or leaving the inbox masked indefinitely. Recheck on focus/visibility and after actions. Clear or keep rows masked at refresh start and on **any** denied, failed or uncertain refresh; display them again only after a successful current-owner probe and page read. Test back/forward navigation and page cursors under a changed account. Reuse the proven TASK-014B verifier pattern where practical, without coupling notification state to DM content.
- Add focused unit/interaction checks for event-code→destination mapping, neutral unavailable rendering, preference semantics and overlapping auth-transition privacy/liveness. Run `pnpm check`, no-store anonymous/denied HTTP checks, real signed-in Auth/HTTP and rendered desktop/tablet/phone plus keyboard checks under disposable local gates. Verify loading, empty, one-page/older-page, preference save failure, mark-read uncertainty, source revocation and signout/account switch. Clean fixtures, restore gates false and stop local web/Supabase/VM. Write a bounded handoff with exact evidence and limits.

## Explicit exclusions
Schema/migration/RLS/RPC or source-hook changes; push/email/Realtime, background reminders, badge counts, unread reversal, friend-activity or marketing notices, message excerpts, arbitrary profile/photo projections, global block/reporting or co-host policy, hosted deployment and production retention; unrelated app-wide redesign or CI repair.

## Acceptance checks
- [ ] Current active owner alone can load their bounded inbox/preferences and mark owned items read; local/loopback and no-store boundaries hold for success and denial. Hosted routes remain unavailable.
- [ ] All A/B event types have clear generic labels and only currently authorized allowlisted destinations; neutral unavailable rows never link or identify hidden sources. Preferences control future optional items only, while cancellation remains essential.
- [ ] Sensitive rows clear on denial, signout/account change and overlapping transitions; stale responses cannot repopulate them, and settled transitions eventually reauthorize. Keyboard, desktop/tablet/phone, empty/loading/error states pass rendered review.
- [ ] No backend/hosted/Realtime scope change; gates false, fixtures/services cleared. Fresh independent security/design exact-tip review, handoff review, canonical main integration and verified task/main remote SHAs complete TASK-015.
