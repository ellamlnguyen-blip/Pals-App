## Allowed scope
- Add a single first-message request entry on a **freshly visible** People detail. The database still validates recipient eligibility; an old URL, friend or attendee ID alone never grants request authority. Show consent copy before send: one first message goes to Requests, with no ongoing chat until the recipient accepts or replies. Avoid a contact suggestion or hidden-person probe. Never expose peer profile/photo data outside a fresh ADR-0013 projection.
- Extend `/chats` with a distinct Requests area and Direct chats area alongside the existing Hangout chats. Use `list_dm_inbox` pages of at most 24 and the participant-only `get_dm_status` result; an incoming pending request may show its first body and server time only while currently authorized. The outgoing pending row shows waiting status, never a first-message preview. An unavailable peer uses a neutral label plus a full participant-owned ID for exact management; fetch a display name only through a separate fresh People detail call, never from a stored DM snapshot. No counts, unread badges, avatars, notifications, friend context, message preview for accepted threads or Realtime claims. Keep the existing Hangout-chat list functional and independently gated.
- Add a direct route (for example `/chats/direct/[id]`) with server-derived caller session, `APP_ENV=local` and validated loopback target guards, no-store pages/actions and fresh TASK-014A status/read authorization. Pending recipient can read the one first message only while body-authorized, then explicitly accept, atomically reply-and-accept, or ignore. A pending initiator sees a **waiting** state from `get_dm_status`: no first-message body/history or composer, because `read_dm_messages` intentionally returns no rows for them; they may withdraw but cannot send again. Do not mistake that empty read for paused or denied access. After acceptance, either participant can page/send bounded plain text; either can close. A current active participant may block the peer by exact ID through the existing `set_people_block` RPC while the People gate is on, including when the peer is now hidden if the database proves current DM participation. Confirm the block's **local** People/friendship/DM effects and explicitly say existing Hangout access/chat is unchanged; do not call it global separation. Update the existing People-detail block confirmation and its success/uncertain action copy to state the same DM termination effect after TASK-014A, including when a block is initiated outside the direct thread. A suspended/banned caller has no controls.
- Body access may pause when either person loses readiness, campus alignment or People opt-in; keep only the minimal participant-owned pair ID/state and ignore/withdraw/close management if still active and caller is an active account. Hide all bodies and composer when current authorization fails, including the caller's historical messages. State that opt-out pauses an accepted thread and later eligibility can resume it; ignore/withdraw/close/block ends the generation and terminal rows have no client route/list/body. A People gate or DM gate denial hides all DM content; do not infer a block or other hidden reason. After a known terminal transition, clear the route's content and return to the inbox or a neutral unavailable state. No client-side copy of terminal history.
- Use `create_dm_request`, `transition_dm`, `send_dm_message`, `get_dm_status`, `list_dm_inbox` and `read_dm_messages` only, plus the existing fresh People projection/block operation. One stable UUID key per first message, reply-and-accept and accepted-thread message; retain exact key/body through an uncertain result, show a deliberate same-payload retry only after fresh authority check, never auto-send a second message or change payload under an old key. State transitions use the current generation ID; a stale conflict requires reload, not an automatic second transition. No client-supplied actor, campus, author or message ID authority.
- Render bodies as escaped literal text with preserved line breaks, server time and `You`/`Peer` only. Never interpret HTML/Markdown or fetch peer photos/email. Use bounded forward keyset pages of at most 50 with explicit Previous/Load newer navigation; visible polling rechecks **only the current page** and must never auto-traverse older/newer history. Recheck current status/body on focus, return and after actions. Mask/clear private text on tab hide/pagehide/bfcache, auth transition, signout or account switch; a completion URL alone must never unmask content. Guarded server reauthorization must resolve the original account before reveal, and stale in-flight responses are discarded. Stop polling while hidden, on denial and navigation. No shared browser storage/cache for DM text.
- Reuse Pals tokens and current People/Chats patterns; preserve the Hangout chat entry. Provide clear loading, empty, pending, accepted, paused, denied, stale-generation, uncertain-send and generic transport states with accessible focus/live-region behavior. Verify desktop/tablet/390px/320px, multiline input, keyboard navigation, visible focus, reduced motion and no horizontal overflow. Design the distinction between Requests and Direct chats without popularity mechanics.

## Hard boundaries
- No migration, table grants/RLS or backend RPC changes in B. If TASK-014A cannot support a required state safely, surface a separate backend correction for review rather than expanding UI authority.
- No Realtime, push/notification, attachment, edit/delete, typing/presence, read receipt, unread count, peer photo, friendship bypass, invitation, global block/reporting, moderator read or hosted enablement. TASK-015/016/017 remain separate. The accepted People block changes DM only as described in ADR-0016; existing Hangout authorization remains unchanged.
- Every content-bearing page/API/action response, including denial/error, is no-store. Database RPCs remain the authority. Never persist request/thread bodies in URL, localStorage, analytics, logs, server cross-user cache or a stale tab after known revocation. Already delivered or in-flight authorized text cannot be recalled; client invalidation discards stale results when it knows authorization changed.
