## Goal
Let an eligible student request friendship from a currently visible People profile, and let each participant privately inspect and resolve their own requests/friendships. Keep relationships as a coordination tool without public lists, counts, peer-photo release or Hangout access changes.

## Backend contract to consume
Use only the caller's public Supabase session and these reviewed RPCs: `create_friend_request(p_target_id,p_request_id)` returns a generation UUID; `get_friendship(p_peer_id)` and bounded `list_friendships(p_after_peer_id,p_limit)` return peer ID, generation ID, direction and pending/accepted state; `accept_friend_request`, `decline_friend_request`, `cancel_friend_request` and `unfriend` require peer and current generation IDs. `set_people_block` is the existing People RPC with ADR-0014's atomic friendship teardown/hidden-current-peer target exception. Peer text still comes only from `get_people_detail` under ADR-0013. Never query private friendship/profile/Storage tables or infer friendship from public Hangout participant IDs.

## Allowed UI and actions
- Add a request control to the existing ready-only People detail for a currently authorized peer. Check current relationship state before showing an action; if backend gate or eligibility changes, show an unavailable/reload state. Do not show a request button on browse cards, hidden detail or an owner profile. Avoid fake DM, invitation, notification or friend-ranking controls.
- Add a private owner relationship management view reachable from People/account navigation without changing the primary nav. Active signed-in owners may access it even when not ready, so they can inspect ID/status and cancel, decline or unfriend; suspended/banned callers remain denied. Page the list by peer ID (max 24). Separate incoming, outgoing and accepted states through labels without publishing counts. Show only currently authorized ADR-0013 People text after a fresh per-peer read; otherwise use a neutral unavailable label and full stable peer ID for exact-action confirmation. Do not cache peer text, snapshot names or expose excluded fields. Clear displayed text on detected denial/block/navigation; prevent late per-peer responses from restoring it and reauthorize on return rather than using a prefetched/cached detail. Previously delivered text cannot be recalled before a remote revocation is detected.
- Use a caller-generated UUID per deliberate create intent and keep that key stable across an uncertain retry in the live UI. A new deliberate request after unfriend uses a new key. Existing transitions submit the immutable generation ID visible to the owner; stale errors require a fresh state read, never a blind replay or toggle. Confirm before decline/cancel that this same requester cannot send another request to that recipient in this local increment; confirm before unfriend that the current relationship ends and a later connection needs a new request. After an uncertain write, read current authoritative relationship state before claiming success; if that read fails, present unknown and disable repeat action until reload. An empty later state proves only that the pair is currently absent, not that this particular lost write succeeded; phrase the outcome accordingly.
- A ready owner may block a current relationship peer by ID even when peer text has become unavailable; a nonready owner may only cancel/decline/unfriend. Confirm that blocking ends any pending/accepted friendship and People visibility, while existing Hangout participation/private instructions are unchanged. Update the existing People detail block confirmation to say that a current request/friendship ends even if the friendship gate is off and status cannot be checked. Do not use `get_people_detail` absence as proof the block succeeded. `list_people_blocked_ids` is paginated: a matching ID proves an outbound block, but absence from the first page proves nothing. Page through the target ID under the bounded API or report an unknown outcome; then refresh relationship state when available. Clear displayed peer text immediately on block/denial/navigation away.
- Every page/action, including errors and POST responses, is no-store. Preserve APP_ENV=local and validated loopback-target guards, live access checks, safe return URLs and keyboard focus. Handle empty, loading, error, gate-off, stale response, invalid ID/page, opt-out and denied states honestly. No service-role path or client persistence of relationship/peer text. Shared tokens remain in `packages/design-tokens/` when needed.

## Out of scope
Database migrations, SQL grants or authorization changes; friend-aware ranking/attendance context; friends-only/invite-only Hangouts or private-location precedence; peer photos or extra profile fields; DM/chat, notifications/push, invitations, reports/moderation; global block UX; hosted deployment/migration/enablement; mock success states or unrelated test-helper repair. If reviewed RPCs cannot support an accepted action safely, report a bounded backend gap to the coordinator instead of inventing permissions in the UI.
