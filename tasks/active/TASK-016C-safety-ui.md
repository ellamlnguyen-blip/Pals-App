# TASK-016C — safety UI

Status: Reviewed and locally complete at remote-verified task `713e7c500f4c91b8ef6ba64b3bbf2c2b99664944`; canonical integration publication pending. Parent: TASK-016. Authority: Accepted ADR-0018. Final handoff and review: `agents/handoffs/TASK-016C.md`, `TASK-016C-REVIEW.md`.

## Outcome and dependency

Provide a usable local safety surface for active students to block a known user with an honest global consequence confirmation, manage their own outbound blocked IDs, and privately report a user or Hangout. Preserve reporting after removal and readiness loss through caller-owned retained Hangout IDs without exposing hidden details. Keep the safety route available to signed-in active owners when People opt-in, readiness, or source feature gates are off. This is disposable-local UI, not hosted moderation or launch readiness.

B has completed independent review and remote-verified canonical integration. Before implementation, the coordinator must finish independent review and publication of this narrowed C contract and the separate visual/interaction plan. A fresh task-specific GPT-6 Sol medium agent starts C from that main. The app's Standard speed setting applies; dispatch tools cannot configure or verify speed.

## Navigation and surfaces

- `/safety` is an owner utility reached from the signed-in header/account area, not a sixth primary tab. The current shared `Frame` header has only wordmark, campus and sign-out, while the profile path may be readiness-restricted, so add a signed-in header link available from active onboarding/verification as well as ready pages. An additional profile/avatar entry is useful but cannot be the only entry. Preserve Hangouts · Calendar · People · Chats · Notifications and Hangout terminology. The stable direct route handles unready or opted-out active owners instead of redirecting to onboarding or People.
- The route has three plain sections: “Block someone”, “Your blocked account IDs”, and “Report a concern”. The first accepts only a full UUID with server-authorized relationship evidence; it is not a search box or lookup. A current People detail, friend row/known relationship, and direct chat can pass a known exact user ID into the same confirmation. Never prefetch a now-hidden target profile to make a safety control work.
- The blocked list calls A's owner-only `list_people_blocked_ids` in keyset pages of at most 24. Show exact outbound IDs only. No incoming list, names, photos, timestamps or target lookups. Unblock only the selected exact full ID with a deliberate confirmation; do not infer absence from a page that does not contain the ID. A's `list_my_retained_hangout_ids` yields at most 24 caller-owned Hangout ID/own-state pairs per page. Show them as neutral, selectable recovery references with no title, host ID, participants, time, location or private detail. Provide “Report this Hangout” and “Report its host” from a selected retained ID. The host action sends the retained Hangout ID to B's private `hangout_host` mode, never resolves or displays the host ID client-side. Do not add arbitrary Hangout-ID target entry to this recovery list.
- Current authorized Hangout detail and chat may offer a same-page shared “Report this Hangout” control, and the host action uses `hangout_host` only if the caller has retained participation, or `user` only when current People/retained-peer evidence authorizes that user. Seeing a host ID on a public Hangout is not sufficient user-report authority; otherwise offer only the Hangout report. A hidden or removed detail must render a neutral unavailable state with a route to `/safety` retained-ID recovery; do not fetch a hidden Hangout or host first. A current People detail, friend/DM surface and safe visible roster identity may offer shared report/block controls with IDs already authorized by that source. Pass contextual references as actor-bound same-page component props, not new safety query strings carrying target IDs. Neutral unavailable routes link to `/safety` without target data. Do not create a peer directory or a roster expansion solely for safety actions.

## Block interaction

- Route every new-block entry point, including legacy People detail, friend and DM affordances, through one global-consequence confirmation flow. Replace the entire old `PersonView` People-only dialog and disabled control, not merely its button label; inspect every old action path and stale hidden dialog. Keep legacy writers denied and send new controls through a small new actor-bound API that requires a versioned global-confirmation field, the current cookie actor marker and exact target ID, or adapt the old writer to reject every old payload missing those fields. This rejects stale pre-C submissions; it does not cryptographically prove a human saw the dialog. The UI must present the confirmation. Database/RPC authorization remains A's authority. No server-minted consent secret, session token or schema addition is required.
- Confirmation must describe **both** cases without guessing which applies: if the caller hosts any shared joined Hangout, that person is removed there; where the caller is a nonhost, the caller leaves. These effects can happen in several Hangouts at once, including retained cancelled ones. Friendship and direct chat end; both students stop appearing to one another in People and lose blocked private coordination. No attendance, friendship or DM is automatically restored on unblock. Say that blocking cannot prevent off-app contact or guarantee physical safety. Do not imply an exact list, count, identity, location or plan details of affected Hangouts; the backend provides no preview. Make “Block this account” distinct from Cancel and place focus in the dialog, with native keyboard dismissal and focus return.
- Submit the exact ID through A's `set_safety_block(id,true)` from the actor-bound web path. Treat a confirmed response plus a freshly verified outbound exact-ID match as confirmed; gate/denied errors stay neutral. Since list pages are bounded, verify the ID with a one-row keyset query after its UUID predecessor (or the first row for the minimum UUID), not a first-page absence; this uses A's existing list API and adds no raw state reader. Unknown outcome offers “Check blocked IDs” and a fresh deliberate confirmation before any same-intent resend. The desired-state RPC has no revision/request key: an already-dispatched earlier block can commit after a later contrary unblock. The UI cannot cancel that transaction or guarantee final state from arrival order. Disable parallel opposing actions in the same surface, broadcast same-actor safety mutation transitions so other tabs mask and recheck, and never auto-replay a prior intention. After uncertainty or an external mutation, check the exact ID, show the observed state and require deliberate confirmation for a new change. Tests assert truthful final state and no stale render/automatic resend, including both commit orders.
- Retire or hard-deny the legacy `unblockPerson(id)` server action, which has no cookie actor marker and only checks the first list page. Route every unblock control, including People/privacy, through the new actor-bound safety path. Unblock uses the exact outbound ID from owner list, says it does not restore any relationship/attendance and may allow future interaction under normal rules, then calls `set_safety_block(id,false)` and checks that exact ID. Unknown outcome asks for a fresh check and deliberate choice. It follows the same commit-order and cross-tab handling as block; do not promise that a pending old unblock cannot commit after a later reblock. No general incoming-block indicator or reason is shown.

## Report interaction

- Report target modes use reviewed B API: `submit_safety_report(p_request_id uuid,p_target_mode text,p_target_id uuid,p_category text,p_narrative text)` with `user`, `hangout`, `hangout_host`. The returned row contains only `receipt_id` and `submitted_at`. The UI receives only opaque receipt ID and server time. Do not look up the resolved host or read a report after submission.
- Forms show target type/reference only when already authorized by the current source; recovered forms show only the caller-owned Hangout ID or a previously held exact user ID. Use native radio/select controls for the five accepted categories: harassment, safety concern, impersonation, spam/commercial promotion, other. Plain-text narrative is optional except for other (1–2000 trimmed characters), and at most 2000 characters in all cases. Match B's JavaScript-style edge trim and PostgreSQL character count (Unicode code points, not UTF-16 code units); do not use a native textarea maxLength as the sole limit if it counts differently. Show a live character count and inline validation; render saved narrative as literal text if it is ever echoed locally, never as HTML or active links. Do not persist narrative to `localStorage`, sessionStorage, URL/query, analytics or logs. Clear narrative on confirmed submission, auth change, denial, navigation/unmount and owner switch. No report history or status page.
- Generate one caller-scoped UUID for a particular submitted payload. Freeze the mode, reference ID, category and normalized narrative for that in-flight attempt. A lost/unknown response preserves that exact UUID and payload **in memory only** while the same authenticated actor remains verified, and offers a user-invoked “Retry this same report” action. No automatic retry. Editing any field or choosing a deliberate new allegation creates a new UUID; the UI must explain that a new report may count toward the five-per-hour local limit. When outcome is unknown, avoid implying a report was or was not saved. A confirmed receipt states “Report saved locally” with server time/receipt if useful, and no staffed-review, case-status or emergency promise. Neutral denied/throttled messages do not reveal whether a hidden target exists.

## Fail-closed web boundary

- Use dynamic/no-store route and API responses for sensitive owner IDs, retained Hangout IDs, target references, report forms and receipt. Actor comes from live server auth and cookie; every sensitive API request must check its client actor marker against the currently authenticated cookie actor before returning data or acting. The marker detects stale cross-account requests and is never authority by itself. Server actions/APIs recheck current account, safety gate and source authority through caller-bound RPCs; do not use service-role web proxy. Validate UUIDs/modes/body size before calls without turning malformed/unknown target into a target-existence oracle.
- Apply the existing `auth-transition` BroadcastChannel/local event pattern, plus a same-actor safety-mutation signal, `pageshow`, focus and visibility handling, to safety state. A block/unblock start or completion in another tab masks affected local state and triggers a fresh exact-ID check; it does not cancel a database transaction. On sign-in/sign-out begin, tab hide, back/forward cache restore, actor mismatch or access uncertainty, synchronously mask IDs, selected target, form narrative, pending retry key and receipt; abort/ignore outstanding fetches with a generation ticket. Reauthorize before revealing data again, and ensure post-await state writes check the ticket, current actor and visible/verified state. On denied/403, gate-off or account restriction, clear private state and show a neutral unavailable message. No cached server component or browser history should restore a prior owner's sensitive UI. Dialogs close on masking and focus returns only if the original actor/surface remains authorized.
- Bound any foreground refresh/reconciliation. There is no reason to poll reports or historical targets. Refresh list/state explicitly after a mutation and on safe reentry; if any periodic check is used, it must be bounded, hidden-tab paused and actor-scoped. Unmount and abort cleanup are required.

## Final B adapter boundary

`submit_safety_report` returns one row with `receipt_id` and `submitted_at`. Category uses JavaScript-style edge trim plus lowercase; narrative uses matching edge trim, with null/empty normalized to null and PostgreSQL Unicode character length. After typed argument parsing, invalid/unknown/denied/throttled/mismatched requests use neutral `42501` “Safety report unavailable”. The UI must not claim a specific throttle reason or reset time from that code. Use one accurate neutral denial message. Fresh exact retries preserve original mode/reference and normalized payload. There is no readback endpoint or resolved-host response.
