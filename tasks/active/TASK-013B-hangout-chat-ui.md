## Goal
Give current joined students a simple, usable text thread for a saved Hangout and a Chats path back to their current Hangout threads in disposable local development. Consume only the reviewed TASK-013A read/send RPCs and existing public Hangout membership; add no new database permission.

## Allowed scope
- Add a Hangout chat entry from the saved Hangout detail only for a currently joined host/participant of a published record **and** after a fresh successful chat RPC authorization; show a neutral unavailable state when the chat gate denies. Add a `/chats` local Hangout-thread list. Gather at most 24 current joined published Hangout candidates per deterministic keyset page from existing RLS-authorized public membership, with a “Load more” path, then require each listed candidate to pass a fresh `read_hangout_messages` authorization, including the valid empty-page result. A public membership row alone does not establish that the chat gate is enabled. When chat authorization denies, show a neutral unavailable state without a clickable thread or hidden reason. No peer name/photo, private-location preview, message preview, unread count, presence, DM tab or claim that empty conversations have content. A direct thread URL must independently enforce current chat access; a hidden link is not authorization. If current navigation has a Chats placeholder, connect it without presenting unfinished DMs as live.
- Add a thread route (for example `/chats/hangouts/[id]`) with local APP_ENV/validated loopback Supabase guards, ready access, no-store and fresh TASK-013A `read_hangout_messages` authorization. Show plain text, server time and minimal `You` / current participant account ID / `Former participant` attribution from the RPC only. Never fetch raw profile/photo or trust user-supplied author identity. Render message bodies as escaped text, preserve line breaks, and never interpret HTML/Markdown/link previews. Explain near the composer that future eligible joiners can read full history and that People blocking does not mute this local Hangout chat.
- Use bounded forward keyset pages from the existing ascending RPC, with an explicit “Load newer messages” path when more history exists. An active visible thread polls through the same authenticated reader and after send; page size at most 50. Avoid overlapping polls, duplicate rows and stale responses after route/account/Hangout changes. On tab hide/pagehide/bfcache entry, mask or clear retained private text and invalidate in-flight request generations. On pageshow/visibility return/focus, reauthorize through a fresh chat read before revealing the thread or composer. Respond to cross-tab signout/auth changes by immediately masking text and invalidating requests; a visible tab continues periodic authorization checks. Stop polling while hidden, on navigation/signout or denial; clear rendered messages and composer on known revocation. An in-flight read may arrive after revocation, so discard responses whose local request generation is obsolete. Do not use Realtime or expose message payloads via a shared cache.
- Composer trims plain text to the accepted 1–2000 character database bound, offers clear count/validation, and sends one stable UUID request key per composed message. Preserve key and draft through an uncertain response; retry the same payload/key only after rechecking current access, and do not auto-send a second message. A successful send clears the draft only after the authoritative response. Denied access clears thread content, while generic transport failure keeps a safe retry state without claiming success. Distinguish current denial, stale membership, empty thread, initial load, page load, send pending, uncertain result and retry recovery.
- Keep styling cohesive with `packages/design-tokens/` and current saved-Hangout components. Use accessible controls, visible focus, keyboard send behavior that does not surprise multiline input, live-region status without reading every polled message aloud, responsive desktop/tablet/390px/320px layouts, and reduced-motion behavior. Write a short interaction/visual plan in `docs/ux/` before implementation.

## Hard boundaries
- No migration, table grant/RLS edit or backend RPC change in B. If backend pagination cannot support a needed UX affordance, surface it to the coordinator as a separately reviewed backend correction rather than silently expanding scope.
- No direct messages, request inbox, notifications, message edits/deletes, attachments, typing/presence, read receipts, unread counts, search, co-host moderation or peer profiles/photos. People blocks remain People-only under Accepted ADR-0015; no global or restricted Hangout rule is inferred. No hosted migration/deployment, live accounts or Realtime transport.
- The message route/action must derive caller session server-side and use the existing local target guard. Database RPC authorization remains authoritative. Every page/action/API response carrying message text or status is no-store; never persist thread text to localStorage or URL. Do not keep stale private text in UI after a known leave/removal/cancellation/readiness/gate denial.
