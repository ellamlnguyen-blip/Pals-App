## Outcome and boundary

Add one caller-bound `public.submit_safety_report(p_request_id uuid, p_target_mode text, p_target_id uuid, p_category text, p_narrative text)` RPC. Target modes are `user`, `hangout`, and `hangout_host`. `hangout_host` accepts the caller's retained Hangout ID, resolves the immutable `public.hangouts.host_id` on the server, and stores a **user** report. Return exactly one opaque server-generated receipt ID and server submission timestamp; neither target nor category/narrative/evidence/host lookup is returned. A new deliberate allegation requires a new request UUID. Self-user reporting fails with the same neutral unavailable result as an unauthorized target, including when reached through `hangout_host`.

This stage commits only a private report table, a private caller-scoped UUID/fingerprint retry ledger, the submission RPC and narrow internal helpers if needed, and necessary engineering/test/handoff updates. Both tables have RLS enabled and explicit `public`/`anon`/`authenticated` revokes. No client or platform-role reader, raw/embedded access, report history, status, edit/delete, moderator or service-role web proxy is added. Store reporter, resolved target type/ID, category, trimmed optional plain-text narrative, server receipt/time and minimal server-derived provenance kind/reference. Do not copy profile, message, photo, public/private place, exact location, or entire source records. Reports remain allegations; submission causes no block, notification or sanction.

## Input, retry and receipt rules

Validate UUID, mode, target ID, category and narrative bounds. Categories are `harassment`, `safety concern`, `impersonation`, `spam/commercial promotion`, `other`. Narrative is trimmed plain text, maximum 2,000 characters; `other` requires 1–2,000 characters and all other categories permit empty text. Specify and test one canonical normalization for category and narrative, including null versus empty; use the **original input mode and reference ID** plus normalized category/narrative for the fingerprint before any target lookup or host resolution. A `hangout_host` input and direct `user` input must conflict under the same request UUID even if they resolve to the same host. Never derive the fingerprint from a looked-up host or mutable source fields. Validate shape without a target-existence oracle; SQL errors and REST responses for malformed/unknown/denied/throttled input must be neutral about target existence. Do not echo a mismatched payload.

Acquire A's shared mutation lock first, require READ COMMITTED, derive the caller through `auth.uid()`, and look up only that caller's retry key without taking a lower lock. If the key exists, lock the safety gate and caller account through commit, freshly recheck enabled safety and active caller, then compare the original-input fingerprint. A match returns **only its original receipt/time**, even if the source was since revoked, removed, cancelled, hidden or deleted; do not resolve the target or reauthorize its source for that replay. A mismatch conflicts generically. A different caller has no access to that receipt and can use the same UUID independently. Safety-gate off or inactive caller denies even exact replay. For a new key, choose the historical or current-source lock path below **before** taking gate/account locks, then authorize, apply the rate limit and atomically insert report plus retry row. A lost response can be replayed without a second report.

## New-report authorization

Derive the reporter only from `auth.uid()`. Require an active account and enabled safety gate; suspended/banned callers and anonymous callers cannot submit. Client-supplied campus, reporter, role, visibility cache or host are never authority. Current source eligibility or retained caller-specific evidence suffices:

- `user`: a currently authorized People user (A's gated, live-ready `private.people_visible` path) **or** `private.safety_peer_evidence(reporter, target)`. The latter covers owned block, current/retained friendship or DM, immutable host of the reporter's own retained Hangout, and A's provable Hangout overlap; merely sharing campus or two nonoverlapping historical membership rows is insufficient. A retained path does not require current People opt-in/readiness/campus or a source gate.
- `hangout`: currently authorized Hangout through A's source read rules **or** a `public.hangout_participants` row for this caller and ID in any state. Historical ownership must work after leave, removal, cancellation, block, campus/readiness loss and source-gate disablement. It yields no title, roster, place, chat or private instructions.
- `hangout_host`: require that same caller-owned retained participation in the supplied Hangout, then privately resolve its immutable host. This route works after removal/cancellation/readiness loss and never returns the host ID. If the resolved host is the reporter, deny neutrally. Record a minimal server-derived Hangout reference as provenance; store the resolved user as the report target. This mode is not a general host-lookup API.

For a new key, a nonlocking private evidence check may select the retained path; it is only a routing hint, never final authorization. On that path, take the safety gate and caller account locks through commit, then freshly recheck active caller, enabled safety and authoritative peer evidence or own Hangout participation. Historical authority needs no People/Hangout gate, target identity or Hangout parent lock. For a `hangout_host` report, resolve the immutable host only from the caller-owned retained Hangout on this path. If the retained proof fails on recheck, deny generically rather than falling through to a current-source path after gate/account locks.

If retained evidence is absent, take the current-source path: acquire any A pair lock required for the user path or the Hangout parent lock **before** gate/identity locks; then lock the safety gate and source gate, live caller/target evidence as appropriate, and keep those locks through commit. For People, reuse A's `private.safety_lock_visible_evidence(uuid,uuid)` and freshly evaluate `private.people_enabled()`, `private.people_ready_campus()` and `private.people_visible(uuid,uuid)`. For Hangouts, lock the parent, separately lock the Hangout feature-gate row, and call `private.safety_lock_hangout_evidence(actor, locked_parent.university_id)` to lock live caller readiness evidence; the helper does not itself lock the parent or gate. Then freshly require `private.hangouts_enabled()` and evaluate `private.can_read_hangout(uuid,boolean)` without private-detail access. Check the source gate explicitly after locking it, then evaluate `can_read_hangout`; a lock without a fresh authorization check is insufficient. In either path, use a **fresh READ COMMITTED statement after every wait** to recheck active caller, safety gate and final target authority. `private.social_hangout_mutation_lock()` precedes every request/rate, pair, parent, gate and identity lock. Reuse A's lower-lock order; never take a parent after safety/account locks. In-flight source reads retain ADR-0018's documented boundary, while a new report cannot authorize from a source revoked before its final check.

## Atomic caller rate limit

At most five **new** reports per reporter in the rolling preceding one hour, across all modes, targets and categories. The same-key exact replay consumes no additional slot and must be checked before the new-report rate decision. Serialize a caller's submit transactions under A's shared transaction lock (and, only if necessary, a consistently ordered caller lock). Obtain a fresh database clock value **after contention**, count committed new reports in `[now − 1 hour, now]` using that database time, and insert report and retry row atomically. At four existing reports, two concurrent distinct requests must yield exactly one new receipt; at five, neither may insert. A report exactly outside the rolling window permits another. A denial/throttle is generic and does not indicate whether the target exists. Document the precise boundary convention used by SQL.
