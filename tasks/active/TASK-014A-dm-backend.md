## Allowed scope
- Add one additive migration after current migrations. Use one unique active unordered pair (`pending`/`accepted`) and privately retained terminal generations (`ignored`/`withdrawn`/`closed`/`blocked`), directional suppression and immutable message/retry records. Add a separate default-disabled private DM gate. RLS and explicit revokes cover every new table; no direct anon/authenticated table or Realtime payload access.
- Add narrow fixed-search-path caller-bound RPCs for first-message request, incoming accept or atomic reply-and-accept, ignore, sender withdrawal, accepted-thread send/close, participant inbox/status and bounded message pages. Derive actor from `auth.uid()`; validate target and current generation server-side. Use 1–2000 trimmed plain text, server IDs/time/order and caller-scoped UUID keys. Exact currently authorized retry cannot duplicate or revive a terminal generation; changed-payload reuse conflicts. A stale generation cannot transition a later pair. Denials are generic and no hidden-recipient or block-reason oracle is introduced.
- Creation requires current ADR-0013 People visibility between ready opted-in same-campus users with neither-direction block. Acceptance/send likewise require both users currently ready, same-campus, opted in and unblocked. Friendship/attendee knowledge grants no bypass. All active-pair status/inbox/body readers and active cleanup operations require the DM gate; cleanup may proceed while the People gate is off or the active caller has lost readiness/opt-in, without returning a body. Suspended/banned clients cannot act. Active participants alone can read minimal ID/generation/direction/state while the DM gate is on; bodies additionally require the People gate and current bilateral eligibility. An incoming pending inbox row may add server time and its single first-message body only while body-authorized. No outgoing pending preview or peer profile snapshot. Terminal records have no client reader. Read pages are keyset-bounded to 50 and inbox pages to 24, with fresh same-statement authorization and no cross-user count.
- Extend `set_people_block` narrowly: under the existing People gate and ready active-caller requirement, a current active DM participant can block their hidden peer by ID after proving current pair participation; a terminal pair alone never qualifies. A block in either direction atomically terminates the active DM generation even with the DM gate off. Preserve its ADR-0014 friendship teardown and existing People policy. Do not alter Hangout or Hangout-chat access. Unblock does not restore a generation.
- Serialize all same-pair create/transition/send/block operations on one deterministic unordered-pair lock, including the existing friendship/People block path. For create/accept/send, hold transaction locks that conflict with updates/deletes of both gates and all live readiness/opt-in evidence, then recheck in a fresh READ COMMITTED statement. Fail closed at stronger isolation. A revocation committed before recheck denies; one begun after mutation locks waits. Reads authorize in the same projection statement; an in-flight authorized read may complete after later revocation.
- Add actual-role SQL/pgTAP, real local Auth/PostgREST and deterministic overlapping-session tests. Update only backend/API/security/data/testing messaging docs. No web route/UI, notification, Realtime, hosted change or moderator access in A.

## Hard invariants and edge cases
- One active generation per unordered pair. Opposite-direction creates race to at most one; a terminal generation cannot be resurrected by stale action, old request UUID or gate re-enable. Directional ignore/withdraw/close suppression survives cleanup; a reverse-direction new generation requires present eligibility and a fresh request UUID. Retained terminal rows and message bodies have no client reader.
- Pending sender has only one first message and cannot send again until recipient acceptance. Reply and acceptance are atomic. A recipient can ignore without explaining why to sender. Accepted threads may pause on opt-out/readiness/campus change; neither side receives bodies while paused. A block terminates instead of merely pausing. A current participant may close/ignore/withdraw with body access revoked, but does not gain hidden peer text.
- Direct private-table REST/DML/embeds denied. No admin/platform bypass, peer profile/photo read, service-role web path or raw Realtime publication. Existing Hangout and Hangout-chat behavior stays unchanged. Already delivered or in-flight authorized bodies cannot be recalled.
