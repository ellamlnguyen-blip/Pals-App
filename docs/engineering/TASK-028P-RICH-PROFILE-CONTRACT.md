# TASK-028P rich peer profile security contract

Status: **accepted policy; bounded implementation pending**. ADR-0036 was explicitly accepted by the user on 2026-10-06. The corrected lock-order plan passed independent planning review; TASK-028P2 defines implementation lanes and requires independent service-boundary review before photo implementation. This contract covers the conditional peer lane of TASK-028P; existing owner/profile UI and current People text may proceed separately. No hosted operation or gate activation follows from this document.

## Fixed baseline and scope

Current `public.profiles` and private `profile-photos` Storage SELECT stay owner-only. `get_people_detail` returns the existing text allowlist only. `private.people_visible` currently requires a subject's People preference, current text publishability (name/year/major/bio), live same-campus eligibility and no bilateral block; the caller's People opt-in is not part of that legacy text predicate. `ready_subject_campus` now checks active account/campus and current confirmed exact-allowlist Auth email without requiring profile completion or a photo. A rich read must apply **both** parties' People preferences, the current text publishability predicate and every current source gate independently. Neither a friendship nor a platform role changes rich access.

Only the currently selected primary and up to four extra photos, up to three owner-authored prompt pairs and optional self-declared hometown may be added. No actual email, Storage path, favorites, weird fact, Instagram, location inference or extra identity claim may be projected. Existing owner editing, readiness and direct profile/Storage RLS do not change.

## Migration and owner writes

1. Reuse the already implemented owner-only hometown migration `20261006000100` under ADR-0037; do not add the column again. It provides nullable `public.profiles.hometown text`, checked as either null or `hometown = private.profile_trim(hometown)` and `length(hometown) between 1 and 100` PostgreSQL Unicode characters. Grant authenticated **owner update of this column only** under the existing owner RLS. Blank form input becomes null. Existing `revision` trigger and editor compare-and-swap apply; ensure the owner save selects and preserves hometown and all existing fields. Hometown is never populated from GPS, IP, email or campus. No peer table grant.
2. Add `private.rich_profile_feature_gate(singleton, enabled)` default false and `private.rich_profile_preferences(account_id primary key, opted_in boolean not null default false, revision bigint not null default 0)` with RLS on and no client table grants. No row means false/revision zero. Existing accounts are all rich-opted-out. Never backfill from People preference or existing photos/prompts. The only client entry points are fixed-search-path, caller-bound `get_my_rich_profile_preference()` and `set_my_rich_profile_preference(p_opted_in boolean, p_expected_revision bigint)` granted to `authenticated`; no arbitrary subject ID. Return consent state/revision only. Reject null, negative/stale revisions, stronger-than-READ-COMMITTED isolation and unknown caller with neutral denial. An authorized identical desired value is a no-op at the same revision; a change increments once. Compare-and-swap serializes absent-row creation via the actor account lock. This revision is separate from the profile-content revision.
3. Rich opt-in requires an active owner, current verified exact-UNC same active campus eligibility, existing People opt-in, current text publishability, pilot availability, `people` capability, enabled People gate and enabled rich gate. It does **not** require any photo, prompt or hometown. Rich opt-out requires only an active authenticated owner and must work with People/rich/capability gates off, lost Auth/campus eligibility and incomplete profile. It is not contingent on an up-to-date content revision. Suspended/banned owners cannot manage consent under the current active-owner rule; their rich reads are already denied. UI must provide a plain disclosure preview before opt-in, including future edits/replacements and the limits of revoking bytes already delivered.
4. Replace `set_people_preference` in the same migration so `p_opted_in=false` clears rich consent **atomically**, increments rich consent revision if it changed, and never auto-restores rich consent on People re-opt-in. Retain the current People-opt-out availability for active owners despite source/readiness loss. The existing implementation locks `accounts` first; **do not append** pilot/social locks after that row. Replace its whole lock acquisition path together with the new rich writer, using the order below. This migration is a reviewed change to the existing People writer, not a passive rich-table addition. No route may directly mutate the private tables.

### Consent mutation lock order and race contract

For **both** `set_people_preference` values and **both** `set_my_rich_profile_preference` values, use one consistent transaction order before acquiring any row lock: (1) reject non-READ-COMMITTED isolation and acquire `private.social_hangout_mutation_lock()` exclusive `(16016,1)`; (2) acquire `private.pilot_evidence_lock()` shared `(16027,1)` even for opt-out, regardless of policy state; (3) lock existing pilot availability singleton and `people` capability rows `FOR SHARE` in the same policy/key order used by pilot management (missing rows fail opt-in, but cannot prevent an active owner's opt-out); (4) lock People then rich feature-gate singleton rows `FOR SHARE` if present, without making their enabled state an opt-out requirement; (5) lock the actor `public.accounts` row `FOR UPDATE`; (6) for opt-in only, lock current `auth.users`, `university_memberships`, then campus `universities` rows `FOR SHARE`, deriving campus from the **locked current membership tuple**; (7) lock/write actor `people_preferences` then `rich_profile_preferences` rows in that order. The shared social/evidence keys stay held through commit. An absent preference row is serialized by the account lock; an absent policy/gate row is not treated as enabled. No consent path takes a profile or Storage row lock after account.

Why this order: `private.pilot_evidence_write_lock()` takes social then **exclusive** pilot evidence before policy and account rows. Account-first followed by either key can deadlock with management holding the key and waiting for that account. Existing social/People safety paths also begin with social, so the proposed writers join that order. The direct profile UPDATE trigger is row-first and later takes shared pilot evidence/account; the consent writer must not lock profile after account, which could invert against that direct row-first path. For opt-in, read text publishability after all required waits in a fresh statement without locking the profile; a concurrent profile edit may commit before the read (and deny opt-in) or after it (the later rich read still enforces text publishability). Do not claim a profile-row commit-order guarantee for this consent choice. Avoiding that new row edge keeps the existing direct-write graph intact; database deadlock/serialization aborts against external Auth/status writers remain possible and must be surfaced as retryable failure, never success.

Recheck active owner and each operation's predicates in fresh READ COMMITTED statements **after** locks/waits and immediately before write. People opt-in retains its current People-gate/live-ready requirement; this contract does not add text publishability to that existing choice. Rich opt-in additionally requires the current `people` capability, rich gate, People consent, text publishability and expected rich revision. Rich opt-out rechecks only active owner and expected rich revision; People opt-out keeps its current active-owner-only rule and clears rich consent even if eligibility/gates disappear. One social lock serializes concurrent People-off/rich-on calls: People-off first makes the later rich opt-in deny; rich-on first is cleared by later People-off. A pilot policy writer first makes rich opt-in observe closure; rich consent first may commit, then policy closure denies all new rich reads. The same commit-order rule applies to sanctions and Auth/campus changes through their actual row locks; if an external writer causes a safe transaction abort, the client reloads state before retry. Tests must observe waits and both committed orders, plus no account→social/evidence inversion in the replacement People RPC.

## Rich text/detail projection

Add a separate `public.get_rich_people_detail(p_account_id uuid)` SECURITY DEFINER RPC, fixed empty `search_path`, `authenticated` EXECUTE only, READ COMMITTED only. Do not extend the existing text RPC or raw-profile grants. A single authorization/projection statement (or one transaction with a documented statement snapshot) derives caller from `auth.uid()` and returns either no row or exactly: current text detail allowlist, `hometown`, bounded `prompts`, `photo_revision` (current `profiles.revision`), and ordered photo **presence/slot identifiers only** (`primary`, `0`–`3`). No path/object ID, email or image bearer token. No empty rich-only result for a subject that fails existing text publishability.

The predicate requires caller and subject distinct and active; both current confirmed Auth emails on the exact approved UNC allowlist; both current membership at the same active UNC campus; pilot availability, current `people` capability, People and rich gates; both People preferences opted in; subject rich preference opted in; subject text publishability; and no `private.people_blocks` in either direction. Match the live evidence currently enforced by `ready_subject_campus`, not stale JWT metadata. Evaluate fields and predicates in one set-based SQL snapshot; do not compose separate volatile helper queries whose snapshots could differ across an authorization/projection. Missing subject and denied subject both return no row. `UNC email verified` is a boolean derived from the current server authorization, not copied from profile text; it means confirmed allowlisted email only. Rich consent does not expand browse/search or the existing `get_people_detail` allowlist. Render blank optional sections honestly.

## Peer photo boundary

Use `GET /people/{subjectId}/photo?slot=primary|0|1|2|3&revision=<positive-current-profile-revision>` as an opaque URL. IDs, slot and revision are bounded syntax; there is no path or arbitrary Storage key parameter. No HEAD/POST, redirect, direct Storage URL, public bucket, signed URL, CDN transform or persistent derivative. The `photo_revision` came from the authorized detail response. A URL can be copied, but it remains cookie-authenticated and revocation-checked on each request.

The route calls `auth.getUser()` using the request's cookie-backed **user** Supabase client and derives `actor_id` solely from that verified Auth result; a request field/header/cookie never supplies a trusted actor ID. A separate server-only service credential, if needed for the final private Storage download, is read only in the server runtime. Never send it to a component, browser bundle, response, logger or analytics. Provisioning it is a separate local environment step; do not ask for or print it. The only service-role RPC is a narrow `public.resolve_rich_peer_photo_for_gateway(actor_id, subject_id, slot, expected_revision)` with EXECUTE revoked from PUBLIC/anon/authenticated and granted to service_role; check original SQL role as service_role, use fixed search path, READ COMMITTED and the exact rich predicate above. This is a **server-trust boundary**: it accepts `actor_id` only from the verified `auth.getUser()` result and exists solely behind this route. The service credential must have no general-purpose client wrapper exposed to app components. A fresh independent review must verify this binding before implementation.

The resolver returns the current exact private object path **only to the server**, with bucket, owner and current profile slot/revision checked in the same set-based statement snapshot as the full rich predicate. Require `profiles.revision = expected_revision`, slot still selected and object metadata still present with matching owner and subject path prefix. It never returns a different/newly selected object for a stale URL. The route downloads **only** that returned exact immutable object name; it must not re-resolve a stale slot after a miss and must not accept a path from the client. If removal/deletion wins before fetch, return a neutral miss. If the request was authorized before a concurrent consent/block/eligibility change, it may complete under the documented read-snapshot rule; the next request must deny. The image path never appears in JSON, response headers, errors, metrics or logs. This service-only resolver does not add any raw profile or Storage client grant.

The gateway limits downloaded input to 5 MiB and admits decoded JPEG/PNG/WebP by magic bytes, not MIME label or extension. Decode with a maintained image library using a hard input-pixel limit (at most 20 million), reject corrupt, oversized, SVG/polyglot and unsupported/multi-frame inputs, auto-orient, resize to at most 2048 pixels on either side, and re-encode a single frame to a bounded WebP/JPEG output with metadata/EXIF/ICC/comments removed. Never return original bytes, original content type or a library error body. Set `Content-Type` to the actual safe output, `Cache-Control: private, no-store, max-age=0`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'`, and no `ETag`/`Last-Modified`. Apply private/no-store to **all** success, denial, stale, decode and failure paths; disable route/framework/CDN caching and response compression/caching that stores derivatives. Generic 404 for unavailable/denied/stale slot, 400 only for malformed syntax, and generic 503 for infrastructure failure; no subject existence or path details. Bound work/concurrency and timeout to resist decompression abuse.

An option that avoids a broad service key must be preferred if a reviewed user-bound private-object access mechanism becomes available. Do not implement a service route that trusts `actor_id` from the request or that fetches a path before authorization. Resolve the service-role privilege question in the independent security review; if it cannot be made narrow and testable, defer peer photos while keeping rich text gated off or split the implementation.

## Revocation, gates and QA

Each new detail/photo request re-evaluates live Auth, active account, same active campus, both People opt-ins, rich consent, text publishability, pilot availability, `people` capability, People/rich gates and bilateral blocks. Opt-out, People opt-out, block, sanction, email change/unconfirm, campus transfer, gate closure and photo replacement/removal deny subsequent requests. A request already authorized before a committed change may finish, consistent with existing statement-snapshot reads. No browser prefetch, service worker, CDN or framework cache may keep peer images; already displayed/downloaded bytes cannot be recalled.

Implementation gate: accepted ADR-0036, reviewed narrower task contract, migration plus disposable-local tests, independent security review, then frontend wiring and rendered QA. Bounded split: (A) consent and caller-bound rich text with denial/revocation tests; (B) privileged photo resolver/gateway and image/privacy tests. Keep B off until its service credential, caller-binding and race tests pass. Neither stage includes hosted migration or gate activation.

Required matrix: SQL grants/RLS for anon/authenticated/service_role, direct raw profile and Storage denial, owner-only writes, default-off and pre-existing People opt-in; CAS stale/no-op and concurrent People-off/rich-on; SQL/Auth HTTP detail for anonymous, forged actor, self, unopted viewer/subject, text-unpublishable subject, cross-campus, unconfirmed/non-allowlisted email, suspended/banned party, both block directions, pilot/capability/People/rich gates off, revoked consent and current success; photo HTTP for each slot, invalid/stale revision, replacement/removal, absent/deleted object, cross-user copied URL, direct Storage path/signed URL absence, `HEAD`/method and arbitrary-path denial; races where opt-out/block/sanction/gate/eligibility change happens before/after authorization and during Storage fetch; hostile images (bad magic, corrupt, >5 MiB, >20 MP, animated, EXIF/GPS, orientation, output size) and no metadata leak; every response cache/error header and no path/log leak; browser at 320/390/793/1280 with owner opt-in preview, owner opt-out while gates/eligibility are lost, peer load/empty/error, Add friend/Say hi/report/block states and photo revocation. Existing critical People, safety, profile, Auth/Storage tests plus lint/typecheck/build must still pass.
