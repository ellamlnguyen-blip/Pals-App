# TASK-016C — safety interaction and visual plan

This plan accompanies the C contract and requires independent review and canonical publication before implementation. Design read: a calm safety utility for college students in the existing Pals app, with familiar rounded Nunito typography and campus blue. Leon Taste dials: `DESIGN_VARIANCE 3`, `MOTION_INTENSITY 2`, `VISUAL_DENSITY 4`. The skill is written mainly for landing pages; its form contrast, hierarchy, mobile and restraint guidance is useful here, while hero and marketing imagery patterns do not apply. The coordinator inspected live usepals.com on 2026-09-23: white canvas, soft blue surfaces, large rounded corners, friendly heavy sans and compact navigation. “Memories” and “Create an event” on that reference are not product authority. No new design library, marketing art, decorative motion or sixth nav item.

## Screen structure

`/safety` begins with a compact heading, one sentence stating that these tools manage privacy and reports, and a plain local-only availability note. The page uses the existing `Frame`, shared `--pals-*` color/spacing/radius tokens and native controls. A one-column reading order works on phone; desktop can use a narrow introductory rail and main content only if it improves scanning. Keep the three sections visible in order: block a known account ID, outbound blocked IDs, report a concern. Add “Safety” to the signed-in shared header/account area so active unready or opted-out owners can reach it; the existing profile path alone may be readiness-restricted. Primary navigation remains exactly five items.

The blocked-ID list and retained Hangout list use text rows with IDs in a wrapping monospace style, a small own-state label only on retained rows, and one action per row. No avatar silhouettes, hidden-person placeholders, fake names or pseudo-detail. A 24-row page has a simple “Next IDs” link with keyset cursor and a way back to first page. On an empty list, say “You have no outbound blocked IDs on this page”; do not imply there are no incoming blocks. An unavailable page offers a reload and retains no stale IDs.

## Key paths and suggested copy

| Trigger | UI path and message |
| --- | --- |
| Current People/friend/DM block | Open native dialog with known exact ID. Lead: “Block this account?” Explain: “Any friendship and direct chat with this person end. If you host a Hangout you both joined, they are removed. In any other Hangout you both joined, you leave. This may affect more than one Hangout. Unblocking later will not restore attendance or your relationship.” Add “Blocking does not guarantee physical safety or prevent contact outside Pals.” Buttons: “Cancel” and “Block this account.” |
| ID-only block on Safety route | Full UUID input, then same dialog. Explain “Use the full account ID. No profile details are shown here.” Authorization remains in the server path. Error: “This account or action is unavailable.” No lookup preview. |
| Confirmed block | “Block confirmed. Your shared Hangout access may have changed.” Link to outbound IDs. Do not enumerate Hangouts or promise a notification. |
| Block response unknown | “We could not confirm the block. Check your blocked IDs before choosing another action.” Fresh exact-ID check, then a new deliberate confirmation for any change. No silent resend or claim that an in-flight old request was cancelled. |
| Unblock | Exact-ID dialog: “Unblocking may allow future interaction under the usual rules. It will not restore a friendship, direct chat or Hangout attendance.” Confirm button names the action. Unknown result asks to refresh exact outbound state. |
| Current report | Known user or Hangout context opens report form with type and already-authorized reference. Avoid copying profile, roster, chat or location into the form. |
| Removed/hidden report | From `/safety`, select a retained Hangout ID and choose “Report this Hangout” or “Report its host.” Display only ID and own participation state. For host, say “Report the host of this Hangout. Their details are not shown here.” |
| Report success | “Report saved locally.” Show opaque receipt/time if present, and “Blocking is a separate choice.” No promised reviewer, response time, emergency help or automatic action. |
| Report unknown | “We could not confirm whether this report was saved.” Offer “Retry this same report” with unchanged payload/key; edit starts a new report attempt and is clearly labeled. |
| Denied or limit | “This report cannot be submitted right now. Check account access or try again later.” Avoid target existence, limit reset estimate or case status. |

Category controls should be native and labeled; “Other” turns the narrative into a required field and focuses its inline error on failed submission. The narrative counter counts Unicode code points in trimmed server-bound text to match PostgreSQL length, rejects more than 2000 characters, and does not keep a browser-storage draft. Preserve the current in-memory draft for a transient network error only while same-actor authorization remains verified; once access is denied or a tab/actor transition begins, clear it. A report form should ask only what is needed: category, optional text and submit. No “evidence upload” or message picker.

## Responsive and accessibility behavior

- Desktop around 1280px: content width follows `--pals-content-width`; readable form line length stays much narrower than the map page. The safety header and utility links remain visually subordinate to five-tab navigation. Dialog max width avoids long lines and has visible cancel/confirm separation.
- Tablet around 768–900px: one main column, actions remain attached to their ID rows, and no side panel overlaps the form. The 36-character UUID wraps or scrolls inside its own text area without pushing the viewport.
- Phone around 360–430px: 1rem horizontal padding, full-width inputs/buttons where useful, stacked dialog actions and native labels above controls. Nothing depends on hover or a precise touch target; safe tap targets and focus rings match existing tokens.
- Light and dark: use the existing canvas/surface/ink/muted/accent/error/line tokens; verify 4.5:1 text contrast, input labels/placeholders and focus ring visibility in both schemes. The positive receipt is plain text, not green alone; error and unknown states have text plus `role=alert`/status as appropriate.
- Keyboard and screen reader: semantic headings in reading order; dialog has labeled title/explanation, initial focus on heading or safest first control, Escape/cancel, focus restoration to a still-authorized trigger. Inline errors associate through `aria-describedby`. Busy state prevents double submit but is announced; after a resolved result focus goes to the status or next actionable control. When auth masking closes a dialog, focus does not jump into a prior actor's content.
- Motion remains limited to existing hover/focus transitions; no animation conveys critical safety state. Respect reduced motion as a default. There is no need to add a motion package.

## Data and state map

The route's owner data are fetched with no-store and rendered only after live active-account checks. Sensitive API calls check the client actor marker against the live cookie actor before returning data; the marker cannot confer authority. The safety gate controls management and report actions, not enforcement of existing blocks. Retire the old unmarked `unblockPerson` action and route People/privacy unblocks through the same new actor-bound safety path. Same-page shared controls receive contextual IDs as actor-bound props, not target query strings; unavailable source links go to `/safety` without a target. Current source entry points pass only IDs they already hold under current authorization; visible public host ID alone does not authorize a user report. Use retained `hangout_host` only for a caller with own participation, authorized `user` only with People/peer evidence, or offer the Hangout report instead; when source detail fails, route to neutral `/safety` recovery rather than fetching hidden records. A selected retained Hangout row carries only `hangout_id` and `own_state`. Report mode `hangout_host` sends that ID; it never surfaces the resolved host. Outbound and retained lists have independent cursors to avoid accidentally treating one list's page as authority about the other.

The client state machine is `checking → ready | unavailable`, with `submitting`, `unknown`, `confirmed`, `denied` as action substates. Every sensitive state carries actor ID plus a generation ticket. Auth-transition begin, document hide, page restore or actor mismatch immediately enters masked `checking`, erases IDs/reference/narrative/receipt/retry key, closes dialog and invalidates outstanding promises. Reentry performs fresh server authorization; no old fetch may update state after a newer ticket. The only in-memory report retry record is `{actor, requestUUID, mode, referenceID, normalizedCategory, normalizedNarrative}` and is erased on denial, auth switch or leaving the page. A response-lost block has no retry key, so the UI checks the exact outbound ID before offering any new deliberate change. The existing desired-state block RPC has no revision/key; an old in-flight request may still commit later. Disable parallel opposite actions in one surface, signal same-actor mutation starts/completions across tabs to mask and recheck, and never replay automatically. Show freshly observed state without claiming to cancel work already dispatched.

## Verification storyboard for the implementation agent

1. Start the built production-mode web app against disposable local Auth/DB after B integration, with safety and selected source gates explicitly toggled for fixtures. Inspect the rendered Safety route, People detail, friend row, DM, current Hangout detail/chat and removed-user path. Use two real actors to test owner-bound responses.
2. Show host and nonhost block confirmation, then act with multiple shared Hangouts; verify departure/removal and no restored membership on unblock. Try old pre-C block and unblock web action/API payloads without the new confirmation version, cookie actor marker and exact target; verify denial. Change target after opening a dialog and verify the old target cannot be submitted by that surface. Exercise both commit orders for concurrent opposing requests: UI masks/rechecks and displays actual final state, while an already-dispatched database request is allowed to finish.
3. Submit user, current Hangout, retained Hangout and retained-host reports. Interrupt a response; invoke the same-key exact retry manually and confirm one receipt, then edit and confirm a fresh UUID. Test “other” empty/2001 characters, neutral hidden-target denial, five-per-hour limit and safety gate/account revocation while a page is open.
4. Verify the hidden/removed path with developer tools or network assertions: no title/host ID/roster/private instructions/chat/location request or response, no report narrative in URL/browser storage/logs, and no report history endpoint. Inspect no-store headers and actor-bound route behavior.
5. Capture actual rendered desktop/tablet/phone and dark-mode states, keyboard through dialogs/forms and loading/empty/error/unknown/denied/confirmed states. Switch accounts across tabs and use back/forward + hide/focus during a slow response to prove immediate masking and no stale post-await render. Record concrete results and screenshots/paths in the handoff; separate exact-tip code/security and visual review complete the stage.

The visual plan is deliberately plain. Safety actions need clear consequences, current authorization and reliable recovery more than expressive page composition. Existing Pals spacing, blue/white surfaces, large radii and Nunito carry the brand without adding ornamental UI.
