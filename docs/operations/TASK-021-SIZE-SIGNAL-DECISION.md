# TASK-021 — Hosted large-Hangout signal decision brief

Status: Proposed for review; no hosted policy accepted
Date: 2026-09-25
Scope: planning only, from reviewed TASK-021 readiness plan and Accepted ADR-0024

## Decision needed
ADR-0024 permits an unconsumed private size observation in disposable local tests only. It is written once per Hangout and policy version when a genuine admitted join first observes at least 25 joined memberships with the safeguard gate on. The row contains Hangout UUID, policy version, threshold value and server observation time. It is retained when size falls or a Hangout is cancelled/disabled. Existing moderator access is limited to submitted reports under ADR-0019. The safeguard gate cannot be used in hosted staging or live operation until a separately accepted consumer, access, retention and response policy exists and its implementation is reviewed.

## Recommended operating model for decision
- Create a **separate, default-off, caller-bound review gate and operator reader** for these observation rows. The existing safeguard gate controls signal creation, host warning and map ordering; turning it off must not block review of retained observations. Deny direct client table DML/SELECT and service-role browser access. Restrict the reader to a current active moderator/admin checked on every request, and exclude the operator's own Hangouts from list, exact detail and review actions. Recheck current immutable host identity after lock waits. No unspecified conflict exceptions are implied; if additional conflict rules are needed, enumerate and accept them before implementation. Keep this queue separate from ADR-0019's report queue.
- An observation row alone is only a trigger to inspect **current, bounded evidence**, not proof of danger. The proposed exact-Hangout review projection may show the four signal fields plus current published/cancelled/disabled state, open/closed joining state, start/end time, public title and approximate public area, and a current coarse `is_large` flag. All are read through a new audited, caller-bound projection, never by granting broad source-table or private-location access. Host ID is used internally for self-review exclusion but is not returned; no exact count, roster, account details, chat, attendance, private instructions or precise coordinates are returned. A cancelled/disabled or unavailable source is marked accordingly without resolving other sources. This is a proposed expansion of operator access that requires a separately accepted ADR and fresh security review; ADR-0019's narrower report-detail allowlist is unchanged.
- A reviewer assesses that current context and records one of two fixed triage outcomes: `reviewed_no_action` or `follow_up_required`. `follow_up_required` remains open until an accepted human escalation/contact path records its disposition; acknowledgement by itself is not completion of a response. The operator may separately decide to pursue a student-submitted safety report under ADR-0019, but cannot create a report, sanction or disable a Hangout from the size signal alone. The escalation owner, approved contact channel, permitted context and completion evidence must be specified and tested before hosted use. There is no automatic notification or emergency response claim. A review state is workflow bookkeeping, not a safety finding.
- List pages use stable descending `(observed_at, hangout_id, policy_version)` ordering, with a cursor over those same fields; the existing signal PK is `(hangout_id, policy_version)`, with no separate signal ID. Every successful page read audits the returned composite keys and count; every detail read and triage transition audits its exact composite key. Triage writes require actor, server time, expected revision, fixed outcome and request UUID for safe response-loss retry. Recheck role, self-host conflict and review gate after waits; neutral denial reveals no target existence. Audit records carry no copied public text or private content.
- Require a named primary reviewer and backup, a documented review window, coverage hours, escalation route for independently identified safety concerns, and a pause/disable procedure if coverage lapses. This is a human operating responsibility; a queue without assigned coverage is not a response service. The observation is not an emergency alert, proof of attendance or a guarantee that anyone has viewed the Hangout. A documented escalation/contact channel is required before `follow_up_required` can be closed; absent that, hosted review remains incomplete.
- Retain signal and review records only for a specifically accepted, bounded period measured from observation, with separate retention for access audit. The present `private.large_hangout_signals` table has an immutable delete trigger and a Hangout FK with delete restriction; any expiry mechanism requires an additive reviewed migration and explicit exception to immutability. Require tested deletion/export/legal-hold behavior and preservation of audit evidence before hosted migration. Do not silently use a full database reset or direct dashboard delete as retention.
- Keep the safeguard gate off until the operator reader/action, audit, retention job, coverage procedures, escalation/contact path and real-role tests pass in the authorized nonproduction target. On coverage failure, the proposed response is to disable the safeguard gate to stop new signals and hosted safeguard use, while leaving the separate review gate available to assigned operators for pending observations and audits. If operator credentials or review access are compromised, disable the review gate too and follow a separately approved recovery procedure; do not treat hidden pending rows as resolved. Gate changes never open student access or erase retained rows.

## Values and owners that must be chosen before acceptance
| Item | Concrete decision required | Why it cannot be inferred |
| --- | --- | --- |
| Review cadence and coverage | Primary/backup roles, operating hours and maximum time from observation to review | No reviewed staffing or response agreement exists. |
| Escalation/contact | Named owner, permitted channel/context, evidence of follow-up completion and recovery path | A triage outcome alone cannot close a required response; ADR-0019 allows sanctions only from exact submitted reports. |
| Retention | Signal/review lifetime, access-audit lifetime, legal hold and deletion/export owner | Current rows cannot be deleted under ordinary trigger behavior. |
| Operational failure | Who disables each independent gate, who drains pending observations and how review resumes | Safeguard gate-off suppresses future signals but does not erase existing rows. |
| Self review | Accept the proposed own-Hangout exclusion for list, detail and triage; decide whether another operator can cover these rows | ADR-0019 excludes own Hangout reports; a self-reviewed observation is not independent. |

## Implementation and verification after an accepted decision
Publish a narrow policy ADR and a separately reviewed backend/operator contract before any migration. Test actor/role/self-host conflict and removal, direct REST denial, old RPCs, both gate-off modes, pending-row review after safeguard shutdown, pagination, lost-response retry, stale revision, access/read audit, concurrency, retention expiry/legal hold and neutral errors on actual local roles. Verify private fields never appear in student APIs, URLs, browser storage or analytics. Review exact-tip security and operator UI if one is built. Hosted authorization, exact migration manifest, staffed dry run and cleanup remain TASK-021 release gates; this brief grants none.

## Options
1. **Audited human review** (recommended for eventual hosted safeguard use): accept and implement the bounded model above after choosing the missing values/owners. It preserves the provisional host warning and map dampening while giving the private observation a real consumer.
2. **Defer hosted safeguard use:** leave its gate off and do not claim the launch large-Hangout review requirement is complete. This can support independent staging checks of other features, but TASK-021's full launch rehearsal remains incomplete.
3. **Revise the size policy:** propose a replacement ADR with a different consumer or remove the observation, then re-review product and safety consequences before hosted use.

No option is accepted by publishing this brief. The user's prior “accept” was for the TASK-021 planning sequence, not a choice of review workflow or retention values.
