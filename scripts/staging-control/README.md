# Pals Staging control preparation

This directory contains SQL statements outside automatic migrations. ADR-0029 and the staging-only ADR-0035 emergency exception are accepted; this implementation still requires independent review and the actual combined migration preflight. Do not execute against hosted staging until the exact reviewed commit, migration and applicable TASK-027/TASK-028R gates are verified.

The runner uses the user's existing logged-in Supabase CLI credential. It calls `projects list` and `db query --linked --project-ref ffabdrgsmtfylrehwmfo` through the Management API; it never asks for a token. The installed CLI rejects `--project-ref` without `--linked` for this query. It requires `SUPABASE_CLI` only when the installed CLI is not on PATH. Set `PALS_CONTROL_PROJECT_REF=ffabdrgsmtfylrehwmfo`, `PALS_CONTROL_SUBJECT_ID=8ebd74bb-2a72-4689-9580-72268106d91b`, `PALS_CONTROL_REVIEWED_COMMIT` to the independently reviewed full checkout SHA, a fresh `PALS_CONTROL_REQUEST_ID`, `PALS_CONTROL_REASON`, and `PALS_CONTROL_AUTHORIZATION_REF` to the recorded staging change authorization. Choose one `PALS_CONTROL_OPERATION`: `first_manager`, `revoke_manager`, `grant_moderator`, `revoke_moderator`, `grant_admin`, `revoke_admin`, `source_gate`, or `emergency_availability_off`. The role table has one row per account. `grant_admin` requires Ella's current `moderator` role and upgrades it to `admin`, retaining moderation authority under the existing RPC checks. `revoke_admin` restores `moderator` even after account status or email loss. Revoke moderator separately to remove all operator authority. Each transition requires a distinct request UUID and audit receipt.

Manager operations additionally require `PALS_CONTROL_EXPECTED_REVISION` (`0` for first manager; the current live revision for revoke). Source gate operations require `PALS_CONTROL_GATE`, `PALS_CONTROL_EXPECTED_ENABLED`, and `PALS_CONTROL_NEW_ENABLED`, using literal `true`/`false`. The exact source gate allowlist is in `run.mjs`; `rich_profiles` maps only to `private.rich_profile_feature_gate`, using the same locked, expected-state, audited SQL as the other gates. Analytics and large-Hangout safeguards are excluded. Each change needs its own authorization and request UUID; read the current gate state before choosing expected state. An exact gate retry succeeds only while the locked gate still has the requested result. After a reversal, an old request UUID fails; a subsequent authorized transition needs a fresh request UUID and the current expected state. Enabling the rich gate does not grant user consent or backfill profiles. Emergency availability-off requires `PALS_CONTROL_EXPECTED_REVISION` for the currently enabled availability row and accepts no gate or desired-state input. An exact retry succeeds only while that shutdown remains the current availability revision; if availability has since reopened, the old request fails and a newly authorized request with the current revision is needed. `node scripts/staging-control/run.mjs` executes one operation. No bulk toggle is available.

Before role or manager writes, independently verify the live Auth/account UUID, confirmed current email, active UNC campus evidence and expected row state; those SQL operations repeat the identity checks under locks. Emergency availability-off is specifically for an incident when Ella's session is unavailable: verify the exact current enabled availability row and revision, incident authorization and CLI project instead of treating Ella's current email as a precondition. Verify the confirmed-UNC migration `20261004000100`, the combined reviewed lane `20261005000100` through `20261005000700`, and reviewed profile migrations `20261006000100` through `20261006000300` in exact staging history. The runner requires all of them, `20261006000300` as the latest applied version, the audit table, the CLI project list name/ref, `postgres` session, and the reviewed checkout commit before writing. A missing required version or later version makes preflight deny the operation. A failed/uncertain response requires read-only audit reconciliation by request UUID. Do not generate a new UUID or retry blindly. The receipt reports the actual shared `postgres` database session, not a named human identity; record the human authorizer, executor and reviewer separately in the change record.

For local verification only, reset a named disposable local stack through reviewed profile migration `20261006000300`, then pipe `node scripts/staging-control/test-local.mjs` to `psql -X -v ON_ERROR_STOP=1`. The test creates a synthetic Ella UUID inside one rolled-back transaction. It must never target hosted SQL. The test exercises exact rich-gate retry, changed-request denial, stale-state denial, on/off reversals and stale receipt denial in both directions, plus the unchanged one-way emergency guard. For an authorized hosted rich-gate rollback, use a new request UUID with expected `true` and desired `false`; revoke admin, moderator and manager separately if those roles were actually granted. Normal availability and capability changes use Ella's genuine authenticated `set_pilot_policy` session. If that session is unavailable during a staging incident, `emergency_availability_off` requires expected revision, request UUID, bounded reason and authorization reference; it can change only availability true to false. It never enables availability. Production requires a separate reviewed adaptation.
