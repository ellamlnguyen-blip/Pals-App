# Pals Staging control preparation

This directory contains SQL statements outside automatic migrations. ADR-0029 and the staging-only ADR-0035 emergency exception are accepted; this implementation still requires independent review and the actual combined migration preflight. Do not execute against hosted staging until the exact reviewed commit, migration and TASK-027 activation gates are verified.

The runner uses the user's existing logged-in Supabase CLI credential. It calls `projects list` and `db query --linked --project-ref ffabdrgsmtfylrehwmfo` through the Management API; it never asks for a token. The installed CLI rejects `--project-ref` without `--linked` for this query. It requires `SUPABASE_CLI` only when the installed CLI is not on PATH. Set `PALS_CONTROL_PROJECT_REF=ffabdrgsmtfylrehwmfo`, `PALS_CONTROL_SUBJECT_ID=8ebd74bb-2a72-4689-9580-72268106d91b`, `PALS_CONTROL_REVIEWED_COMMIT` to the independently reviewed full checkout SHA, a fresh `PALS_CONTROL_REQUEST_ID`, `PALS_CONTROL_REASON`, and `PALS_CONTROL_AUTHORIZATION_REF` to the recorded staging change authorization. Choose one `PALS_CONTROL_OPERATION`: `first_manager`, `revoke_manager`, `grant_moderator`, `revoke_moderator`, `grant_admin`, `revoke_admin`, `source_gate`, or `emergency_availability_off`. The role table has one row per account. `grant_admin` requires Ella's current `moderator` role and upgrades it to `admin`, retaining moderation authority under the existing RPC checks. `revoke_admin` restores `moderator` even after account status or email loss. Revoke moderator separately to remove all operator authority. Each transition requires a distinct request UUID and audit receipt.

Manager operations additionally require `PALS_CONTROL_EXPECTED_REVISION` (`0` for first manager; the current live revision for revoke). Source gate operations require `PALS_CONTROL_GATE`, `PALS_CONTROL_EXPECTED_ENABLED`, and `PALS_CONTROL_NEW_ENABLED`, using literal `true`/`false`. The exact source gate allowlist is in `run.mjs`; analytics and large-Hangout safeguards are excluded. Emergency availability-off requires `PALS_CONTROL_EXPECTED_REVISION` for the currently enabled availability row and accepts no gate or desired-state input. An exact retry succeeds only while that shutdown remains the current availability revision; if availability has since reopened, the old request fails and a newly authorized request with the current revision is needed. `node scripts/staging-control/run.mjs` executes one operation. No bulk toggle is available.

Before role or manager writes, independently verify the live Auth/account UUID, confirmed current email, active UNC campus evidence and expected row state; those SQL operations repeat the identity checks under locks. Emergency availability-off is specifically for an incident when Ella's session is unavailable: verify the exact current enabled availability row and revision, incident authorization and CLI project instead of treating Ella's current email as a precondition. Verify the confirmed-UNC migration `20261004000100` and the combined reviewed local lane `20261005000100` through `20261005000700` in hosted migration history. The runner requires `20261005000700` as the latest applied version, as well as the audit table, the CLI project list name/ref, `postgres` session, and the reviewed checkout commit before writing. These newer migrations are not yet proven deployed on staging, so the preflight must deny any control operation until separately reviewed deployment. A failed/uncertain response requires read-only audit reconciliation by request UUID. Do not generate a new UUID or retry blindly. The receipt reports the actual shared database session; record the named operator/reviewer in the separate change record.

For local verification only, reset the named disposable local stack from the combined migration lane through `20261005000700`, then pipe `node scripts/staging-control/test-local.mjs` to `psql -X -v ON_ERROR_STOP=1`. The test uses an exact synthetic Ella UUID inside one rolled-back transaction. It must never target hosted SQL. Run source gate rollback with expected `true` and desired `false`; revoke admin, moderator and manager separately after shutdown. Normal availability and capability changes use Ella's genuine authenticated `set_pilot_policy` session. If that session is unavailable during a staging incident, `emergency_availability_off` requires expected revision, request UUID, bounded reason and authorization reference; it can change only availability true to false. It never enables availability. Record the human authorizer, executor and reviewer separately from the shared `postgres` audit session. Production requires a separate reviewed adaptation.
