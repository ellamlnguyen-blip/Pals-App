# ADR-0011 — Owner profile enrichment and additional photos

Status: Accepted
Date: 2026-09-22

## Context
Accepted MVP includes optional profile sections and four additional photos. TASK-003 implements required profile drafts, a primary photo and live readiness only. Its profile table has no optional fields; Storage permits immutable owned objects but does not model additional-photo membership. Peer privacy/block precedence is undefined. TASK-006 must not infer it or depend on Proposed ADR-0010.

## Decision
1. Keep required fields and limits unchanged: real name 1–100, major 1–200, bio 1–2000 characters and graduation year 1900–2200. Owners may edit these through a ready-only profile page reached from the avatar/header. University and verified email are read-only identity information. Do not implement email/campus changes, new eligibility attributes or inferred identity. The editor requires nonblank required values and a primary photo; existing direct draft updates may still cause readiness to return to onboarding. Do not weaken that live gate.
2. Add typed optional columns to the existing owner-only profile row: interests and down-to-do as ordered text arrays (0–10 items each; each trimmed item 1–80 characters; no duplicates), favorite music and favorite foods as nullable plain text (1–500 characters when present), weird fact as nullable plain text (1–500), prompts as an ordered JSON array of at most three objects with exactly `question` (1–120 characters) and `answer` (1–500), and Instagram as a nullable handle (1–30 ASCII letters, digits, underscores or periods, no URL or leading @ after normalization). Empty optional fields normalize to null/empty arrays. Enforce shapes/counts/bounds in database constraints as well as server validation. No HTML, arbitrary extensible JSON, remote embeds, external fetching or social OAuth. Future sections use explicit migrations. These bounds and representations were explicitly accepted with this ADR.
3. Add `additional_photo_paths text[] not null default '{}'` to profiles. Preserve `primary_photo_path` and readiness semantics. Store at most four ordered, non-null, nonblank, unique extra paths, none equal to the primary. Every referenced path must identify an existing object owned by this profile owner in the private profile-photos bucket under their UUID. Validate the entire resulting primary/extra set on every photo-reference update, including direct API writes. Row-level atomic updates serialize competing photo-set changes; stale editors must be rejected or reconciled without silently resurrecting a removed reference.
4. Support primary replacement and extra-photo add/replace/remove. Extra display order is insertion order; custom reordering and promoting an extra to primary are deferred. Upload new immutable objects before assigning references. Keep the old reference until assignment succeeds; removal detaches first, then deletes. Extend Storage deletion protection to every referenced primary or extra object. Assignment versus deletion races must preserve referential safety or fail closed; a privileged object loss must still revoke readiness if it affects the primary. No client overwrite policy. Clean up failed/new or detached uploads where possible without deleting any currently referenced object; report cleanup failure, retain private unreferenced objects for retry, and do not claim cross-service atomicity. Five is the displayed reference limit, not a bucket object quota.
5. Preserve current access distinctions: existing profile draft reads/updates remain active-owner-only at the database boundary; photo reads/uploads/deletes require the live active verified owner. Optional text uses the same profile-row policy. The profile editor/actions and app photo streams require live ready access. Incomplete users retain TASK-003 onboarding, including its verified-owner upload path. No peer, anonymous, same-campus, friend, moderator or admin client bypass. Serve only the caller's currently referenced photos through authenticated uncached routes with opaque slot selection, never arbitrary supplied paths/user IDs, public URLs or bearer signed URLs. Include no-store on error responses too.
6. Preserve the existing private bucket, 5 MB JPEG/PNG/WebP restrictions, signature checks and immutable UUID paths. No image processing/EXIF removal is added here; metadata remains in private originals as documented in TASK-003. Peer photo release requires a separate accepted privacy/blocking and image-metadata decision with tests. No launch-readiness claim.

## Consequences
A single owner profile row keeps photo references and optional data inside the existing RLS boundary without a new service or new reader classes. Database validation must defend direct API requests and concurrent mutations, not only editor submissions. No TASK-005 table, RPC, policy or ADR acceptance is needed. TASK-003 deployed HTTPS callback and real UNC delivery remain independently open.

## Alternatives
- Separate photo/section tables: more extensible but unnecessary for four fixed extra references and this bounded owner-only increment.
- Unconstrained profile JSON: flexible but weakens validation and introduces unreviewed attributes.
- Peer-visible profiles now: deferred because privacy and blocking rules are not resolved.

## Acceptance evidence
On 2026-09-22, the user replied “i accept” to the coordinator's explicit request to accept ADR-0011 as written (optional-field limits, four additional private photos, safe replacement/removal rules). This accepts the complete decision above and authorizes local TASK-006 implementation under its bounded contract. Hosted Supabase/Vercel changes and deployment remain excluded. ADR-0010 is unaffected and remains Proposed.
