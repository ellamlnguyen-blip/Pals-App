# ADR-0014 — Local friendship requests and relationship privacy

Status: Proposed — explicit acceptance required before TASK-012 implementation
Date: 2026-09-23
Task: TASK-012

## Context
Accepted ADR-0007 calls for mutual friendship as coordination infrastructure, without follows, public counts or popularity scores. Accepted ADR-0013 supplies an opt-in, same-campus text People directory and directional People-only blocks. It expressly does not authorize friendship or global Hangout/private-data block precedence. Raw profiles and photos remain owner-only. Existing Hangouts are campus-visible and unrestricted under ADR-0010; friends-only access is still rejected. The product specifications do not settle request eligibility, relationship visibility, re-request behavior or how a People block affects a friendship.

## Proposed decision
Acceptance would authorize only disposable-local TASK-012 stages after narrower contracts are published. A separate default-disabled `private.friendship_feature_gate`, with no client write grant, controls direct friendship reads/mutations and web entry points. Safety teardown triggered by an authorized People block is the explicit exception: it still runs while the friendship gate is off, under the existing People gate and active-owner checks. The web additionally requires `APP_ENV=local` and a validated loopback Supabase target. No hosted migration, deployment or live student use follows.

### Requests and state
- A friendship is mutual only after an explicit recipient acceptance. Store one canonical unordered account pair with the campus at formation, requester ID, a server-generated immutable request-generation ID and state `pending` or `accepted`; do not model follows or public popularity. Database constraints and caller-bound operations prevent self-pairs, duplicate/opposite pending pairs, forged actors and cross-campus creation/acceptance. A recipient may accept or decline; a requester may cancel; either accepted friend may unfriend. Every transition of an existing request must supply its immutable generation ID; a stale transition cannot act on a later request for the same pair. Request creation also uses a caller-scoped UUID idempotency key with a private retained ledger: retrying an old key cannot create a new pending pair after the first request was accepted, declined, cancelled, blocked or unfriended. It returns only the original result while still authorized, or a generic unavailable result after teardown. A deliberate new request after unfriend uses a new key. Desired-state retries must not duplicate requests or reverse a later transition. Return a generic unavailable/conflict result when the current generation/state cannot authorize the action.
- A new request requires both accounts to be live-ready at the same active campus, both opted into People, and mutually visible under ADR-0013, including its either-direction People block check. The UI offers requests only from existing People detail. The database independently rechecks visibility for any supplied target ID, so possession of an attendee ID or old link alone grants no friendship action or hidden-person probe.
- Request receipt and acceptance use current database eligibility, not a prior page view. The recipient may decline an existing incoming request and the requester may cancel an outgoing request even after their own readiness/People visibility changes, provided the caller remains an active account. Accepted friends may unfriend under the same active-owner rule. Suspended/banned callers cannot manage friendship through client APIs. Acceptance requires both accounts currently ready, same-campus, opted in and unblocked; otherwise the recipient can decline but cannot turn stale eligibility into friendship.
- Decline and cancellation clear active relationship state while retaining a private directional request suppression record: the same requester cannot resend to that recipient in this local increment, but the former recipient may initiate a new request when both become eligible. Unfriending clears the accepted relationship; either person may explicitly initiate a fresh request later. A block in either direction clears pending and accepted friendship; unblocking never recreates a request or friendship, though a fresh request may be possible under current eligibility and any existing decline/cancel suppression. Suppression is not a public reputation signal or browse filter. Any future retry interval or appeal requires a separate decision.
- If a participant later loses readiness, opts out or changes campus, an existing relationship remains as participant-owned ID/status only. New requests and pending acceptance fail until both satisfy current eligibility; active participants can still cancel, decline or unfriend. It grants no cross-campus People text, Hangout access or other reader. Campus transfer itself is outside this task; any automatic relationship expiry on transfer requires a later decision.

### Readers and privacy
- Each active participant can read only their own pending incoming/outgoing and accepted relationship IDs, immutable generation ID, direction and state. There is no incoming request enumeration for nonparticipants, count, public friend list, mutual-friend discovery, ranked People recommendations, or platform-role bypass. Relationship rows and suppression records have no direct client table access; fixed caller-bound APIs enforce the reader and gate.
- UI may display peer text only by calling the existing ADR-0013 People projection under its current opt-in/readiness/campus/block rules. If the other person becomes unavailable, show a neutral unavailable label alongside the caller-owned relationship control; never hydrate text from a saved relationship snapshot, hidden profile row or photo. Request/accept responses contain no additional peer fields. Every response, including denials, is no-store, and the UI clears peer text after loss of access.
- Block and friendship mutations for the same unordered pair serialize and recheck current eligibility after waiting. The existing `set_people_block` operation is extended narrowly so setting a block also ends that pair's pending/accepted relationship in the same transaction, even if the friendship gate has since been disabled; its People gate and active-caller requirement remain in force. This proposal adds a narrow exception to ADR-0013's visible-target block rule: a caller may set a People block on an ID currently in their own pending/accepted friendship pair even if that peer has since opted out, lost readiness or changed campus. The database proves current pair participation after the pair lock; mere possession of an old ID is insufficient, and no peer text or incoming-block information is returned. Existing owner-directed blocks retain their current rules otherwise. A committed block prevents a subsequent request or acceptance; after friendship-gate re-enable, no cleared relationship returns. No friendship exception to People suppression. A new request after committed opt-out, readiness loss, campus change or gate disable is denied. Already delivered text cannot be recalled.
- No automatic notification, push, DM, invite or chat is created by friendship actions in this increment. The UI states request status through owner-only views; TASK-015 owns notification policy and delivery. No friend graph becomes a generic peer reader or a Hangout authorization input under this ADR.

## Consequences and sequencing
Friendship can be tested locally from the opted-in People flow without changing the owner-only profile/photo boundary or current Hangout queries, rosters, joining and private instructions. Friend-aware ranking, friend-attendance context and friends-only Hangouts still need separate, accepted access and block-precedence contracts. TASK-016 still owns global block/report behavior before hosted use. TASK-010 and Proposed ADR-0012 remain independent.

Implement the database/state and concurrency boundary first; independently review and integrate it before the People friendship UI. Committed migrations are additive; both feature gates remain disabled by default and test data is disposable. Privileged functions require fixed search paths, narrow grants, live membership checks and actual-role SQL/HTTP tests. No direct client DML or service-role web proxy.

## Alternatives
- Allow requests from any same-campus account ID: simpler but creates a contact/probing path outside opt-in People; rejected for this proposal.
- Preserve friendships through a People block: simpler state but unblocking could silently restore a relationship; rejected for this proposal.
- Permit immediate re-requests after decline: useful for accidental declines but invites repeated unwanted requests; deferred.
- Add notifications, mutual friends, friend-aware ranking or restricted Hangouts now: exceeds this local relationship boundary and requires separate reader/access decisions.

## Acceptance evidence
None. This ADR is Proposed. Publishing it does not authorize migration, peer reads, relationship actions or hosted operation.
