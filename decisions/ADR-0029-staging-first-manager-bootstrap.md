## Exact operations and boundary

`first_manager` inserts only Ella as the first active admission manager, when no active manager exists and her manager row is absent at expected revision zero. `revoke_manager` changes only her active manager row at its expected revision. Both take the existing `pilot_lock_management` ordering. Grant rechecks her locked live active Auth/account/membership/UNC evidence after waits. Revocation checks the exact still-existing Auth/account UUID and may proceed after suspension, ban, or email change so compromise cannot prevent rollback. Both append the existing immutable `pilot_manager_audit` and the new control audit in the same transaction. They cannot write admission, policy, platform roles, or gates. An old fixture function remains for disposable local tests; this channel never invokes it on hosted.

`grant_moderator` inserts only Ella's `moderator` platform role, requiring no existing operator role for anyone else. `revoke_moderator` removes exactly that role. A table lock serializes competing platform-role writes; existing social/Hangout and moderation lock order is taken first. Neither operation grants `admin` or report permissions beyond the existing audited moderation boundary. Ella is the user's sole launch moderation owner; a backup is not required. Grant rechecks active Auth/account and exact UNC evidence; revoke requires the exact still-existing Auth/account UUID but works after status/email loss. A separately decided admin sanction/reinstatement operating path remains outstanding if launch requires it.

`source_gate` changes exactly one preexisting source gate per request with a compare-and-swap expected boolean. The allowlist is `hangouts`, `hangout_chat`, `people`, `friendship`, `dm`, `notifications`, `attendance`, `safety`, and `moderation`, mapped to fixed private tables in the committed runner. It excludes large-Hangout safeguards and external analytics. The shared pilot evidence writer lock, policy rows, and target gate row are locked before recheck/write. No arbitrary table name is accepted from the operator. The normal `set_pilot_policy` RPC remains the **only** channel for capability and availability changes; it must be called with Ella's genuine signed-in session after first-manager provisioning, under its existing live manager authorization and immutable audit. There is no administrative SQL substitute for that caller-bound policy transition.

Each operation requires a unique request UUID, bounded reason, authorization reference, and expected state/revision. A repeated UUID with identical payload returns the prior result without a second write; reuse with changed payload fails. A conflict, inactive/changed Ella account, wrong project/role/migration, stale state, or operation error aborts the single SQL statement with no partial write. The immutable audit records previous/new state, request UUID, reason, references, database session/PID, and time in the same transaction. A response failure is uncertain: use read-only UUID reconciliation before any retry.
