# ADR-0029 — Staging first-manager bootstrap

Status: **Proposed — no hosted action authorized**
Date: 2026-10-04
Scope: TASK-027, nonproduction `Pals Staging` (`ffabdrgsmtfylrehwmfo`) only

## Context

Pals Staging has the 27 committed migrations applied, zero active pilot admission managers, and every source/capability gate off. Accepted ADR-0028 removes pilot roster membership from student eligibility, but the existing manager RPC is still the controlled way to change private capability policy. Accepted ADR-0027 deliberately excludes its `private.set_pilot_manager_fixture` function from hosted bootstrap. That function's `postgres` session provenance is insufficient to identify a hosted human executor. A moderator's `public.platform_roles` row is a separate authority and cannot grant admission-manager rights.

## Proposed decision

Create a **staging-only, single-purpose, authenticated bootstrap channel** for the first active admission manager. Its implementation requires a separately reviewed committed migration and operating contract before use. The migration must bind the exact Pals Staging project ref and one preapproved Auth/account UUID in private configuration, with no client grants; production must have no bootstrap role, target binding, or EXECUTE grant. A private `SECURITY DEFINER` operation can create one active manager row only for that bound UUID, with expected revision zero, a reason, and a unique request UUID. It must require zero existing active managers and atomically consume a one-time bootstrap authorization. It must use the existing pilot management serialization/row-lock order and recheck a current active target account after waits. It must atomically append immutable audit evidence containing the previous and new state/revision, target UUID, reason, request UUID, server time, and actual database `session_user`. A mismatch, retry with changed payload, inactive target, existing manager, consumed authorization, failed lock/recheck, or non-staging invocation must fail without a partial write. There is no general manager-assignment API, email resolver, policy change, platform-role write, source read, or gate enablement in this operation.

The sole executor is an individually identified human using a unique staging PostgreSQL login. That login is `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, and `NOBYPASSRLS`; it has only the minimum connection/schema/execute grants needed for this operation after a catalog review of inherited and `PUBLIC` grants. The function checks an exact allowlist of that login via `session_user`, never an actor string, email, client metadata, request payload, JWT claim, or `application_name`. The login has no direct DML on the manager, policy, audit, account, Auth, or platform-role tables. Supabase documents default function `EXECUTE` and Data API grants, so implementation must inspect/revoke effective and default `PUBLIC`, `anon`, `authenticated`, and `service_role` paths and prove denied access with actual roles. Provisioning the role, function, grants, and target binding must be reproducible from reviewed, committed staging migration/configuration changes. A shared `postgres` credential, Supabase SQL editor session, browser service-role key/proxy, or the fixture writer is not this channel.

**A project ref written by the same migration that installs the bootstrap does not prove that the migration ran on staging.** Before acceptance for implementation or use, a concrete mechanism must prevent bootstrap objects and grants from being installed by ordinary production migration replay and independently verify the exact staging endpoint immediately before execution. A project-ref constant or database setting installed by that migration is self-attestation and insufficient. If staging-only application cannot be established, this proposal must be rejected or replaced by another reviewed design.

The named executor and distinct approver must be recorded in the staging change record before credential release. The executor authenticates to the approved credential vault with MFA and receives a unique, short-lived staging credential through an access-controlled channel; it is never placed in Git, chat, shell arguments, client bundles, CI logs, or browser storage. `session_user` identifies a database login, not the human who operated it. Before credential release, verify and record the active Supabase connection-log configuration, required retention/access, and provider/vault issuance and revocation evidence mapping that login to the named executor; connection logging may not be enabled by default. The approved direct PostgreSQL connection must be limited to the exact staging project endpoint; the project ref, certificate/endpoint, and current migration SHA are checked immediately before execution. If the host cannot support independently checked staging identity, a unique login, scoped grant, trustworthy vault/MFA record, and retained database connection audit, this proposal cannot be used; no substitute actor string or shared credential is acceptable.

## Execution and independent verification

1. The approver records the exact staging project ref, target account UUID, intended manager state, request UUID, reason, migration SHA, executor identity, credential expiry, and rollback plan. The target UUID is resolved through a controlled administrative account lookup and checked against the live Auth/account records. Email alone never grants authority. A second person reviews the target and target-environment evidence before the operation.
2. The named executor performs exactly one call to the scoped bootstrap function from the authenticated staging database session. The function returns only the new revision and audit ID. No gate or student access setting changes in this step.
3. A different reviewer uses read-only access to independently verify the live manager row, corresponding immutable audit row, `session_user`, request UUID, vault issuance record, staging connection log, exact target UUID, and unchanged source/capability gates. The reviewer records a signed/attributed result and immediately verifies that ordinary `anon`, `authenticated`, `service_role`, and moderator sessions cannot execute the bootstrap function or write the private row. Review also confirms the manager is still a current active account.
4. The executor credential is revoked and its connection terminated after verification. Any later manager addition or revocation requires a separately approved operating path; this one-use bootstrap is not a standing superuser mechanism. Ordinary capability changes then use the accepted caller-bound `set_pilot_policy` RPC under live manager authority and its own audit, revision, and release gates. The existence of a manager does not authorize enabling any capability or opening hosted access.

No positive staging smoke result may be claimed until these checks pass. The exact migration, role grants, function behavior, transaction/audit semantics, denied roles, and rollback must receive an independent security review and actual-role nonproduction verification before credential issuance.

## Independent design review (2026-10-04)

The independent reviewer found the direction compatible with ADR-0027/0028 but not ready for acceptance as an executable design until the staging-only migration/identity mechanism and human-to-login audit evidence above are made concrete. Later implementation review must also verify function ownership, fixed `search_path`, transitive execute grants, effective/default grants, one-use transaction/idempotency behavior, and denied-role checks. No hosted change was made. This draft remains **Proposed** and is not approval to create credentials, roles, migrations, managers, or enable gates.

## Rollback and failure handling

On a wrong target or unexpected result, leave all source/capability gates off and stop. Revoke the unique executor credential and terminate its sessions. A separately reviewed, exact-target rollback operation must revoke the manager row under its current expected revision with the same lock and immutable audit discipline, using a fresh individually authenticated executor credential and approval; it cannot assign or switch targets. Audit history is retained. Recheck the manager row, audit, credential revocation, and every gate independently. Never delete or rewrite audit evidence to simulate rollback. An uncertain response requires read-only reconciliation by request UUID and revision before any retry.

## Boundaries and consequences

This is a proposal for Pals Staging only. It changes no production database, domain, Auth/SMTP setting, Vercel deployment, user roster, or gate. It does not provision a moderator: moderator/admin authority under ADR-0019 needs its own approved, audited bootstrap, MFA/recovery, and operational readiness. Under the user's 2026-10-05 decision, Ella Nguyen (`ella_nguyen@unc.edu`) is the sole launch moderation owner; a backup moderator is not required. Manager authority grants no report handling, sanction, profile/photo/message/private-place reader, or account-enforcement bypass. Suspended or banned accounts cannot use the manager RPCs even if their manager row remains active. ADR-0028's roster-free verified-UNC eligibility, existing RLS/privacy/safety rules, and the separate action-time confirmation for opening hosted access remain in force. If this design is accepted, a bounded implementation task must specify the exact staging target, named humans, credential system, migration, verification evidence, and one-use operation before any hosted write.
