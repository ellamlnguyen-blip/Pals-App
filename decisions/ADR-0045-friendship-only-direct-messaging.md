# ADR-0045 — Friendship-only direct messaging

Status: Proposed — explicit acceptance required before schema or permission implementation
Date: 2026-10-16
Task: TASK-039B

## Context

Ella now asks to remove Message requests and require acceptance of a friendship request before direct messaging. Accepted ADR-0016 originally required a first-message request; Accepted ADR-0042 extended access to either a current friendship or an independently accepted message request, including request-origin conversations that remain valid after unfriending. The current database, API, notifications and UI implement both paths. Removing only the cue would strand incoming requests and leave a nonfriend contact path available to direct API/RPC callers. The new instruction therefore changes accepted consent and retention behavior and requires an explicit new decision under AGENTS.

## Proposed decision

For the bounded disposable-local implementation, **a current accepted friendship is the sole direct-message consent source**. Both people must still satisfy every existing active-account, same-campus, bilateral People visibility/opt-in, DM and friendship gate, safety block and current authorization check. Friendship acceptance alone sends no message, creates no empty conversation and reads no prior DM. A first actual send between current friends creates an accepted pair/generation and its first message atomically; subsequent reads and sends require the friendship to remain current. The server derives the caller from `auth.uid()` and checks current relationship state under the established shared social/pair locks. A declined, pending, cancelled, removed or blocked friendship never grants DM access.

No new first-message requests may be created. Revoke or replace the old authenticated `create_dm_request`, recipient accept/reply/ignore/withdraw, and independent `allow_dm` paths, including old overloads and direct RPC grants; web/API removal alone is insufficient. Friend-send exact retries must reauthorize current friendship before returning any pair or text. A stale client, old request key, saved direct URL, attention cursor or notification link must not bypass current friendship. Existing source gates, block precedence and People concealment stay at least as strict as today.

At migration, terminalize pending message-request generations and accepted generations whose two participants are **not** current accepted friends. Keep their pair, messages, retry ledger and any reporting/audit evidence private; do not delete text, make it client readable, create a new directional suppression or emit a social notification from this retirement. Use an additive neutral terminal reason or a documented existing terminal state that does not misrepresent a recipient decision. Current accepted-friend generations remain active, regardless of original consent label, but every read/send now requires the live friendship. Ending friendship later must atomically end that active generation under the shared lock, with future reads/retries denied; a later renewed friendship starts a fresh generation without old messages. Retained directional suppression from an old ignored, withdrawn or closed request must not block a new *current-friend* generation; it continues to prevent any revived request path, and never weakens a safety block. Blocking keeps its stronger terminal effect. A gate or readiness loss denies immediately even if a cleanup transition has not occurred.

Current friends retain an explicit “Close chat” action as an intentional terminal reset. Closing keeps the old text private, does not remove friendship, and does not reopen the old generation; either current friend may start a new generation on a later first send only after all current checks, with no old text inherited. The close action must use the shared lock and current pair generation, and an old close or send retry cannot affect a newer generation.

Inbox and attention projections show only currently authorized accepted-friend DM generations; no pending request rows or page-local request count remain. Retire new DM-request notification creation. Existing request notifications become neutral unavailable on read and cannot link to message text; friend-request notifications and their accept/decline actions remain. Messages between current friends keep the normal message notification policy. A declined friendship yields no DM notification or access. Retained evidence remains under existing private RLS/no client table grants and later retention policy.

The student UI has no Message requests cue, request inbox, independent DM consent control or request-specific composer. On a peer profile, the direct-message entry point is offered only when the authoritative current friendship state permits it; the backend remains decisive. On an old direct URL or after unfriending, the page clears peer identity and message bodies and presents a neutral unavailable state with a route back to Pals. Do not use cached friendship labels as authorization. Hangout chats remain available to eligible joined members and do not require friendship.

## Verification required before acceptance of code

Apply only an additive migration to a named disposable local database. Test friend first-send, accepted-friend history, pending and request-origin retirement, legacy directional suppression under renewed/current friendship, explicit close/restart, unfriending/refriending, decline, block, People opt-out, gate/readiness loss, old RPC and exact-retry denial, inbox/attention paging, neutral old notifications, and two-session races between friend teardown and read/send. Confirm private table grants/RLS and no client service-role path. Verify actual web/API flows on two authorized accounts at desktop and phone widths, including stale URLs and state transitions. Fresh security review must inspect the migration and exact tip. Disposable-local verification is not final release acceptance; accepted-environment persistence, predecessor sign-off, hosted deployment/gate enablement, historical deletion and application-main integration remain separate gates.

## Alternatives and tradeoffs

Hiding Message requests while retaining the old RPCs is rejected because it would make the UI misleading and leave nonfriend DMs possible. Preserving request-origin chats after friendship ends is rejected because it contradicts the new sole-consent rule. Deleting old rows is rejected because it destroys safety/reporting evidence. Reopening old generations when a friendship is renewed is rejected because historical consent does not carry into a new relationship. This policy narrows contact options; it may make an existing nonfriend chat unavailable, with history retained privately.

## Acceptance

Proposed. Ella must explicitly accept this complete local policy, including retirement of current nonfriend/request-only conversations, before TASK-039B implementation. Upon acceptance, ADR-0045 supersedes only the DM request/consent portions of ADR-0016 and ADR-0042; their Hangout, notification, safety and other accepted decisions continue unless specifically amended. Approval does not authorize hosted changes or waive predecessor release gates.
