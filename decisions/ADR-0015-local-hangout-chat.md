# ADR-0015 — Local Hangout chat authorization and delivery

Status: Accepted — local-only policy
Date: 2026-09-23
Task: TASK-013

## Context
Accepted ADR-0004 makes conversation part of casual Hangout coordination. Accepted ADR-0010 provides campus-only saved Hangouts, joined membership, cancellation and live private-detail revocation, but no message policy. The realtime/messaging specification requires server-enforced membership, leaving, removal and blocking. People blocks from ADR-0013 are explicitly People-only; ADR-0014 friendship grants no Hangout access. Proposed ADR-0012 does not yet grant co-host powers. A local chat increment needs an explicit reader, write, retention and block boundary before new peer content exists.

## Proposed decision

1. **Scope and gate.** A saved Hangout owns exactly one group conversation, created atomically on first authorized send; an authorized read before the first send returns an empty page. No free-standing conversations or client-chosen recipients. A separate database chat feature gate defaults disabled and is not client-writable. Chat also requires the existing Hangout gate. Both gates are enabled only for disposable local testing; no hosted migration, enablement or live student use is authorized.
2. **Current membership and history.** Only the current joined host and joined participants of a published, campus-visible Hangout, with live ready status in that Hangout's campus, may read or send. An authorized current member can page the full retained thread, including messages from before their first join or during a period when they had left. This gives late joiners and permitted rejoiners coordination context; authors should assume a future eligible joiner can read the thread. Joining closed does not evict current members. A campus discoverer, left/removed participant, unready account or any client role after cancellation gets no messages, even their own historical posts. A removed participant cannot rejoin under ADR-0010. Host status does not bypass loss of readiness or cancellation. Co-host designation, if later accepted, grants no additional chat read/write or moderation power by itself; joined status remains necessary. There is no time-based expiry while published, matching ADR-0010.
3. **Minimal content and author projection.** Messages contain trimmed plain text only, 1–2000 characters, with server-owned ID, author, Hangout, created time and monotonic per-Hangout ordering key. No attachment, link preview, arbitrary HTML or system message. A reader receives body/time/order and `mine`; the author account ID is returned only when that author is currently ready and joined in the same Hangout, otherwise the projection returns a neutral former-participant label with no ID. This does not make voluntarily disclosed identity in message text secret. Peer profile/photos remain owner-only.
4. **Transactions and retries.** Client sends a fresh UUID creation key per composed message. A caller-scoped private ledger maps `(Hangout, author, key)` to one immutable message and canonical payload digest. Exact retry returns that message only after current authorization; key reuse with changed content fails. Never recreate a message after a lost response or revocation. Send/read operate at READ COMMITTED and fail closed at stronger isolation. Send serializes on the Hangout row used by join/leave/remove/cancel. It also takes transaction-held shared locks on both gate rows and all live-readiness evidence used by `get_access_state()` (account/Auth user, membership/campus, profile and referenced photo objects), then rechecks authorization in a fresh READ COMMITTED statement. Implement a deterministic lock order and test races with gate disable, account/readiness/photo/campus changes and Hangout transitions. A revocation that commits before those locks/checks denies; a revocation begun after the locks waits until send commits. A send committed first may be read only while later read authorization succeeds. Existing join/leave/remove/cancel Hangout-row serialization is preserved.
5. **Page and delivery.** Read uses bounded keyset pages of at most 50 in stable server order, with a fresh authorization check in the same database statement that projects each page. A read already authorized before a concurrent revocation can complete and be delivered afterward; previously delivered or in-flight content cannot be recalled. Requests whose authorization statement begins after a committed revocation must deny. The initial local UI refreshes an active visible thread by authenticated polling and after a send. Every poll uses the same authorized reader; stop polling and clear rendered text on denial/signout/navigation. This stages the eventual Supabase Realtime MVP transport: no message body, metadata or presence is published to a channel in this increment because subscription revocation and stale authorization need a separate reviewed design. Polling is a local implementation boundary, not a claim that MVP Realtime is complete.
6. **Retention and safety.** Leaving, removal, cancellation, readiness loss and gate disable revoke future client reads/sends but retain records in private storage for future reporting/moderation work. No client delete/edit and no moderator bypass is introduced. Production retention, report access and auditable moderation require separate accepted policy. Previously delivered messages cannot be recalled, so the UI must make revocation immediate for future requests and clear local display when known.
7. **People-block boundary.** Existing People blocks continue to govern only People discovery and friendship under ADR-0013/0014. They do not silently alter Hangout membership or this disposable-local chat. This explicit local limitation is not a decision that blocked people may message each other in hosted Pals. Before hosted chat, TASK-016 must establish global block precedence, restricted/private access and reporting/moderation rules, then implement and test the resulting chat separation. The local UI must not describe People block as muting Hangout chat.
8. **Least privilege.** Message/ledger storage is private with no authenticated direct DML/SELECT; caller-bound functions derive `auth.uid()` and use fixed search paths. No admin/platform bypass, raw profile read, generic peer list, server service key in client or user-provided membership claim. The web route/action additionally retains APP_ENV=local and validated loopback Supabase guards, no-store responses and clear denied/uncertain states. Database enforcement remains authoritative.

## Alternatives and tradeoffs
- Direct Realtime row payloads: deferred because an already subscribed client may retain access after membership revocation; body/metadata leakage needs a separate transport policy and tests.
- Globally apply People blocks now: rejected for this local stage because those blocks were accepted as People-only and global precedence with public/restricted Hangouts is unresolved. Hosted chat stays gated until that decision.
- Let past participants read their own message history: deferred because chat may contain private meeting instructions and ADR-0010 revokes private detail access on leave/removal/cancellation.
- Delete all messages on cancellation: deferred because later safety reporting/moderation needs evidence, and production retention is unresolved.

## Consequences
This decision permits a local coordination thread while preserving current Hangout revocation and avoiding a new peer-profile reader. It intentionally leaves Realtime delivery, global blocks, reporting/moderation and hosted use open. Acceptance alone changes no schema or access.

## Acceptance evidence
After the complete reviewed proposal was published on canonical main, the coordinator asked, “Do you accept ADR-0015 as written?” The user replied “yes” on 2026-09-23. This accepts the local-only reader/history, send/read revocation, author projection, retry, retention, People-block boundary and polling delivery decisions above. It authorizes the bounded TASK-013A/B stages after narrower contracts are published. It does not accept ADR-0012, global messaging block precedence, Realtime transport, hosted migration or deployment.
