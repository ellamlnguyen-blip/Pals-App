# ADR-0013 — Local People discovery and peer text privacy

Status: Accepted — local TASK-011 stages only
Date: 2026-09-22
Task: TASK-011

## Context
MVP and Accepted ADR-0007 require People browse/search/filter and profiles. Accepted ADR-0011 currently permits owner-only profile/photo access and requires a separate privacy/blocking and image-metadata decision before peer photos. AUTHORIZATION describes discovery suppression without precise block precedence. No friendship or block implementation exists. TASK-010/ADR-0012 remain pending and are not dependencies of this proposal.

## Proposed decision
This is a deliberately partial, text-first local People increment, not completion of the full MVP People experience. Acceptance would authorize only the local stages in the TASK-011 contract, including their committed migrations after narrower dispatch contracts are published.

### Visibility and fields
- Add an owner-controlled People visibility preference, default off for existing and new accounts. Explicit opt-in shares the allowlisted text below with live-ready students at the same active campus. Browsing does not require opting in. Opt-out revokes future peer reads, including direct profile links; it does not hide existing public Hangout participant IDs or change Hangout access.
- Both viewer and subject must be currently ready under the existing database evidence (active account/campus, current verified email, required profile and existing primary photo). Self-profile remains the existing owner route. No anonymous, other-campus, incomplete, suspended/banned or platform-role bypass. Readiness loss suppresses sharing but retains the visibility preference; restoration makes an opted-in subject visible again unless blocked. The owner may turn sharing off through a caller-bound active-owner preference operation even if no longer ready; turning it on requires live readiness.
- Browse cards return account ID, real name, campus display name, graduation year and major only. A direct peer detail returns those fields plus bio, interests and down-to-do. These are explicit fixed projections of current owner fields, not a new broadly readable profile table. The opt-in screen previews exactly those fields and explains that future edits to them are shared while enabled.
- Never return email, membership evidence/status timestamps, birth date, photo paths/bytes, extra photos, Instagram, music/foods/facts/prompts, editor revision, raw account records or arbitrary JSON. Owner data and all raw profile/Storage policies retain their current boundaries. Peer display of excluded fields requires a later accepted expansion.
- No peer photos in this increment, including initials derived from unavailable names or remote avatar lookups. Neutral placeholder artwork is allowed. Existing originals may contain metadata; a later accepted image sanitization/delivery policy and tests are required before any peer photo release.

### Minimal local block prerequisite
Stage A introduces only a directional caller-owned block relation and caller-bound set-block/unblock operations needed for People. This explicitly brings a bounded prerequisite forward from TASK-016; it does not complete TASK-016 or define global blocking.

- Either A blocking B or B blocking A suppresses both directions of People browse/search/detail, regardless of opt-in or any future friendship. No friendship exception. Direct known-ID requests and pagination must enforce the same rule in the database. Blocked, opted-out, nonready, cross-campus and nonexistent subjects produce the same unavailable result to peer readers; do not disclose why.
- A ready caller may block a same-campus visible peer, or repeat an already-owned block. No self-block, arbitrary cross-campus targeting, client-supplied blocker identity or unblock of someone else's relation. Serialize changes for an unordered account pair and recheck authorization after waiting. Concurrent mutual blocks based on previously visible profiles must fail closed: a losing call may return unavailable instead of disclosing the reverse block.
- Only the blocker can list their own outbound blocked IDs and unblock them. This bounded, paginated management read returns IDs only, no peer names/profile data, reverse-block existence or timestamps. Retained IDs allow removing a block even if the subject later becomes unavailable. The local block-management UI displays the full stable account ID with copy/select support and confirms that exact ID before unblocking; shortened display alone is insufficient. It does not retain names or caller labels. Identifying a person from an ID is an acknowledged local-only usability limitation, not a finished launch experience. Active owners retain this list/unblock path when not ready; suspended/banned callers have no client block-management access. Unblock removes only the caller's direction and never restores visibility if the other direction, opt-out or readiness denial still applies.
- Block/unblock use explicit desired state, not toggles; retry is idempotent. The database derives caller identity; no generic table DML or incoming-block enumeration. Preserve outbound blocks through readiness loss and opt-out. No automatic unblock or claim of full separation.
- Existing local Hangout discovery, rosters, joining, private instructions and host authority are unchanged under Accepted ADR-0010. This People-only block does **not** remove attendees or revoke their Hangout instructions. The local UI states this limitation before block confirmation. Block/private-location precedence remains a separately accepted and tested prerequisite before hosted use. No DM/friend/invite subsystem is implemented or enabled here.

### Read boundary, revocation and search
- Use a separate database-controlled People gate, default disabled after migration/reset, without client write grants. Every new peer read, opt-in and block mutation/read requires this gate; the gate is enabled only in explicit disposable-local setup. Owner opt-out remains available with the People gate disabled: an active owner may always set their own preference off, including after readiness loss. Turning it on still requires the gate and readiness. Existing owner profile and Storage access do not depend on it. Web routes/actions additionally require APP_ENV=local and a validated loopback Supabase target.
- Expose bounded caller-session database reads with fixed field allowlists and fixed search paths; no service-role client or web proxy that bypasses RLS. Direct profile tables, embeds and Storage must not become peer-readable. If privileged SQL helpers are necessary, limit execution/grants and independently enforce all gate/readiness/campus/visibility/block checks inside them.
- Browse is alphabetical by normalized real name then stable account ID, with a bounded cursor and maximum 24 rows per page. Search is trimmed case-insensitive literal name substring (maximum 100 characters; wildcard characters are literals), optional exact graduation-year and case-insensitive exact major filters within existing field limits. No total campus counts, popularity, friendship recommendation, inferred attributes, bulk export or filter-option enumeration of hidden subjects. Changes between pages may move results; never retain authorization from a cursor or client cache.
- Reauthorize each database request using live READ COMMITTED state; reject stronger transaction isolation for these APIs as existing Hangout APIs do. Preference/block mutations recheck current gate and actor/target permission after lock waits, except owner opt-out, which rechecks active ownership but does not require the People gate or readiness. A new request after a committed block, opt-out or readiness loss must deny the affected peer; no promise to recall already-delivered text or to cancel a response already in flight. No cross-user or public caches. All app responses, including errors, are no-store; clear displayed peer data on denial and on navigation away after block/opt-out. Do not place peer bio or result payloads in logs or persisted browser storage.

## Consequences and sequencing
The first useful slice is an opt-in campus text directory with working local privacy controls. It intentionally lacks photos, attendance context, recommendations, friend requests and DM requests; present that honestly, without fake action buttons. Neither TASK-010 nor TASK-012 is required for this slice. Later People expansion and hosted release remain separate tasks; accepting this ADR does not accept ADR-0012 or authorize hosted migration, deployment, live students, restricted Hangouts or Hangout block precedence.

Stage A provides privacy/block primitives and tested text reads; stage B provides owner controls, People screens and block management. Fresh independent security review and reviewed main integration of A precede B. All services and fixtures are disposable local; restore both feature gates to false and clean fixtures after verification.

## Alternatives
- Wait for full TASK-016 and photo privacy work: fewer temporary product limitations, but delays a useful independently testable directory. Choose this if a text-only local slice is not useful.
- Campus-visible profiles by default: less friction but expands existing private owner data without an explicit sharing action; not recommended.
- Release photos now: would require additional accepted metadata removal, safe derivatives, delivery/revocation and storage rules; deferred to a separate bounded proposal.
- Mock People shell only: can explore layout without peer permissions but does not prove real search or authorization; no mock implementation is authorized by publication alone.

## Acceptance evidence
On 2026-09-22, after the coordinator presented this complete ADR-0013 proposal and explicitly asked “Do you accept ADR-0013?”, the user replied “yes” in this task. This accepts the stated local text visibility, default-off opt-in, bilateral People blocking, minimal block prerequisite, separate disabled gate, field allowlists and local-only stages. It does not accept ADR-0012 or authorize hosted changes, photo release, global block precedence, friendship or messaging. Record this acceptance on canonical main before TASK-011A implementation dispatch.
