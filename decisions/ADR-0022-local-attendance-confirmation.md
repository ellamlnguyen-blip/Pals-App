# ADR-0022 — Private self-reported attendance

Status: Proposed — explicit acceptance required before schema or permission work
Date: 2026-09-24
Task: TASK-018

## Context

The accepted MVP calls for attendance confirmation and an authoritative count of confirmed attendance. The current participant row records joining, leaving and removal, but none proves that someone met offline. A Hangout can have no end time, remain published after its scheduled time, or be cancelled after it began. Existing blocks and moderation can remove source visibility while retaining a person's own membership evidence. The product and engineering specs do not settle who may attest, when, whether an answer can change, or who may see it. This is a domain, privacy and authorization decision.

## Proposed decision

1. Attendance is a **private self-report**, never inferred from joining, elapsed time, location, chat activity or a host's assertion. The only answer is `attended` or `did_not_attend`. A confirmed-attendance metric counts current `attended` answers, describes them as self-reported and never claims verified physical presence. There are no peer attendance badges, rosters, public counts, host results or popularity ranking inputs in this task.
2. A caller may answer only for their own retained participant row, including host, left or removed states. The actor always comes from `auth.uid()`. An active account can read and answer its own row after profile readiness or campus membership is lost; suspended/banned accounts cannot. A block against the host or another attendee does not expose that peer or prevent this ID-only self action. An attendance-specific owner list returns at most 24 past retained Hangout IDs per keyset page, the caller's own answer and open/closed eligibility flags; it does not depend on the separate safety gate. Exact own-response reads return only Hangout ID, answer, revision and answer time. Neither path includes title, host, place, scheduled time, exact window bounds, roster, private instructions or peer feedback. Ordinary detail remains separately authorized. A disabled Hangout denies attendance listing, new answers and own answer reads, consistent with ADR-0019's student mutation/read denial; safety reporting remains available.
3. Answers open at the scheduled end when one exists, or two hours after the start when no end exists. The window closes 30 days after that opening instant. The database clock is authoritative. Once that opening instant is reached, `starts_at` and `ends_at` become immutable for that Hangout, even if the attendance gate is off; other permitted edits remain available. Before opening, a host may change either scheduled instant under the existing Hangout revision rules, and the window follows the new schedule. The edit boundary rechecks time after acquiring the same parent lock as attendance writes, so a concurrent edit cannot shift a window after an answer is admitted. A Hangout cancelled before its start cannot receive an answer. A cancellation at or after the start does not erase an answer opportunity because the gathering may have occurred; it retains the same scheduled opening and closing instants. A later moderation disable revokes attendance access as in item 2. Time passing or cancellation never creates an answer automatically.
4. A person may correct their answer within the open window using an expected revision. The first answer expects revision zero. A committed change advances a server revision. During the open window, a request whose answer equals the *current* stored answer is a no-op and returns current own state before testing its expected revision; this can recover a lost response but never restores an earlier value. A request that would change the current answer requires its exact current revision and fails stale otherwise. After the window, writes are denied and the answer is read-only while the attendance gate is enabled; exact own-read is the recovery path for a response lost at closing. The private record retains the latest answer and server timestamp, without a peer-visible history. No client may write a participant attendance column directly.
5. A new private attendance gate defaults **off** and has no client table grants. Caller-bound RPCs enforce it, the Hangout source gate for writes, active account status, the retained participant relation, the clock window, and current moderation disable state. Reads require the attendance gate and active account, and return only own rows; a Hangout source gate being off masks the optional source detail elsewhere, not this owner-only record. Stronger-than-READ-COMMITTED client mutations fail closed. Stage A must use the established social/Hangout lock order and prove cancellation, disable, account sanction, block and answer races with actual client roles. A committed revocation first denies a later action; a previously authorized action may finish before the revocation commits.
6. The student UI offers an honest attendance question for eligible past Hangouts, shows the saved answer and whether correction is open or closed, and handles a response whose outcome is unknown by re-reading the caller's exact own row before inviting another deliberate action. It explains the general 30-day rule; an exact deadline may appear only when the ordinary Hangout detail authorization independently provides its schedule. A hidden or removed Hangout is represented only by its retained ID, without source details. The UI offers the existing private safety-report path as a separate action; an attendance answer never files a report or sends an allegation. No scheduled job, stored attendance notification, push, email or Realtime subscription is part of this task.
7. This is a disposable-local increment only. Migrations are committed, all gates remain default off after reset, web routes remain local/loopback guarded, and no hosted migration, production data, gate enablement or deployment is authorized. TASK-019 may instrument an explicitly reviewed analytics path later; this decision alone authorizes no PostHog event containing attendance identity or sensitive feedback.

## Tradeoffs and remaining work

Self-reporting is useful for the product's outcome metric but cannot independently verify an offline meeting. The two-hour fallback can open before a long Hangout without an end time; it is a prompt-eligibility convention, not proof of completion. Freezing scheduled instants then prevents hosts from correcting an old time or extending an end, so the edit UI must explain that limit rather than silently fail. A 30-day correction window limits late changes but requires a future production retention policy. Safety comfort and “happened as described?” feedback need a separate privacy/moderation contract; the existing report flow is available now and an answer must never be treated as a safety finding.

## Acceptance gate

Publishing this proposal or the TASK-018 contract does not accept it. Explicit user acceptance of the exact policy is required before Stage A adds schema, RPCs or authorization exceptions. Material changes to the policy need a revised proposal and acceptance.
