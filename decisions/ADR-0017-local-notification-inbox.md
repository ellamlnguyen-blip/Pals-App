# ADR-0017 — Disposable-local notification inbox and preference policy

Status: Accepted — disposable-local TASK-015 stages only
Date: 2026-09-23
Task: TASK-015

## Context
The accepted MVP requires a Notifications tab and category preferences. `NOTIFICATIONS.md` lists requests, messages, Hangout changes, reminders, safety and attendance, but does not define which events create rows, what muting means, or what is safe to retain and display after access changes. Existing friendship, DM, Hangout and chat work is disposable-local behind separate default-off gates. TASK-010/ADR-0012, global blocking/reporting, moderation, attendance, hosted delivery and Realtime remain unresolved. Persisting notifications and changing source mutations crosses schema and privacy boundaries, so a decision is required before implementation.

## Decision
Acceptance authorizes only reviewed, narrower disposable-local TASK-015 stages. Add a separate private notification gate, disabled by default and not client-writable. Web routes additionally require `APP_ENV=local` and loopback Supabase validation. No hosted migration, live-student delivery or push follows.

### Sources and recipients
- Generate rows server-side only from committed authoritative mutations, in the same transaction as the source change. Never let a client choose a recipient, type, actor, link or payload. Exact source retries and no-op transitions make no additional notification. A source action may commit even while the notification gate is off; in that case no row is backfilled when the gate returns.
- This increment covers: incoming friendship request and acceptance to the requester; incoming first-message DM request, explicit or reply-based DM acceptance to the initiator, and later accepted-thread direct messages to the other participant; Hangout-chat message to current joined participants other than the sender; material Hangout detail update/cancellation to current joined participants other than the actor; join/leave to the current host. The atomic first reply is represented by one acceptance event, not a second message event; explicit no-body acceptance produces that same acceptance event. Its stable identity is the accepted pair generation and transition, while later message events use their server message ID. Include only supported local public Hangouts and existing roles. A message event means an item that opens the relevant conversation, never copied body text. An edit event means a meaningful committed detail change, not a mere revision retry. No participant count or mass fan-out to nonparticipants.
- Do not generate events from hidden profile browsing, People blocks, ignored/withdrawn/closed DM generations, old terminal friendship generations, or inferred offline attendance. Safety/moderation notices, attendance prompts, timed reminders, co-host events and restricted invitations wait for their owning accepted policies and implementation. The MVP category list remains a target, not a claim that these missing sources exist.

### Preferences and essential events
- Owner preferences are category-based for `social_requests`, `messages`, `hangout_updates` and `host_activity`. Each defaults on, can be turned off by its owner, and affects only *future optional inbox-row creation*. Muting does not delete existing rows, change source authorization, suppress a source action, or imply push/email consent. Preferences can be read/changed by an active owner even if readiness is lost, subject to the local gate; a suspended/banned owner cannot use the client inbox.
- A Hangout cancellation for a current participant is essential and always creates an item while the notification gate is on, even if `hangout_updates` is muted. Future security/moderation/account notices are also essential, but no such generator is authorized here. Essential items have no mute control. No friend-activity push or engagement-oriented category is introduced.
- A source feature gate being off blocks new events from that source; the notification gate being off blocks all new notification rows and inbox access. Preference writes and read-state updates require the notification gate. Previously stored rows remain private when gates are off; no automatic replay/backfill.

### Privacy, reads and lifecycle
- Store recipient, source type/opaque ID, minimal server-owned event code, server timestamp and read timestamp in private tables with RLS and no authenticated direct table grants. Do not store message bodies, peer names/photos/emails, exact locations, private Hangout instructions or copied public descriptions. Retain rows privately after source teardown for future safety policy; no client may enumerate another recipient's items. No platform-role client bypass.
- Owner-only caller-bound RPCs return at most 24 items per keyset page, plus owner preferences; mark-read is idempotent and scoped to the caller's item, with no unread reversal in this increment. The inbox can show a generic event label and time. For each item, the projection must recheck current source permission before returning a target, actor ID or source-specific label. A join/leave item may identify the departed attendee only if a current source permission independently allows that ID; otherwise it uses generic wording, since the public roster omits departed members. If the source is no longer accessible, return a neutral unavailable item with no deep link; old rows do not become a back door to revoked DM bodies, People text, private Hangout details or hidden membership. An item that was authorized before a concurrent revocation may finish that read; later reads must observe the committed revocation.
- On destination open, perform current authorization through the source's existing route/RPC; the stored notification is never proof of access. No external or arbitrary URL from the row. Every web response is no-store; signout/account switch and denied reads clear cached sensitive items. Polling may refresh only a visible bounded page, with focus refresh; no raw table Realtime publication or background delivery in this increment.
- Source mutation and notification insertion use one transaction and a stable source-event identity so concurrent/retried actions cannot make duplicates. Preference writes and event creation serialize on an existing per-recipient lock target even before that recipient has a preference row; the backend contract must choose and consistently order this lock with existing source locks. A committed mute first suppresses a later event, while an event that secured the lock first may commit before the mute. Reads and mark-read require READ COMMITTED and live caller status; test revocation and race behavior with actual client roles.

## Alternatives and tradeoffs
- Client-generated rows are rejected because they permit forged recipients and source probes.
- Copying message previews or private location into an inbox is rejected because a later block, opt-out, removal or suspension cannot retract copied text from a delivered response.
- Treating every category as muteable is rejected for cancellation and future safety/account notices, which carry operational or safety information.
- Adding push, email or Realtime now is deferred until delivery consent, stale subscriptions, revocation and hosted retention are reviewed separately.

## Consequences and acceptance evidence
This decision authorizes a private local event ledger and minimal owner inbox without changing the source feature gates or their accepted access rules. Backend source hooks and preferences are cross-cutting and must be independently security reviewed. TASK-016 still decides global block precedence/reporting; TASK-010/ADR-0012 remains Proposed. Acceptance changes no schema, route, grant or deployment by itself; narrower implementation contracts require independent review and canonical publication before dispatch.

After the complete reviewed proposal and planning contract were published on canonical main, the coordinator asked, “Do you accept ADR-0017 as written for the bounded, disposable-local TASK-015 implementation?” The user replied “yes” on 2026-09-23. This accepts the local event, muting, revocation, retention and delivery policy above. It does not accept ADR-0012, global blocking/reporting, push, email, Realtime, hosted operation or production retention.
