# ADR-0016 — Local DM request consent and direct-chat privacy

Status: Proposed
Date: 2026-09-23
Task: TASK-014

## Context
The MVP and messaging specification call for a first-message request, recipient reply/accept, ordinary one-to-one chat afterward, and ignore/block. Accepted ADR-0013 makes peer text visible only through opt-in People projections and establishes People-only directional blocks. Accepted ADR-0014 makes friendship participant-owned and gives blocks a narrow friendship teardown. Accepted ADR-0015 authorizes disposable-local Hangout chat, explicitly without global block precedence. None authorizes DM discovery, delivery, request consent or a DM effect for People blocks. Global Hangout/private-location separation and reporting remain TASK-016 decisions.

## Proposed decision
Acceptance authorizes only the disposable-local stages in TASK-014 after narrower contracts are published. A separate private DM feature gate defaults disabled and is not client-writable; web routes also require `APP_ENV=local` and validated loopback Supabase. No hosted migration, enablement or live student use follows.

### Initiation and consent
- A ready sender at the recipient's current active campus may initiate only from a recipient currently visible under the ADR-0013 People projection: recipient ready, opted in and neither direction People-blocked. Friendship, an attendee ID or an old link is not an exception. The database rechecks the target; the UI's visible button is not authority.
- The first message is a plain-text request body, trimmed to 1–2000 characters. Store at most one **active** canonical unordered pair with initiator, recipient, campus at creation, immutable generation and state `pending` or `accepted`; no duplicate or opposite pending pair. The recipient alone can explicitly accept or reply to accept; reply and acceptance are one atomic transition with its first response. The initiator cannot send another message while pending. The recipient can read the pending first message but cannot be placed in ordinary chat without their action.
- The recipient can ignore a pending request. Ignore removes the active pair from both inboxes and permanently suppresses a fresh request from the same initiator to that recipient in this local increment. It does not create a friendship or notify the sender why. The sender may withdraw a pending request; withdrawal has the same directional suppression. Closing an accepted thread likewise ends that active generation and suppresses its initiator-to-recipient direction. A block ends the active generation. Record its terminal reason privately as `ignored`, `withdrawn`, `closed` or `blocked`. A deliberate reverse-direction request may create a **new** generation only after the old pair is terminal and both parties are currently eligible; the old generation and its messages never revive. Keep terminal generation, messages, retry ledger and directional suppression privately, without client participant-list access to terminal pairs. An active pair is unique per unordered pair, and all transitions serialize on that unordered pair. Accepted threads are not reset to pending.
- Request creation and each send use a caller-scoped UUID idempotency key and a retained private ledger for exact-payload retries. Reusing a key with different content conflicts; an old key cannot reopen an ignored/withdrawn/blocked pair or send a second copy after a lost response. State transitions carry the immutable generation and reject stale actions. Do not use timestamps or client-selected actors as authority.

### Reads, sending and privacy
- Only a participant of the **current active generation** can read that pair's request/thread metadata and bounded messages while the DM gate is on. Request list projections contain only pair/generation, direction/state, server time and the first-message body for an incoming pending request; no hidden peer text, photo, email, profile copy, block reason or public count. An unavailable peer is identified by a neutral label plus the participant-owned ID needed for active-pair management. Terminal pairs have no client list, status or message-body reader, including for their former participants. Any display name must come from a fresh ADR-0013 People projection, which may return no row. No third-party or platform-role client bypass.
- New request creation, acceptance and message send require both accounts currently ready in the same active campus, both opted into People, no People block in either direction, and the relevant gates on. Existing participants may ignore/withdraw a pending request while active even if visibility/readiness later fails; this cleanup grants no message body beyond what remains readable under the next bullet. Suspended/banned callers have no client DM operations. A friendship provides no bypass. Campus transfer does not carry a thread into a cross-campus chat; future transfer/retention policy is separate.
- After either participant loses readiness, changes campus or opts out, both sides lose future client access to message bodies, including their own history, and cannot send. An active participant may still see minimal current pair ID/state and close an accepted thread or ignore/withdraw a pending request. Closing does not delete private evidence; an old generation cannot reopen. Restoring readiness/opt-in does not silently create a new generation. If eligibility returns while a pair remains active and unblocked, an accepted thread may resume; the UI states that opt-out alone pauses rather than ends it.
- A People block in either direction explicitly ends the current pending request or accepted thread in the same serialized transaction, even when the DM gate is off. The existing bilateral People-block check denies new DM creation while either direction remains blocked. Unblock never restores the terminated generation; a later new generation is possible only under current eligibility and directional suppression. Extend `set_people_block` only for this DM teardown and a narrow target exception: a ready active participant may block the peer ID of their **current active pending/accepted pair** after that peer becomes hidden, under the People gate, with current pair participation proven after the pair lock. A terminal pair alone gives no hidden-target block right or ID reader. This builds on the ADR-0014 friendship exception; it does not change Hangout discovery, membership, private instructions or Hangout chat. A user who has lost readiness can still close/ignore/withdraw a current pair where applicable but cannot create a new People block until ready.
- The UI must not describe a People block as global separation. It can accurately say it stops People discovery, friendship and this local DM pair, while Hangout access/chat remain under ADR-0010/0015 until TASK-016. Previously delivered text cannot be recalled. No automatic notification, invitation or friendship follows a request or acceptance; TASK-015 owns notification policy.

### Storage, authorization and delivery
- Store request/thread messages and retained retry/suppression records in private tables with RLS and no authenticated direct table grants. Use fixed-search-path caller-bound functions deriving `auth.uid()`, READ COMMITTED only, bounded keyset pages (at most 50 messages and 24 inbox pairs) and no raw profile/Storage reads. Messages are immutable plain text with server-owned ID/time/order; no client delete/edit. Retain records privately after ignore, close, block, gate disable and account readiness loss for future safety work. Production retention, report access and auditable moderation need separate accepted policy.
- Mutations for a pair, including People block and friendship teardown, share one deterministic unordered-pair serialization boundary. Creation/acceptance/send lock all relevant gate, account/Auth membership, profile/photo and People preference evidence through commit, then recheck in a fresh READ COMMITTED statement. A revocation committed first denies; a mutation that secured locks first may commit before revocation. Reads authorize in the same statement as their projection; a read authorized before concurrent revocation may complete afterward. No new request after committed revocation returns a body. Test opposite-direction creation, ignore/reply, block/send, gate disable, opt-out, readiness and lost-response races.
- Local UI may poll only the visible bounded page through the authorized reader, recheck on focus and after actions, and clear sensitive text on denial/signout/account transition. Each web response, including errors, is no-store. Do not publish raw tables or payloads to Supabase Realtime yet: subscription revocation and stale authorization require a separate design. No client service-role key, generic peer list or platform bypass.

## Alternatives and tradeoffs
- Let any ready student message any account ID: rejected because opt-in People would become a hidden-recipient probe and contact path.
- Let friendship bypass People opt-out: rejected because accepted friendship is not consent to indefinite DM access.
- Allow repeated requests after ignore: deferred to avoid unwanted retries; a local ignore is durable for that direction.
- Treat People blocks as global Hangout/chat separation now: deferred to TASK-016 because those access and private-location rules remain unresolved. This ADR decides only DM behavior and the explicit People-block extension above.
- Ship Realtime or notifications now: deferred until delivery revocation and notification policy are separately reviewed.

## Consequences
This creates a consent-based local DM path with explicit privacy checks and private retained evidence. It adds a narrow DM consequence to People blocks while leaving accepted Hangout behavior unchanged. Acceptance changes no schema or access by itself. TASK-016 global blocking/reporting/moderation and hosted release remain open.
