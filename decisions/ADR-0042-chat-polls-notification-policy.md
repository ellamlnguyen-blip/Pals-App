# ADR-0042 — Chat polls, co-host invitations and notification policy

Status: Accepted — bounded disposable-local implementation; hosted and application-main gates remain
Date: 2026-10-15
Task: TASK-033

## Context and existing authority

Ella requests polls in chats, automatic chat access after joining a Hangout, friend-request accept/decline and DM behavior, host and co-host notifications, a start-soon reminder, and three optional Hangout activity settings. Her current explicit request supersedes the old MVP exclusion of polls in intent. She clarified the DM rule as **friendship or accepted message request** and chose a reminder **one hour before** the Hangout. Friend-initiated direct chat changes Accepted ADR-0016's request-only formation path; co-host invitation changes Accepted ADR-0012's immediate promotion. Ella explicitly accepted the complete proposal on2026-10-15.

Existing backend already provides `accept_friend_request`/`decline_friend_request`, current joined-member Hangout chat read/send (no separate enrollment), join-to-host, DM/Hangout message and friendship-acceptance inbox events. It has a private notification ledger with `social_requests`, `messages`, `hangout_updates`, `host_activity`, default-on categories, owner preference RPCs and live source reauthorization. Current co-host RPCs directly promote/demote/step down. No poll or invitation records, start-soon scheduler, or the three independent activity preferences exist. These conclusions concern the source candidate only; they are not hosted persistence evidence.

## Accepted decision

Acceptance authorizes separately reviewed, bounded local implementation stages and additive committed migrations on the named disposable environment. Every caller is derived from `auth.uid()` under current gates, active-account, current campus/source rights and shared safety blocks. Private tables have RLS and no authenticated direct grants; functions use fixed search paths and fail closed. Do not introduce Realtime publication, push/email, a new provider, client-generated notification items, or a separate `Event` domain. In this decision, a new event means a newly published **Hangout**.

### Joined Hangout chat and friendship

Joining a currently eligible published Hangout immediately makes its existing conversation available under `private.chat_authorized`; opening or sending still rechecks current joined state, source gates, ready campus and block rules. Leave, removal, cancellation, disablement or readiness loss revokes future reads, writes and exact-send retries. No chat membership table or automatic conversation message is added. An accepted friendship and declined request retain their existing generation/transition semantics.

For DMs, retain ADR-0016's nonfriend first-message request and recipient accept/reply/ignore path. Additionally, two current accepted friends who meet every existing bilateral People, campus, account, gate and block check may start an accepted DM pair on their **first actual send**. If no pair is active, that send atomically creates a new accepted friend-origin generation and its first message. If a request pair is pending, that send atomically transitions the **same pending generation** to friend-origin accepted and appends the actual message; the pending first message remains in that active generation, and no independent recipient request acceptance is inferred. Friendship acceptance alone creates no empty conversation, changes no pending request, reads no DM history and sends no message. Store whether accepted access derives from current friendship or explicit recipient message-request acceptance; backfill existing accepted generations as request-origin because the present writer accepts only through recipient action, and preserve pending/terminal rows without state changes. An existing accepted request-origin generation stays independently consented if friendship ends. Unfriending immediately pauses a friend-origin generation unless its recipient separately and explicitly accepts DM access through an adapted request-consent action; this records independent consent, never silently. Blocking still terminates it under existing safety precedence. A later friendship may restore a still-active paused friend-origin generation only after fresh eligibility checks. Old ignored/withdrawn/closed/blocked generations, messages and retry records never revive or leak into a new generation. Retained directional suppression still stops nonfriend requests, but a **new current accepted friendship** supplies consent for a **new** friend-origin generation; it never bypasses a bilateral block. A declined friendship does not authorize DM. Exact retries recheck current consent source and access before returning any message or pair data. This is an accepted amendment to ADR-0016 for bounded local implementation; migration and verification are still required.

### Polls in DM and Hangout conversations

Polls are conversation coordination objects, not posts or public discovery content. A poll belongs to exactly one active DM generation or one Hangout conversation. Creation requires current ability to send in that conversation; read and vote require current ability to read and send there. For DM, `pending` cannot create/read/vote; only an accepted, currently eligible generation can. For Hangouts, only current ready joined members of a published authorized Hangout can act. A retained terminal DM generation, removal, leave, cancellation, block, opt-out, gate disable or campus/readiness revocation denies future poll reads, votes, closes and exact retries even for creator and prior voters. Existing prior responses cannot be recalled.

Use a single-choice poll with a trimmed plain-text question of 1–200 characters and 2–6 distinct trimmed options of 1–100 characters each. Creation supplies a caller-scoped UUID request key; private retry ledger returns the same poll only while access remains current, conflicts on changed payload, and cannot resurrect a revoked conversation. Store server-owned poll/option IDs, order, creation and close timestamps. The creator may close while still eligible; closing is one-way and idempotent. No deletion/editing, anonymous polls, attachments, write-ins, duration automation, cross-conversation sharing or discovery feed. A participant has at most one **current** vote per poll and may change it while open and eligible; serialize vote/close on the poll row after the source authorization lock. A vote retry key replays only its exact poll/option operation while still eligible and open; stale request IDs cannot reapply a prior vote after a different vote or a close. Enforce a modest creation rate (proposed: five new polls per actor per conversation in a rolling hour, exact retries excluded) and source conversation bounds; no poll notification fan-out in this increment.

Reader returns bounded polls/options and aggregate per-option counts plus the caller's own current choice. It never returns voter identities, counts for an inaccessible poll, peer metadata, message bodies or a raw vote ledger. Counts cannot be described as anonymous: a small group may infer a vote by watching changes. Present that limitation before creation. Hide removed/revoked participants' past votes from the current aggregate to avoid an old member's choice surviving as current coordination signal; retain private evidence for safety/audit under a later retention policy. Author IDs are displayed only when the source's existing projection currently permits them. Poll/list pages are keyset bounded, and one statement checks access with projection. No direct private table access.

### Co-host invitation and response

Replace immediate host promotion as the normal student path with an explicit pending invitation. Only the immutable host may invite an existing current ready joined nonhost on a published Hangout, under the same host/target/source gate, block, social mutation and Hangout revision checks as current promotion. Invitation creation uses a host-scoped request key; one pending invite per Hangout/target. Pending status conveys no co-host authority, private instructions or new membership. The recipient may accept or decline only while still joined, ready, same-campus and otherwise eligible. Acceptance atomically consumes the invitation and inserts the existing `private.hangout_cohosts` assignment through the current effective-authority rules, advancing the Hangout revision. Decline terminally consumes it without assignment. The host may withdraw; cancellation, leave, removal, block, disablement or loss of target eligibility makes the invite inactionable. Do not automatically join anyone or reopen a terminal invitation. Host demotion and co-host step-down continue to use the existing assignment model.

The existing `promote_hangout_cohost` executable path must be removed or narrowed in the same migration as invitation acceptance, including old overloads, so a student cannot bypass consent. The source should retain private invitation/request evidence and one current status; retries and concurrent host/recipient/source transitions serialize with the existing shared social lock and Hangout parent/revision lock before source and recipient locks. A lost response requires authoritative reread. Generate one invitation item to the target on a real creation, no duplicates from retries. The host reads accepted/declined state through an authoritative host-only status projection; no extra host notification is generated for either response. Read projection rechecks current source and recipient rights; inactionable/blocked items become neutral unavailable. Do not disclose the invitee ID to others through notifications.

### Notification rows, preferences and reminders

Keep the existing notification ledger and source-trigger pattern. Current join-to-host, message and friendship-acceptance events remain; use the existing `host_activity`, `messages`, and `social_requests` preferences and source rechecks. Co-host invitation adds one source-backed event code for the target; response state is read by the host without an extra event. A start-soon item is due **one hour before** start only for current joined recipients of a published Hangout whose start is still upcoming; use a backend scheduled database job or existing approved backend scheduling capability with a committed schedule/configuration and operator evidence. No browser-only timer and no new provider. Store a per-Hangout/start-time revision or equivalent stable reminder identity so scan retries create at most one item per recipient for the current schedule; reschedule invalidates stale due work and does not send a reminder for a past start. At execution recheck current status, start, participant state, campus readiness, gate, block and recipient mute under source/recipient locks. Bound batch size and fan-out; resume with a durable cursor or recurring bounded scan. Source mutations must not fail because optional fan-out is over limit or scheduler unavailable. A reminder has no copied location or message body and links only to an authorized Hangout reader. Map it to `hangout_updates`, default on, subject to the existing optional mute; cancellation remains essential.

Add **three independent** owner-scoped boolean preference categories, each default **off**: `campus_new_hangout`, `friend_created_hangout`, `friend_joined_hangout`. Their settings affect only future optional in-app rows, never source access, existing rows, or push/email consent. Campus-new targets active, current-ready users in the same campus who can presently discover the new published Hangout. Friend-created targets current accepted friends of the host who can presently discover it. Friend-joined targets current accepted friends of a newly joined participant who can presently discover it. Exclude actor and host where nonsensical, suppress blocked/ineligible recipients, avoid duplicate rows for the same recipient/Hangout/source action, and recheck authorization again at inbox read. A user may qualify for multiple categories; emit at most one item for a single source action with deterministic category precedence (`friend_created_hangout`, then `friend_joined_hangout`, then `campus_new_hangout`) only among opted-in categories. Do not imply friendship bypasses Hangout visibility. Fan-out must be bounded and asynchronous or batched behind durable source evidence so a campus-wide insert does not hold a Hangout mutation open; do not enumerate the campus through a client API. Recipient policy and preferences are checked at delivery after the standard lock order. No backfill on opt-in. If the chosen backend cannot supply durable bounded fan-out safely, defer the campus category and surface the design gap rather than implement an unbounded trigger.

For all new codes, source events and notification identity are server owned; exact retries and no-op transitions add no rows. Keep no copied message, profile, exact location or private instructions. Source gate first, notification gate then recipient advisory locks in UUID order; preference mute committed first suppresses a later optional row. Existing items become neutral on source revocation and destinations independently authorize. Failed scheduled/optional delivery never rolls back a source action. Mark-read/attention behavior remains owner-bound. No client-selected recipient or direct ledger write.
