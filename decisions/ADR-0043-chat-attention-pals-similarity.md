# ADR-0043 — Owner-private chat attention and similarity-ranked Pals discovery

Status: **Proposed; explicit Ella acceptance required before dependent schema, permission, or ranking implementation**
Date: 2026-10-15
Task: TASK-034B, under TASK-034
Baseline: canonical main `6c984dd`; application dependency `c63992d` (TASK-033 candidate remains gated)

## Context

Ella requests an unread indicator on each currently authorized chat, a combined inbox ordered globally by recent visible message or the owner's last use, and Pals discovery ordered by similarity of saved interests, graduation year, hometown, and major with **major and year filters only**. The existing `/api/chats` interleaves two source batches: `list_dm_inbox` orders DM generations by creation time and the Hangout participant query orders IDs; the web layer sorts only that bounded mixture. `browse_people` currently offers a name query and name/ID keyset. Message sequences are already server assigned and immutable within a DM generation or Hangout conversation. Hangout readers omit blocked authors; DM pending and accepted reads have different consent rules. Raw profile fields, including hometown, are owner-only; peer hometown requires the separate rich consent projection. Source code is not hosted persistence evidence.

This changes the schema, authorization projections, and discovery behavior. The requested outcome authorizes this proposal, not acceptance of its policy. No hosted write, gate enablement, release, or application-main integration follows from acceptance.

## Proposed decision

### Conversation identity and owner state

Add one private, RLS-enabled, client-revoked owner attention row per `(owner_id, source_kind, source_id)`, where `source_kind` is `dm` or `hangout`, `source_id` is the **DM generation UUID** or **Hangout UUID**. Store nonnegative `read_through_sequence`, nullable server-owned `last_used_at`, and server timestamps. This is a private owner preference/attention record, not a read receipt. Never show it to the peer, host, other participants, moderators by default, or public profile. Account deletion follows existing privacy/deletion policy. No copied body, actor roster, location, title, or derived behavioral score is persisted.

The row grants no access. Every read, acknowledge, and touch rechecks the currently effective source, account/campus/pilot gates, membership, bilateral block, and DM state/consent. A current Hangout row requires `private.chat_authorized` and current joined membership; a DM row is returned only to a current participant in an active generation and must observe the exact readable-message rule. Pending DM recipient may see the pending first message while eligible; pending initiator retains management metadata but no readable-message/unread claim. A paused accepted friend-origin DM may retain management metadata but neither unread body-derived signal nor a touch/ack until consent returns. Terminal generations and revoked Hangouts remain private history, never revived by attention state. A later DM generation has a fresh row and watermark. Hangout leave/rejoin uses the same Hangout row: the former watermark persists, and newly visible incoming messages above it may become unread after rejoin; leaving itself reveals no activity.

### Unread and acknowledgment

Unread is true only when at least one **currently visible incoming** message has sequence greater than the owner's acknowledged watermark. Own messages never count; hidden blocked-author Hangout messages never count; unseen future messages never clear. Inbox rows may return a boolean `has_unread`, not an unread count, raw watermark, hidden high sequence, or peer receipt. Eligibility is evaluated before computing the boolean. A newly created conversation without an owner row starts at zero. The additive migration baselines only **currently authorized** existing owner/source rows to the maximum currently visible sequence. Other historical sources start at zero if access later returns; their newly visible history may produce an honest unread badge. No timestamp cutoff or deferred backfill is used. Never backfill raw messages to a client.

Opening the inbox, following a notification, viewing a conversation shell, polling a summary, or sending a message does **not** acknowledge incoming text. Both thread readers page visible messages forward by immutable sequence, at most 50 per page. The foreground UI acknowledges only after a successful authorized page has rendered, supplying its highest visible sequence. The RPC rechecks owner/source/generation and current consent, derives the first at most 50 currently visible messages **after the current watermark**, and accepts an upper sequence only if it is one of those messages. It advances monotonically and idempotently, so no caller can jump over a visible unread page or forge a future sequence. If the UI begins on older pages below a migration baseline, acknowledgments are harmless until it reaches new messages. A client cannot prove pixels were seen and can mark its own first forward page read; the server enforces bounded sequence validity, not human attention. No peer receipt or cross-user signal is emitted. An authorization change forces a fresh forward read; later incoming messages remain unread until their page renders.

### Last use and global inbox

`touch_chat(source)` records `clock_timestamp()` on the server after current source authorization and real visible thread entry; the caller supplies neither a time nor an owner ID. Treat a source-management page or notification navigation as insufficient. Throttle repeated touches per owner/source within a short interval and never let a stale retry move time backward. Touch itself does not clear unread. An owner may use a message-free joined Hangout or accepted DM; this use may move that row upward. Pending management requests retain their existing management entry and may use creation-time fallback, but no fabricated readable-message activity.

Replace two independently paged source lists with one caller-bound `list_my_chat_attention` RPC. For each **currently authorized** DM generation or current joined Hangout, compute the newest message currently visible to this owner under the same read predicates as the thread API. The sort time is `greatest(latest_visible_message.created_at, valid_owner_last_used_at)`; if neither exists, use source creation time. Order descending by `(sort_time, source_kind, source_id)` using a fixed bytewise kind order and UUID tie break. Return a bounded page (maximum 24), source identifiers and permitted minimal labels/management state, `has_unread`, and a cursor. Never use a hidden message's timestamp or sequence, stale owner row, other participant's activity, or a denied source to determine rank, presence, or `has_more`.

The first page creates a short-lived private ordered-ID snapshot for this owner, storing the source identity and rank order after evaluating **all** eligible sources, before limit. A caller-bound opaque cursor refers to that snapshot and an offset; it carries no raw peer activity or hidden IDs. Each later page reauthorizes each candidate live, recomputes unread from current visibility, and drops revoked rows. The page scans past revoked IDs to fill the bounded output; `has_more` and the next cursor are based only on **remaining live-authorized** candidates, never raw snapshot length. A new message or touch after snapshot creation can change order only on refresh; do not claim a frozen database view across requests. The backend tests more than 24 of either kind. Snapshot expiry returns a generic stale response and requires refresh. The web discards the cursor and refreshes after local send/touch/revocation or stale response. Closing a page does not extend its TTL.

### Similarity-ranked Pals

Add a separate caller-bound `browse_similar_pals(major?, graduation_year?, cursor?, limit<=24)` projection. It uses the same current-ready owner, same-campus, subject People opt-in, account/email/campus, pilot/gate, and bilateral block checks as `private.people_visible`. It excludes self. **First** filter the complete eligible set by normalized exact major and exact graduation year. No name-search parameter, hidden-subject count, or enumeration path is added. Reject unknown inputs and stale/forged cursors with a generic invalid/stale response.

Score only saved fields: +2 per distinct normalized shared interest, capped at four matches (+8); +3 exact major; +2 exact year; +1 exact hometown. Normalize with Unicode-aware lowercasing, trim and whitespace collapse, using deterministic database collation; do not infer hometown from location. Empty/missing values add zero, not a penalty. Hometown contributes only where the subject's optional hometown is **currently allowed by the rich sharing boundary** as well as People visibility; never read owner-only subject hometown into ranking when that consent/gate is absent. The owner's own saved hometown may be used without publishing it. Return no raw score, match explanation, unmatched private attributes, friend count, or popularity signal. Order by score descending, normalized visible name ascending, account UUID ascending. Friendship does not add score in this stage; the requested heart and outgoing clock are separate owner-relative status projections and confer no profile access.

The first page creates a short-lived private ordered-ID snapshot bound to the owner, normalized filters, campus, owner profile revision and ranking-policy version. For each ID the private snapshot also saves the subject profile and rich-preference revisions, **not** field values or scores. An opaque cursor carries only the snapshot handle and offset. Candidate order is deterministic as of the first page; owner edit, candidate profile/rich-preference revision change, or TTL expiry returns a generic stale response and refreshes the rank. On **every** later page, each candidate is checked again for current People/rich sharing, account/campus/gate, bilateral block and the requested major/year filters. Revoked or newly mismatched rows are omitted and safe display fields are fetched fresh. Scanning skips revoked IDs to fill a page; `has_more`/cursor existence depends only on remaining live-authorized candidates. A rich-consent withdrawal cannot expose a rank calculated with now-private hometown because its revision invalidates the snapshot. This bounded as-of-first-page behavior avoids broad epoch triggers across unrelated writers. No browsing history or external provider is created.

For either surface, keep at most one active snapshot per owner and surface, replace it on a new first-page request, cap stored candidate IDs at 10,000, rate-limit snapshot creation per owner, and expire snapshots after five minutes. If the campus exceeds the cap, return a generic bounded-work error rather than a partial list. The migration provides bounded expired-row cleanup through the existing local job mechanism, with account deletion cascading snapshots. These limits prevent repeated refreshes from accumulating private ordered lists.

### Security and compatibility

Migrations are additive, committed, default-deny private tables, explicit `REVOKE` from client roles, fixed `search_path` security-definer RPCs, `auth.uid()` ownership, READ COMMITTED source checks, bounded input/outputs and existing lock order. Preserve notification read state separately; a notification is not a chat acknowledgment. Do not expand raw `profiles`, private message, participant, or Storage grants. Preserve old RPCs for existing clients until the web switches, or revoke only in a separately reviewed compatibility step; old name search must not remain exposed as a product route once the new Pals UI is active. No Realtime, push, AI model, behavioral tracking, inferred location, or new provider.

## Alternatives and consequences

Client-local read times cannot persist across devices or resist forged future timestamps. Sorting separate 24-row DM/Hangout batches cannot produce a globally correct page. Ranking on raw hometown without rich consent would turn a private field into a hidden inference oracle. Private ordered-ID snapshots make a page stable while live authorization keeps revocation authoritative. Their TTL, owner binding and cleanup add bounded storage and migration work; retained order may be briefly stale after a new message or profile edit, and refresh recomputes it.

## Acceptance and rollout gates

Ella must explicitly accept this **specific** proposed policy before attention/ranking backend implementation. Then publish two disjoint bounded contracts and perform fresh security review of migrations, RLS/grants, exact API replacement, cursor invalidation, hidden-source races, migration idempotency, upgrade compatibility, >24 pagination, and denied/allowed persistence. Disposable-local verification may follow reviewed committed migrations. Hosted application and final feature completion require Ella's separate final candidate sign-off, named target persistence/authorized-read evidence, application-main review/integration, and remote SHA verification under `AGENTS.md`.
